# MediaVault UIモックリファレンス

MediaVaultのフロントエンド画面構成は `docs/frontend/ui/` 配下に、HTMLモックとして定義されている。
Obsidianライクな3ペイン・ダークUIを基調としたデザインシステムであり、新規画面の設計や既存画面の
改修を行う際はこれらのモックを正のドキュメントとして参照する。記憶や一般的なUIパターンからの
推測で設計すると、既存画面との一貫性が崩れる（配色トークン、コンポーネント命名、レイアウト構造の
ズレなど）。

## 作業手順

1. **まず `docs/frontend/ui/_shared.css` を読む。**
   全画面共通のデザイントークンとコンポーネントクラスが定義されている:
   - CSSカスタムプロパティ（`--bg-app`, `--accent`, `--text-muted` 等の配色、`--font-display`
     / `--font-ui` / `--font-mono` のフォント使い分け、`--sidebar-w` / `--properties-w` の
     レイアウト寸法）
   - 共通コンポーネントクラス（`.app-shell`, `.sidebar`, `.titlebar`, `.card-grid` /
     `.media-card`, `.tag-pill`, `.properties` / `.prop-row`, `.btn` 系, `.form-grid` /
     `.form-field`, `.settings-shell` / `.settings-tab`, `.result-row`, `.doc-section` /
     `.group-block` 等）

   これを飛ばすと、独自のスタイルを新たに作ってしまい、既存画面と見た目が揃わなくなる。

2. **タスクに関係する画面モックを特定して読む。**

   | ファイル | 画面 | 特徴的な構造 |
   |---|---|---|
   | `01_home.html` | 全体一覧 | サイドバーのカテゴリツリー、フィルタチップ、カードグリッド |
   | `02_item_detail.html` | 作品詳細 | 3ペイン構成（サイドバー＋本文＋右側プロパティパネル）、シーズン/エピソード表示、Properties/タグ/カテゴリ/関連付け/スタッフ/マイリストの各セクション |
   | `03_search_add.html` | 検索・追加 | 外部API種別ごとのフィルタチップ、検索結果の`.result-row`一覧、手動追加への導線 |
   | `04_item_form.html` | 手動追加・編集フォーム | `.form-grid`による2カラムフォーム、必須/エラー/ヒント表現、メディア種別ごとの独自項目欄 |
   | `05_settings.html` | 設定 | `.settings-shell`によるタブ＋パネル構成、APIキー管理の`.kv-card` |

   サイドバーのナビゲーション構造（全体一覧／一般メディアとそのインデントされた子カテゴリ／
   学術書・専門書／論文・文献、ライブラリ配下のマイリスト・タグ/カテゴリ・スタッフ、設定）は
   全モックで共通なので、新規画面を作る場合もこの構造を踏襲する。

   1つの画面が複数の関心事にまたがる場合（例: 詳細画面はカード一覧のバッジ表現とプロパティ
   パネルの両方に関わる）は、関係するモックを複数読むこと。

3. **読んだ内容をレイアウト・コンポーネントの正として扱う。** 画面設計やタスク定義を書く際は:
   - 新規要素は既存クラス（`.chip`, `.status-dot`, `.empty-state` 等）やCSS変数で表現できないか
     まず検討し、できるならそれを使う設計にする
   - 3ペイン構成（`.app-shell.has-properties`）を使うか2ペイン構成（`.app-shell`）を使うかは、
     対象データが「プロパティパネルに出すべき属性群」を持つかどうかで判断する（詳細画面は3ペイン、
     一覧・検索・フォーム・設定は2ペイン）
   - 独自のUIパターンが本当に必要な場合のみ新規定義し、既存モックにない場合はユーザーに確認するか
     「モックへの追加が必要」と明示する

4. **画面構成を追加・変更した場合**、対応するモックHTML（共通トークンやコンポーネントが増える
   場合は `_shared.css` も）を更新し、`docs/frontend/ui/` を正の情報源として保つ。

## 実装（React化）が必要な場合

モックの内容を実際にReact + TypeScriptコンポーネントへ変換する作業は、このスキルの範囲外。
`mock-to-react` スキルに引き継ぐ。このスキルは設計方針・画面構成・レイアウトの意思決定に
モックを反映させる段階を担う。
