## 0. 開発言語・テストフレームワーク

### プログラミング言語

- **プログラミング言語**: Rust（1.70+）
  - **言語選択の理由**: 既存の MediaVault バックエンド全体が Rust + Axum + sqlx で実装されており、TASK-0031 は既存資産（`item_repository`, `api_credential_repository`, `api-client-lib::clients::steam`）を再利用するため、同一言語が必須。
  - **テストに適した機能**: `#[cfg(test)]` によるインラインテスト、`Result`/`enum` による網羅的なエラー表現、所有権モデルによる副作用の局所化、コンパイル時の型検証でテストの前提条件を保証できる。
- 🔵 信頼性レベル: note.md「1. 技術スタック」「言語・ランタイム: Rust 1.70+」に直接対応

### テストフレームワーク

- **テストフレームワーク**: `cargo test`（標準）+ `tokio::test`（非同期）+ `wiremock` 0.6（Steam Web API モック）
  - **フレームワーク選択の理由**: note.md「テストフレームワーク: cargo test（インラインテスト）+ tokio::test（非同期テスト）」「HTTPモック: wiremock 0.6（Steam Web APIモック）」に準拠。TASK-0030 の `import_booklog.rs` がインラインテストパターンを確立済み。
  - **テスト実行環境**:
    - DB非依存ユニットテスト: `cargo test -p mediavault-api`
    - DB依存統合テスト: `DATABASE_URL=postgres://... cargo test -- --ignored`（`#[ignore]` 属性付き）
    - PostgreSQL コンテナ: `docker compose up -d db`（プロジェクトルート）
- 🔵 信頼性レベル: note.md「5. テスト関連情報」「テスト実行方法」に直接対応

### テストの分類方針（DB依存性）

- **DB非依存ユニットテスト**（`cargo test`で常時実行）: `steam_id` 形式検証、`SteamGameEntry → CreateItemRequest` 変換、`ImportSummary` 集計ロジック、エラー型マッピング。`ApiCredentialLookup::Fixed` でAPIキーをDI注入（TASK-0023パターン）し、wiremock で Steam API をモックする。
- **DB依存統合テスト**（`#[ignore]`、`--ignored`で明示実行）: 実テストDBへの `items`/`game_details` 登録、重複スキップ、トランザクション原子性の確認。
- 🔵 信頼性レベル: note.md「DB非依存テストは`test_pool()`、DB依存は`unreachable_pool()`」「`#[ignore]` - DB依存テスト」に対応

## 1. 正常系テストケース（基本的な動作）

### TC-017-01: 正常な所持ゲーム一覧の一括登録（複数件）

- **テスト名**: 有効なAPIキー・複数ゲーム返却時の一括登録成功
  - **何をテストするか**: 有効な Steam APIキーが設定済みで、Steam Web API が複数件の所持ゲームを返すとき、全ゲームが `items`(`media_type=game`, `source=api`)+`game_details`(`steam_appid`) として登録され、`ImportSummary` の `success_count` が件数と一致すること。
  - **期待される動作**: `steam_id` 検証 → APIキー取得 → `get_owned_games` 呼び出し → 各 `SteamGameEntry` を `CreateItemRequest`(`media_type=game`,`source=api`,`external_id=appid`) に変換 → `create_item_with_source` で登録 → 結果集計 → `200 OK` で `ImportSummary` 返却。
- **入力値**:
  - リクエストボディ: `{ "steam_id": "76561198000000000" }`
  - Steam API モックレスポンス: `game_count=2`, `games=[{appid:440,name:"Team Fortress 2",playtime_forever:1200,...}, {appid:570,name:"Dota 2",playtime_forever:600,...}]`
  - APIキー: `ApiCredentialLookup::Fixed("valid-steam-key")` で注入
  - **入力データの意味**: `76561198000000000` は17桁の正規 SteamID64 の代表値（要件定義書2章のリクエスト例と一致）。2件のゲームは「複数件登録」の最小代表ケース（appid 440/570 は実在の Steam appid で現実的）。
- **期待される結果**:
  - HTTPステータス: `200 OK`
  - レスポンスボディ: `{ "success": true, "data": { "success_count": 2, "failure_count": 0, "failures": [] } }`
  - DB（統合テスト）: `items` に2行（`media_type=game`,`source=api`,`external_id` がそれぞれ `"440"`/`"570"`）、`game_details` に対応する2行（`steam_appid=440`/`570`）。
  - **期待結果の理由**: TC-017-01 の受け入れ基準「取得件数分の `items`+`game_details` が登録され `success_count` が件数と一致する」に直接対応。
- **テストの目的**: 主要正常フロー（取得 → 変換 → 登録 → 集計）が件数整合性を保って動作することを確認する。
  - **確認ポイント**: `success_count == games.len()`、`media_type=game`/`source=api` が正しく設定されること、`external_id` が appid を文字列化したものになること。
- 🔵 信頼性レベル: TASK-0031.md「単体テスト要件 テストケース1（TC-017-01）」・要件定義書4章「正常系（TC-017-01）」に直接対応

### TC-017-N02: 単一ゲームの登録成功（最小正常系）

- **テスト名**: 所持ゲーム1件のみ返却時の登録成功
  - **何をテストするか**: Steam API が1件だけ返す場合に、1件が正しく登録され `success_count=1` となること。
  - **期待される動作**: 1件分の変換・登録が行われ、`ImportSummary { success_count:1, failure_count:0, failures:[] }` を返す。
- **入力値**:
  - `{ "steam_id": "76561198000000000" }`
  - Steam API モック: `game_count=1`, `games=[{appid:730,name:"Counter-Strike",playtime_forever:0,...}]`
  - **入力データの意味**: 「複数」と「空」の中間にあたる最小単位（1件）の登録を独立に検証する。`playtime_forever:0`（未プレイ）も妥当な現実値。
- **期待される結果**: `200 OK`, `{ success_count:1, failure_count:0, failures:[] }`、`items`/`game_details` 各1行。
  - **期待結果の理由**: 件数集計が0/複数だけでなく1でも正しいことを保証する（オフバイワンの検出）。
- **テストの目的**: 単一要素ループの正当性を確認する。
  - **確認ポイント**: `playtime_forever:0` でも登録が成功し失敗扱いにならないこと。
- 🟡 信頼性レベル: TC-017-01（複数）からの妥当な細分化。単一件の明示テストは要件に直接の記述はないが網羅性のため追加

### TC-017-N03: ItemSource=Api / media_type=game としての登録確認

- **テスト名**: 登録アイテムの source/media_type 属性確認
  - **何をテストするか**: 変換結果の `CreateItemRequest` が `source=ItemSource::Api`、`media_type=game`、`external_id=Some(appid.to_string())` を持つこと（DB非依存の変換ロジック単体テスト）。
  - **期待される動作**: `SteamGameEntry { appid:440, name:Some("Team Fortress 2"), playtime_forever:1200, .. }` → `CreateItemRequest { title:"Team Fortress 2", media_type:Game, .. }`、source/external_id が正しく付与される。
- **入力値**: `SteamGameEntry { appid:440, name:Some("Team Fortress 2"), playtime_forever:1200, img_icon_url:Some("...") }`
  - **入力データの意味**: TASK-0030 の TC-021-02「ItemSource::Manual として登録確認」に対応する、Steam版（Api）の属性検証ケース。
- **期待される結果**: 変換後オブジェクトで `media_type == Game`、`source == ItemSource::Api`、`external_id == Some("440")`、`title == "Team Fortress 2"`。
  - **期待結果の理由**: 要件定義書2章「各 `SteamGameEntry` → `CreateItemRequest`(`media_type=game`,`source=api`,`external_id=appid`)」に直接対応。
- **テストの目的**: 外部API型 → 内部登録型のマッピング正当性を、DB依存なしで高速に検証する。
  - **確認ポイント**: `appid:u32` が `external_id:String` へ正しく文字列化されること（`"440"`、ゼロ埋めなし）。
- 🔵 信頼性レベル: 要件定義書2章のデータフロー・TASK-0030 TC-021-02 の対称ケースに対応

### TC-017-02: プロフィール非公開（空配列）時の正常終了

- **テスト名**: 所持ゲーム0件（空配列）時の正常終了
  - **何をテストするか**: Steam プロフィールが非公開等で API が空配列を返す場合、エラーとせず `success_count=0, failure_count=0, failures=[]` で `200 OK` を返すこと。
  - **期待される動作**: 空配列に対してループが0回実行され、空の `ImportSummary` を正常返却する。
- **入力値**:
  - `{ "steam_id": "76561198000000000" }`
  - Steam API モック: `game_count=0`, `games=[]`（HTTP 200）
  - **入力データの意味**: Steam Web API はプロフィール非公開時にエラーではなく空のゲーム一覧を返す（prep.md・TASK-0031注意事項記載の仕様）。
- **期待される結果**: `200 OK`, `{ "success": true, "data": { "success_count":0, "failure_count":0, "failures":[] } }`、`items`/`game_details` に変化なし。
  - **期待結果の理由**: TASK-0031注意事項「この場合は `success_count=0, failure_count=0` として正常終了させ、エラーとはしない設計とする」に直接対応。
- **テストの目的**: 空入力を異常系ではなく正常系として扱う仕様を確認する。
  - **確認ポイント**: 空配列で `401`/`400`/`500` を返さないこと、`ImportSummary::empty()` 相当が返ること。
- 🟡 信頼性レベル: TASK-0031.md注意事項・要件定義書4章「プロフィール非公開（TC-017-02）」に対応（空配列の返却挙動はSteam API仕様の妥当な推測を含む）

## 2. 異常系テストケース（エラーハンドリング）

### TC-017-E01: Steam APIキー未設定・無効時の401

- **テスト名**: APIキー無効/未設定時の STEAM_API_KEY_INVALID（401）
  - **エラーケースの概要**: Steam APIキーが DB に未登録、または Steam Web API が認証エラー（401/403相当）を返すケース。
  - **エラー処理の重要性**: APIキーの設定漏れ・失効はローカル運用で頻出する。安全に 401 を返し、キー内容を漏らさず、後続のDB登録に進ませないことが必須。
- **入力値**:
  - **ケースA（未設定）**: `{ "steam_id": "76561198000000000" }`、APIキー lookup が `None`（`api_credentials` に Steam キーなし）
  - **ケースB（無効）**: APIキーは存在するが、Steam API モックが `401`（または `403`）を返す
  - **不正な理由**: ケースAはキー欠如、ケースBはSteam側がキーを認証拒否したもので、いずれも有効な所持ゲーム取得が不可能。
  - **実際の発生シナリオ**: ユーザーが `PUT /settings/api-keys/steam` での登録前にインポートを実行した／登録キーが失効・誤入力された場面。
- **期待される結果**:
  - HTTPステータス: `401 Unauthorized`
  - レスポンスボディ: `{ "success": false, "error": { "code": "STEAM_API_KEY_INVALID", "message": "..." } }`
  - **エラーメッセージの内容**: APIキーが無効/未設定である旨を示し、キー文字列そのものは含めない。
  - **システムの安全性**: DB登録は一切実行されず、`items`/`game_details` に副作用がない。
- **テストの目的**: 認証失敗を専用エラーコード `STEAM_API_KEY_INVALID` + 401 へ正しくマッピングすることを確認する。
  - **品質保証の観点**: セキュリティ要件（キー漏洩防止・認証失敗の安全停止）と新規エラーコード追加の正当性を担保する。
- 🔵 信頼性レベル: TASK-0031.md「テストケース2（TC-017-E01）」・要件定義書3章/4章「STEAM_API_KEY_INVALID（401）」に直接対応

### TC-017-E02: 一部ゲーム登録失敗時のスキップ継続（EDGE-002）

- **テスト名**: 1件登録失敗でも他ゲーム登録が継続される
  - **エラーケースの概要**: 取得した複数件のうち1件が DB制約違反・変換失敗（例: `name` が `None` で必須項目を満たせない）等で登録失敗するケース。
  - **エラー処理の重要性**: 1件の失敗で一括インポート全体が中断すると、ユーザーは何件登録できたか分からず再実行も困難になる。部分成功を許容し失敗を可視化することがEDGE-002の趣旨。
- **入力値**:
  - Steam API モック: 3件返却。うち1件が登録失敗を誘発するデータ（例: `{appid:0, name:None, ..}` または既存登録と一意制約衝突する appid）。
  - **不正な理由**: 当該1件は必須項目（タイトル）欠如、もしくはDB一意制約違反で `create_item_with_source` が `Err` を返す。
  - **実際の発生シナリオ**: Steam API が稀に `name` を欠いたエントリを返す／DB側の制約に抵触するデータが混在する場面。
- **期待される結果**:
  - HTTPステータス: `200 OK`（全体は正常終了）
  - レスポンスボディ: `{ success_count:2, failure_count:1, failures:[{ <識別子>, reason:"..." }] }`
  - 正常な2件は `items`/`game_details` に登録される。
  - **エラーメッセージの内容**: `failures` に失敗ゲームの識別情報と理由が記録される。
  - **システムの安全性**: 失敗1件のトランザクションのみロールバックされ、他2件には影響しない（ゲーム単位でトランザクションを分離する）。
- **テストの目的**: 部分失敗時の処理継続と失敗記録（EDGE-002）を確認する。
  - **品質保証の観点**: 一括処理の耐障害性を保証し、ユーザーへ正確な成否内訳を返す。
- 🟡 信頼性レベル: TASK-0031.md「テストケース3（EDGE-002）」・要件定義書4章に対応。失敗を誘発する具体データ（appid:0/name:None）は妥当な推測

### TC-017-E03: steam_id 形式不正時の400（VALIDATION_ERROR）

- **テスト名**: 不正な steam_id 入力時の VALIDATION_ERROR（400）
  - **エラーケースの概要**: `steam_id` が空文字・非数値・桁数不正などSteamID64形式に合致しないケース。
  - **エラー処理の重要性**: 不正な `steam_id` で Steam API を呼び出すと無駄な外部通信・誤った結果を招くため、ハンドラ段階で早期に弾く必要がある。
- **入力値**（パラメタライズ）:
  - 空文字: `{ "steam_id": "" }`
  - 非数値混在: `{ "steam_id": "7656119800000000a" }`
  - 桁数不足（16桁）: `{ "steam_id": "7656119800000000" }`
  - 桁数超過（18桁）: `{ "steam_id": "765611980000000000" }`
  - **不正な理由**: いずれも検証式 `steam_id.len() == 17 && steam_id.chars().all(|c| c.is_numeric())` を満たさない。
  - **実際の発生シナリオ**: ユーザーが SteamID ではなくプロフィール名/URL を貼り付けた、桁を打ち間違えた場面。
- **期待される結果**:
  - HTTPステータス: `400 Bad Request`
  - レスポンスボディ: `{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "..." } }`
  - **エラーメッセージの内容**: `steam_id` が SteamID64 形式でない旨を示す。
  - **システムの安全性**: Steam API 呼び出し・DB登録のいずれにも進まない（外部副作用ゼロ）。
- **テストの目的**: 入力検証が外部API呼び出し前に機能することを確認する。
  - **品質保証の観点**: 無駄な外部通信の抑止と早期失敗による堅牢性を担保する。
- 🟡 信頼性レベル: TASK-0031.md「テストケース4」・note.md「SteamID64 形式検証」に対応。各不正パターンの具体例は検証式からの妥当な展開

### TC-017-E04: 外部APIタイムアウト/ネットワークエラー時の502

- **テスト名**: Steam APIタイムアウト時の EXTERNAL_API_TIMEOUT（502）
  - **エラーケースの概要**: Steam Web API がタイムアウト、または接続エラー（到達不能）を返すケース。
  - **エラー処理の重要性**: 外部API障害をクライアントに区別可能なエラー（502系）として返すことで、認証エラー（401）や入力エラー（400）と混同させず、リトライ判断を可能にする。
- **入力値**:
  - 有効な `steam_id` + 有効なAPIキー、ただし Steam API モックが遅延（タイムアウト超過）または接続拒否を返す。
  - **不正な理由**: 入力自体は正当だが外部依存が応答しないため処理を完了できない。
  - **実際の発生シナリオ**: Steam 側の一時障害・ネットワーク断・レート制限による遅延。
- **期待される結果**:
  - HTTPステータス: `502 Bad Gateway`（相当）
  - レスポンスボディ: `{ "success": false, "error": { "code": "EXTERNAL_API_TIMEOUT", "message": "..." } }`
  - **エラーメッセージの内容**: 外部APIが応答しなかった旨を示す。
  - **システムの安全性**: DB登録は実行されない。
- **テストの目的**: 外部API障害が `EXTERNAL_API_TIMEOUT`(502) へマッピングされること（TASK-0018/0019パターン再利用）を確認する。
  - **品質保証の観点**: 障害種別の切り分けとリトライ可能性の明示。
- 🟡 信頼性レベル: TASK-0031.md注意事項・要件定義書4章「外部APIタイムアウト」に対応。502マッピングはTASK-0018/0019パターンからの再利用（妥当な推測）

### TC-017-E05: 重複 steam_appid のスキップ（重複は失敗扱いにしない）

- **テスト名**: 既登録 steam_appid を含む一覧の重複スキップ
  - **エラーケースの概要**: 既に同一 `steam_appid` で `items`(`media_type=game`,`source=api`) に登録済みのゲームを含む所持ゲーム一覧をインポートするケース。
  - **エラー処理の重要性**: 再インポートや差分インポートのたびに重複行が増えると、コレクションが汚染される。重複は静かにスキップ（または更新）し、`failure` には数えない設計が必須。
- **入力値**:
  - 事前状態: `items` に `(media_type=game, source=api, external_id="440")` が1件登録済み。
  - Steam API モック: `games=[{appid:440,..}, {appid:570,..}]`（440は既登録、570は新規）。
  - **不正な理由**: 不正というより「重複」。`(media_type=game, source=api, external_id=440)` で既存チェックがヒットする。
  - **実際の発生シナリオ**: ユーザーが同一 `steam_id` を再度インポートした、ライブラリに新規ゲームが1本追加された後の差分取り込み。
- **期待される結果**:
  - HTTPステータス: `200 OK`
  - レスポンスボディ: 新規登録された 570 のみが成功カウントされ、`failure_count=0`（重複は失敗ではない）。
    - 想定: `{ success_count:1, failure_count:0, failures:[] }`（重複1件はスキップ＝集計外、または更新として success にカウント。**集計方針は実装で確定が必要**）。
  - DB: `external_id="440"` の行は二重登録されず1件のまま、`external_id="570"` が新規1件追加。

## 3. 境界値テストケース（最小値・最大値・null等）

### TC-017-B01: steam_id がちょうど17桁（境界の内側）

- **テスト名**: 17桁ちょうどの steam_id 受理
  - **境界値の意味**: 検証式 `len() == 17` の合格境界。16桁/18桁は不合格、17桁が唯一の合格桁数。
  - **境界値での動作保証**: 桁数判定がオフバイワンなく `== 17` で機能すること。
- **入力値**: `{ "steam_id": "76561198000000000" }`（17桁・全数字）
  - **境界値選択の根拠**: SteamID64 の正規桁数（17桁）であり、合格側の境界そのもの。
  - **実際の使用場面**: 正規の SteamID64 を入力する通常運用。
- **期待される結果**: 検証通過 → API呼び出しへ進む（`400` にならない）。
  - **境界での正確性**: 17桁が確実に受理されること。
  - **一貫した動作**: 16桁(E03)で拒否、17桁(B01)で受理、18桁(E03)で拒否という一貫性。
- **テストの目的**: 桁数境界の合格側を確認する。
  - **堅牢性の確認**: 境界条件での判定の正確性。
- 🔵 信頼性レベル: note.md「17桁の数値文字列」検証式に直接対応

### TC-017-B02: name が None のゲームエントリの扱い

- **テスト名**: name=None エントリの登録時挙動
  - **境界値の意味**: `SteamGameEntry.name` は `Option<String>` であり、`None`（タイトル欠如）は境界的な入力。タイトルは `items` の必須項目になり得る。
  - **境界値での動作保証**: `None` のとき「フォールバック値で登録」「failure として記録」のいずれかへ一貫してルーティングされること。
- **入力値**: `SteamGameEntry { appid:99999, name:None, playtime_forever:0, img_icon_url:None }`
  - **境界値選択の根拠**: `Option` の `None` 側境界。`include_appinfo:false` 相当や API の欠損時に発生し得る。
  - **実際の使用場面**: `include_appinfo` が無効、または Steam 側でゲーム名が取得できなかった場合。
- **期待される結果**: **実装方針に依存**。
  - 方針A（フォールバック）: `title = "Unknown (appid:99999)"` 等で登録 → `success_count` 加算。
  - 方針B（失敗記録）: タイトル必須のため `failures` に記録 → `failure_count` 加算（EDGE-002流）。
  - **境界での正確性**: `None` が `unwrap` でパニックせず、いずれかの分岐で安全に処理されること（パニック禁止）。
  - **一貫した動作**: `Some(name)` は通常登録、`None` は一貫した方針で処理。
- **テストの目的**: `Option` の `None` 境界が安全に処理されること、および採用方針の確認。
  - **堅牢性の確認**: 欠損データでパニック・全体中断しないこと。
- 🟡 信頼性レベル: note.md「API レスポンス: ゲーム appid・名前の null チェック」に対応。方針A/Bのどちらを採るかは実装で確定（未確定事項）

### TC-017-B03: 多数ゲーム（大量件数）の一括登録

- **テスト名**: 大量ゲーム（例: 500件）の一括登録
  - **境界値の意味**: バッチ処理の上限側境界。1件のトランザクション処理（note.mdのバッチ最適化）が大量件数でも破綻しないこと。
  - **境界値での動作保証**: 件数が増えても全件登録され `success_count == 件数` を保つこと。
- **入力値**: Steam API モックが 500件の `SteamGameEntry`（appid を一意に振った合成データ）を返す。
  - **境界値選択の根拠**: ヘビーユーザーのライブラリ規模（数百本）を想定した現実的上限。
  - **実際の使用場面**: 大規模 Steam ライブラリを持つユーザーのインポート。
- **期待される結果**: `200 OK`, `success_count == 500`, `failure_count == 0`。タイムアウト・メモリ破綻なし。
  - **境界での正確性**: 全件が漏れなく登録され件数が一致すること。
  - **一貫した動作**: 2件(TC-017-01)と500件(B03)で同一ロジックが機能。
- **テストの目的**: スケール時の正当性とバッチ最適化の有効性を確認する。
  - **堅牢性の確認**: 大量データでの安定動作。
- 🟡 信頼性レベル: note.md「バッチ処理の最適化」「1回のトランザクション処理」からの妥当な推測（具体件数500は代表値）

### TC-017-B04: ImportSummary 集計の整合（failure_count == failures.len()）

- **テスト名**: 集計不変条件 failure_count == failures.len()
  - **境界値の意味**: `ImportSummary` の不変条件（`failure_count` が常に `failures` の長さと一致）の境界検証。成功0/失敗0、成功N/失敗0、成功0/失敗M、成功N/失敗M の各組合せ。
  - **境界値での動作保証**: `record_success`/`record_failure` を任意回数呼んでも不変条件が保たれること。
- **入力値**: 成功・失敗を混在させた集計シーケンス（例: 成功3件・失敗2件を記録）。
  - **境界値選択の根拠**: 既存 `models/import.rs` の `record_failure` が `failure_count = failures.len()` を保証する設計（TASK-0030）に Steam インポートも従うことを確認。
  - **実際の使用場面**: 部分成功（TC-017-E02）時のサマリ生成。
- **期待される結果**: `failure_count == failures.len()`、`success_count` は成功記録回数と一致。JSON シリアライズ形状が `{ success_count, failure_count, failures:[{...}] }`。
  - **境界での正確性**: 0件・複数件いずれでもカウントとリスト長が同期。
  - **一貫した動作**: TASK-0030 の `ImportSummary` 既存テスト（`import_summary_record_failure_keeps_failure_count_in_sync`）と同等の保証。
- **テストの目的**: 共通 `ImportSummary` 型の集計不変条件が Steam 文脈でも維持されることを確認する。
  - **堅牢性の確認**: 集計ロジックの一貫性。
- 🔵 信頼性レベル: 既存実装 `backend/mediavault-api/src/models/import.rs` の `record_failure`/既存テストに直接対応

### TC-017-B05: steam_id の数値変換（String→u64）の境界

- **テスト名**: steam_id 文字列の u64 変換成功
  - **境界値の意味**: 17桁の `steam_id`（最大 `76561...` 台、`u64` の範囲内）を `GetOwnedGamesRequest.steam_id: u64` へ変換する際のオーバーフロー境界。17桁の最大値でも `u64`（最大約1.8×10^19、20桁）に収まる。
  - **境界値での動作保証**: 桁数検証を通過した `steam_id` が `parse::<u64>()` で必ず成功すること。
- **入力値**: `"99999999999999999"`（17桁の最大数値文字列）/ `"76561197960265728"`（SteamID64 下限の代表値）
  - **境界値選択の根拠**: 17桁最大値が `u64` 範囲に収まることの確認、および note.md記載のSteamID64下限 `76561197960265728` の妥当性確認。
  - **実際の使用場面**: 大きな SteamID64 を持つアカウント。
- **期待される結果**: `parse::<u64>()` が `Ok` を返し、`GetOwnedGamesRequest` が構築される（変換失敗で500等を出さない）。
  - **境界での正確性**: 17桁全域で `u64` 変換が成功。
  - **一貫した動作**: 形式検証通過 = 数値変換成功、が常に成り立つ。
- **テストの目的**: 形式検証と数値変換の整合（検証通過したものは必ず変換成功）を確認する。
  - **堅牢性の確認**: オーバーフロー・パース失敗による予期せぬ500の防止。
- 🟡 信頼性レベル: note.md「SteamID64範囲」「u64」記載に基づく。17桁最大値がu64範囲内である点は妥当な算術的推測

## 6. 実装時に確定が必要な未確定事項（テスト設計上の論点）

実装（tdd-red/green）で以下の方針を確定する必要がある。テストの期待値はこの確定に合わせて調整する。

1. **重複 steam_appid の集計方針（TC-017-E05）**: 重複を「スキップ＝集計外（success/failureどちらにも数えない）」とするか「更新＝successにカウント」とするか。TASK-0031完了条件は「スキップまたは更新」と両論併記のため、実装で一方を確定する。
2. **name=None エントリの扱い（TC-017-B02）**: フォールバックタイトルで登録（success）するか、必須項目欠如として failures に記録するか。
3. **ImportFailure の識別子フィールド**: 既存 `ImportFailure { row_number: u32, reason: String }` は CSV 行番号前提。Steam インポートでは「行番号」が存在しないため、(a) `row_number` に配列インデックス（0始まり/1始まり）を流用、(b) `row_number` に `appid` を格納、(c) `ImportFailure` を拡張（`identifier` フィールド追加 or enum 化）のいずれかを確定する必要がある。**既存実装は `row_number: u32` のみのため、appid(`u32`)流用が型上は最も低コストだが意味的に紛らわしい点に注意。**
4. **ImportSummary のカウント型**: 既存実装は `success_count: u32`/`failure_count: u32`（要件定義書記載の `usize` ではない）。テスト・実装は既存の `u32` に合わせる。
5. **トランザクション分離単位**: 部分失敗継続（EDGE-002）を満たすため、ゲーム1件ごとに独立トランザクション（`create_item_with_source` を件数分呼ぶ）とするか、バッチ内で個別ロールバックするか。note.mdは「1回のトランザクション処理」を推奨する一方、EDGE-002は「1件失敗でも他継続」を要求するため、両立方針（例: 件数分の独立トランザクション + 失敗のみスキップ）を確定する。
