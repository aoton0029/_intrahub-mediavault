# TASK-0015 テストケース定義: タグ・カテゴリCRUD実装

## 1. 正常系テストケース

### TC-1: タグ作成の正常動作 🔵
- **テスト名**: `create_tag_request_deserializes_valid_name` / `create_tag_inserts_and_returns_tag`
  - **何をテストするか**: `POST /tags`相当の処理が、有効な`name`を受け取りタグを作成できること
  - **期待される動作**: `CreateTagRequest`が`{ "name": "お気に入り" }`を正しくデシリアライズし、リポジトリ層が新規UUIDを付与してタグを作成する
- **入力値**: `{ "name": "お気に入り" }`
  - **入力データの意味**: タスク仕様のテストケース1（TASK-0015.md L59-62）に明記された代表例
- **期待される結果**: 201、`{ success: true, data: { id: <UUID>, name: "お気に入り" } }`
  - **期待結果の理由**: 既存`created_response`パターン（item.rs/items.rs同型）と一致させる
- **テストの目的**: タグ作成APIの基本フローが動作することを確認
  - **確認ポイント**: 返却される`id`がUUID形式であること、`name`が入力と一致すること
- 🔵 信頼性レベル: タスク仕様テストケース1と完全一致

### TC-2: カテゴリ作成の正常動作 🔵
- **テスト名**: `create_category_inserts_and_returns_category`
  - **何をテストするか**: `POST /categories`がタグと同様のパターンでカテゴリを作成できること
  - **期待される動作**: `{ "name": "本棚A" }`を受け取り、201でカテゴリを返す
- **入力値**: `{ "name": "本棚A" }`
  - **入力データの意味**: タスク仕様のテストケース4（TASK-0015.md L74-77）の代表例
- **期待される結果**: 201、`{ success: true, data: { id: <UUID>, name: "本棚A" } }`
  - **期待結果の理由**: タグ作成と対称的な実装のため同一の検証パターンを適用
- **テストの目的**: カテゴリ作成APIがタグ実装と同型であることを確認
  - **確認ポイント**: レスポンス構造がタグと同一であること
- 🔵 信頼性レベル: タスク仕様テストケース4と完全一致

### TC-3: タグのアイテム付与 🟡
- **テスト名**: `attach_tag_to_item_inserts_item_tags_row`
  - **何をテストするか**: `POST /items/:id/tags/:tag_id`が`item_tags`テーブルに複合キーレコードを作成すること
  - **期待される動作**: 既存item, 既存tagの組み合わせでINSERTが成功する
- **入力値**: 既存の`item_id`, `tag_id`（事前にDBへINSERT済みのUUID）
  - **入力データの意味**: タスク仕様テストケース3（TASK-0015.md L69-72）の前提条件
- **期待される結果**: 201（または200、付与成功を示すステータス）。`item_tags`に該当行が存在する
  - **期待結果の理由**: エンドポイント形式自体がAPI仕様未記載のため妥当な推測（🟡）だが、付与成功時のレスポンスはitems系の201パターンを踏襲
- **テストの目的**: 多対多関連の作成処理を確認
  - **確認ポイント**: `item_tags`テーブルへの実際のINSERTが行われること（統合テスト）
- 🟡 信頼性レベル: タスク仕様テストケース3が前提だが、HTTPステータスコードの詳細は推測

### TC-4: タグのアイテム解除 🟡
- **テスト名**: `detach_tag_from_item_deletes_item_tags_row`
  - **何をテストするか**: `DELETE /items/:id/tags/:tag_id`が`item_tags`から複合キーで該当行を削除すること
  - **期待される動作**: TC-3で付与した関連を削除し、204を返す
- **入力値**: TC-3で付与済みの`item_id`, `tag_id`
  - **入力データの意味**: タスク仕様テストケース3「付与→解除」の流れの後半
- **期待される結果**: 204 No Content。`item_tags`から該当行が消える
  - **期待結果の理由**: 既存`delete_item_handler`の204パターンと統一
- **テストの目的**: 多対多関連の削除処理を確認
  - **確認ポイント**: 削除後に`item_tags`へ再度SELECTした際に該当行が存在しないこと
- 🟡 信頼性レベル: タスク仕様テストケース3が前提だが、削除成功時ステータスは既存パターンからの推測

### TC-5: カテゴリのアイテム付与・解除 🟡
- **テスト名**: `attach_and_detach_category_to_item`
  - **何をテストするか**: `POST/DELETE /items/:id/categories/:category_id`がタグと同様に動作すること
  - **期待される動作**: TC-3/TC-4と対称
- **入力値**: 既存`item_id`, `category_id`
- **期待される結果**: 付与時201、解除時204
  - **期待結果の理由**: タグの実装パターンを完全に踏襲
- **テストの目的**: カテゴリの多対多関連処理がタグと同型であることを確認
  - **確認ポイント**: `item_categories`テーブルへの反映
- 🟡 信頼性レベル: タスク仕様の完了条件「item_categoriesへの付与・削除エンドポイントが実装される」（TASK-0015.md L30）からの推測

### TC-6: タグ削除時のカスケード削除確認（統合テスト） 🟡
- **テスト名**: `delete_tag_cascades_item_tags`
  - **何をテストするか**: `DELETE /tags/:id`実行後、関連する`item_tags`レコードがDBのON DELETE CASCADEにより自動削除されること
  - **期待される動作**: タグ削除後、紐付いていた`item_tags`行が存在しなくなる
- **入力値**: タグ作成→アイテム付与→タグ削除、の順で実DBに対して操作
  - **入力データの意味**: タスク仕様の統合テスト要件（TASK-0015.md L81）に明記
- **期待される結果**: タグ削除後、`SELECT * FROM item_tags WHERE tag_id = ?`が0件
  - **期待結果の理由**: DBスキーマのFK制約`ON DELETE CASCADE`が正しく機能することの確認（アプリ側の削除処理は不要であることの裏付け）
- **テストの目的**: カスケード削除がDB制約レベルで機能することを確認
  - **確認ポイント**: アプリケーションコードで`item_tags`を個別削除するロジックを書いていないこと（実装しすぎていないことの確認も兼ねる）
- 🟡 信頼性レベル: タスク仕様に明記された統合テスト要件だが`#[ignore]`実DB前提のため🟡

## 2. 異常系テストケース

### TC-7: タグ名重複でエラー 🟡
- **テスト名**: `create_tag_with_duplicate_name_returns_conflict_error`
  - **エラーケースの概要**: 既存タグと同名の`name`で`POST /tags`を呼んだ場合の挙動
  - **エラー処理の重要性**: DBのUNIQUE制約違反を生のSQLエラーとしてクライアントに返さず、適切なAPIエラーコードに変換する必要がある
- **入力値**: 既に存在するタグ名と同一の`name`（例: 2回目の`{ "name": "お気に入り" }`）
  - **不正な理由**: `tags.name`は`UNIQUE`制約のため、DB側でSQLSTATE `23505`が発生する
  - **実際の発生シナリオ**: 利用者が同じタグ名をうっかり再作成しようとした場合
- **期待される結果**: 409（または422）、エラーコード`DUPLICATE_TAG_NAME`相当
  - **エラーメッセージの内容**: 「タグ名は既に存在します」等、内部SQLエラーを含まない汎用メッセージ
  - **システムの安全性**: `db_error`相当の関数を通す前にユニーク制約違反を個別検出し、内部情報を漏らさない
- **テストの目的**: 一意制約違反の適切なエラーマッピングを確認
  - **品質保証の観点**: DBエラーがそのままクライアントへ漏洩しないことを保証する既存方針（item_repository.rsの`db_error`）の踏襲確認
- 🟡 信頼性レベル: タスク仕様テストケース2（TASK-0015.md L64-67、エラーコード例は「例: 409 DUPLICATE_TAG_NAME」と明記されているため実質🔵に近いが、最終的なステータスコード確定は実装判断のため🟡)

### TC-9: 存在しないタグIDでDELETE時に404 🟡
- **テスト名**: `delete_nonexistent_tag_returns_not_found`
  - **エラーケースの概要**: 存在しないUUIDを指定して`DELETE /tags/:id`を呼んだ場合
  - **エラー処理の重要性**: 削除対象がない場合にクライアントへ明確なエラーを返す必要がある
- **入力値**: DBに存在しないランダムなUUID
  - **不正な理由**: 該当する行がないため、DELETE文の影響行数が0になる
  - **実際の発生シナリオ**: 既に削除済みのタグへの再削除リクエストや、誤ったIDの指定
- **期待される結果**: 404、既存`ItemNotFound`相当またはタグ専用エラーコード
  - **エラーメッセージの内容**: 「指定されたタグが見つかりません」等
  - **システムの安全性**: 影響行数チェック（`rows_affected() == 0`）により判定し、例外的なクラッシュを防ぐ
- **テストの目的**: 存在しないリソースに対する削除操作のエラーハンドリングを確認
  - **品質保証の観点**: 既存`delete_item_handler`の404パターン（影響行数チェック）との一貫性確認
- 🟡 信頼性レベル: タスク仕様に明記なし、既存`DELETE /items/:id`の404パターンからの妥当な推測

### TC-13: 存在しないitem/tagの組み合わせでの付与時エラー 🟡
- **テスト名**: `attach_tag_to_nonexistent_item_returns_not_found`
  - **エラーケースの概要**: 存在しない`item_id`または`tag_id`を指定して付与しようとした場合
  - **エラー処理の重要性**: FK制約違反（SQLSTATE `23503`）が発生するため、適切なエラーへの変換が必要
- **入力値**: 存在しないUUIDを`item_id`または`tag_id`に指定
  - **不正な理由**: `item_tags`のFK制約（items, tagsへの参照）違反
  - **実際の発生シナリオ**: 削除済みのitem/tagへの付与リクエスト
- **期待される結果**: 404、`ITEM_NOT_FOUND`またはタグ専用の404
  - **エラーメッセージの内容**: 「指定されたアイテムまたはタグが見つかりません」
  - **システムの安全性**: FK違反を内部エラーとして露出させず、404として処理する
- **テストの目的**: 多対多関連付与時の参照整合性エラーハンドリングを確認
  - **品質保証の観点**: 事前存在チェック方式かFK違反ハンドリング方式か、実装判断が必要な領域（note.md注意事項参照）
- 🟡 信頼性レベル: タスク仕様に明記なし、DBスキーマのFK制約構造からの妥当な推測

### TC-14: 既に付与済みのタグを再度付与した場合 🟡
- **テスト名**: `attach_already_attached_tag_returns_conflict_or_noop`
  - **エラーケースの概要**: 既に`item_tags`に存在する組み合わせへの再付与
  - **エラー処理の重要性**: 複合PK制約違反（SQLSTATE `23505`）への対応
- **入力値**: TC-3で付与済みの`item_id`, `tag_id`に対して再度POST
  - **不正な理由**: 複合PKの重複
  - **実際の発生シナリオ**: クライアントの二重送信
- **期待される結果**: タスク仕様に「既存の場合はno-opまたは409」と明記（TASK-0015.md L45）。本実装ではエラーとする方針のため409を期待
  - **エラーメッセージの内容**: 「既に付与されています」等
  - **システムの安全性**: 複合PK違反を内部エラーとして露出させない
- **テストの目的**: 重複付与時の挙動が方針通り一貫していることを確認
  - **品質保証の観点**: 仕様上選択の余地がある部分（no-op or 409）について、実装判断を明文化し一貫させる
- 🟡 信頼性レベル: タスク仕様L45に「no-opまたは409」と明記されているが、最終選択は実装判断のため🟡

## 3. 境界値テストケース

### TC-15: タグ名の最大長（100文字）境界 🟡
- **テスト名**: `create_tag_with_max_length_name_succeeds`
  - **境界値の意味**: `tags.name VARCHAR(100)`の上限値
  - **境界値での動作保証**: ちょうど100文字なら成功し、101文字なら失敗することを確認
- **入力値**: 100文字の`name`文字列、および101文字の`name`文字列
  - **境界値選択の根拠**: DBカラム定義`VARCHAR(100)`から導出
  - **実際の使用場面**: 長いタグ名を付けようとするユーザー入力
- **期待される結果**: 100文字は201で成功。101文字はDB側で切り捨てまたはエラー（PostgreSQLの`VARCHAR(100)`は超過時にエラーを返す）→ 422または400相当
  - **境界での正確性**: ちょうど境界での成功/失敗が明確に分かれること
  - **一貫した動作**: アプリ側で事前に文字数チェックを行うか、DB制約に委ねるかは実装判断（タスク仕様に明記なし）
- **テストの目的**: カラム長制約の境界動作を確認
  - **堅牢性の確認**: 極端な長さの入力でもシステムがクラッシュせず適切なエラーを返すこと
- 🟡 信頼性レベル: DBスキーマの`VARCHAR(100)`制約からの推測（タスク仕様にはバリデーション要否の明記なし）

### TC-16: name未指定（フィールド欠落）でのデシリアライズエラー 🔵
- **テスト名**: `create_tag_request_missing_name_field_fails_deserialization`
  - **境界値の意味**: 必須フィールドが存在しない境界ケース
  - **境界値での動作保証**: `name`なしのJSONでは確実にエラーとなることを保証
- **入力値**: `{}`（nameフィールドなし）
  - **境界値選択の根拠**: serdeの必須フィールド欠落時の標準動作
  - **実際の使用場面**: クライアント側の実装ミスによるフィールド欠落
- **期待される結果**: 400、`VALIDATION_ERROR`（既存`deserialize_request`パターンの「リクエストの形式が不正です」メッセージ）
  - **境界での正確性**: serdeの型システムによって構造的に保証される
  - **一貫した動作**: 既存`CreateItemRequest`等の必須フィールド欠落時と同一の挙動
- **テストの目的**: DTOの必須フィールド制約を確認
  - **堅牢性の確認**: 不正なリクエストボディに対して安全にエラーを返すこと
- 🔵 信頼性レベル: 既存`deserialize_request`パターン（item.rs）と完全一致するため高信頼

## 4. 開発言語・フレームワーク

- **プログラミング言語**: Rust（edition 2024）
  - **言語選択の理由**: 既存プロジェクト全体がRust/axumで統一されているため
  - **テストに適した機能**: 型システムによるデシリアライズエラーの構造的検出、`#[cfg(test)]`によるインラインテスト
- **テストフレームワーク**: Rust標準テスト（`#[test]`, `#[tokio::test]`）+ sqlx
  - **フレームワーク選択の理由**: 既存`item_repository.rs`, `items.rs`と同一のテスト基盤を踏襲し、一貫性を保つため
  - **テスト実行環境**: 純粋関数・デシリアライズ系テストは`cargo test`（DB不要）、DB依存の統合テスト（TC-3〜TC-10, TC-13, TC-14）は`#[tokio::test] #[ignore]` + `DATABASE_URL`環境変数 + docker-compose Postgres、`cargo test -- --ignored`で実行
- 🔵 信頼性レベル: 既存プロジェクトのテスト基盤（note.md記載）と完全一致
