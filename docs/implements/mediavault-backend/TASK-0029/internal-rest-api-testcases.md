## 0. テスト戦略・前提

### 0.1 開発言語・フレームワーク 🔵

- **プログラミング言語**: Rust (Edition 2024)
  - **言語選択の理由**: 既存 mediavault-api バックエンドが Rust + Axum で実装済み。本タスクはルーティング・薄いハンドラの追加であり、同一言語・同一スタックでの実装が必須（note.md「1. 技術スタック」）。
  - **テストに適した機能**: `#[tokio::test]` による非同期テスト、`tower::ServiceExt::oneshot` によるルーター単体起動なしのHTTP統合テスト、`assert_eq!` マクロによる明確な検証。
- **テストフレームワーク**: Rust 標準 `#[test]` / `#[tokio::test]` + `tower::ServiceExt`
  - **フレームワーク選択の理由**: 既存テスト（`routes/mod.rs`, `middleware/api_key_auth.rs`, `handlers/items.rs`）がすべて同フレームワークで統一されており、新規外部依存を増やさない方針（note.md「5. テスト関連情報」）。
  - **テスト実行環境**:
    - DB非依存テスト: `cargo test -p mediavault-api`
    - DB必須テスト（`#[ignore]`付き）: Docker Compose の Postgres を起動（`docker compose up -d db`）し、`DATABASE_URL` を設定したうえで `cargo test -p mediavault-api -- --ignored`
- 🔵 信頼性レベル: note.md「5. テスト関連情報」「7. 実装チェックリスト」、既存 `routes/mod.rs` テスト群に直接対応

### 0.2 テスト分類と実行方式（既存方針の継続）🔵

| 区分 | 属性 | 実行コマンド | 用途 |
|---|---|---|---|
| ルーティング/ミドルウェア（DB非依存） | `#[tokio::test]` | `cargo test -p mediavault-api` | 認証ミドルウェア・ルートマウント確認 |
| ルーティング/ハンドラ（DB必須） | `#[tokio::test]` + `#[ignore]` | `cargo test -p mediavault-api -- --ignored` | 実DBを通したCRUD・検索・404確認 |

- 認証ミドルウェアのテストは、`api_key_auth` が `INTERNAL_API_KEY` 環境変数を直接読むため、DB接続を必要としないダミーハンドラ（または `AppState` を伴う `/internal` ルーター）で検証可能。
- 🔵 信頼性レベル: `middleware/api_key_auth.rs` L15-31 の実装（envから読む）、`routes/mod.rs` L172-182 の `test_app_state()` パターンに直接対応

### 0.3 重要な前提・既知の注意点 🔵🟡

- 🔵 **APIキー照合元**: `api_key_auth` ミドルウェアは `std::env::var("INTERNAL_API_KEY")` を照合元とする（`AppState.internal_api_key` ではなく環境変数）。テストでは `unsafe { std::env::set_var("INTERNAL_API_KEY", ...) }` でキーを設定する（既存 `api_key_auth.rs` テストと同方式）。
- 🔵 **Bearer許容**: ヘッダー値は `Bearer <key>` 形式・生キー文字列の両方を許容する（ミドルウェア実装 L22）。
- 🟡 **空キー時は常に401**: `INTERNAL_API_KEY` が未設定（空文字）の場合、どんなヘッダーでも401になる（ミドルウェア L25 の `!expected.is_empty()` 条件）。テスト前に必ずキーをセットする必要がある。
- 🔵 **バージョンプレフィックスなし**: `/internal/items` で直接マウントする。`/api/v1/internal/items` ではないことをルーティングテストで検証する。
- 🔵 **ハンドラ共通化（選択肢A）**: `/internal/*` は既存ハンドラ（`create_item_handler` 等）を共用する方針。したがって入力検証・404判定などのビジネスロジックは既存テストで担保済みであり、本タスクのテストは「`/internal` ルートにマウントされ、APIキー認証が掛かった状態で既存挙動が正しく機能すること」に焦点を当てる。

### TC-018-01: 正しいAPIキーでPOST /internal/items が201を返す（ミドルウェア通過＋ハンドラ実行）🔵

- **テスト名**: 正しいAPIキー付きのPOST /internal/items でアイテムが新規作成され201が返る
  - **何をテストするか**: `/internal` ルーターにAPIキー検証ミドルウェアが適用され、正しいキーを伴うリクエストがミドルウェアを通過し、既存 `create_item_handler` が実行されて作成成功（201）になること。
  - **期待される動作**: ミドルウェア通過 → ハンドラ実行 → items テーブルへINSERT → `201 Created` と作成済みitem（`ApiOk<Item>`）が返る。
- **入力値**:
  - ヘッダー: `Authorization: Bearer {INTERNAL_API_KEY}`（正しいキー）
  - ボディ: 有効な `CreateItemRequest`（例: `{"title":"テスト作品","media_type":"anime", ...必須項目}`）
  - **入力データの意味**: 巡回バッチが外部API取得結果を内部APIへ登録する最小成功ケースを代表する。`media_type` は既存enum有効値を選定。
- **期待される結果**: HTTPステータス `201 Created`、ボディが `{"success":true,"data":{...item}}` 形式。
  - **期待結果の理由**: note.md「2. レスポンス形式（作成時201）」、TASK-0029.md 完了条件「正常なAPIキーを伴うリクエストが対応するハンドラ処理を正しく実行する」、要件定義 4.1「アイテム新規登録」に対応。
- **テストの目的**: APIキー検証ミドルウェアの適用と、既存ハンドラの `/internal` 経由での正常実行を同時に確認する。
  - **確認ポイント**: (1) 401にならない（認証通過）、(2) 201が返る（ハンドラ実行・作成成功）。
- 🔵 信頼性レベル: TASK-0029.md「単体テスト要件 テストケース1（TC-018-01）」、要件定義 4.1 に直接対応

  - **エラーメッセージの内容**: `ApiErrorCode::Unauthorized`（「認証に失敗しました」）。

  - **品質保証の観点**: TC-018-E01 の中核。認証境界の健全性を保証する。
- 🔵 信頼性レベル: TASK-0029.md「テストケース2（TC-018-E01）」、`api_key_auth.rs` L86-98、要件定義 4.2 に直接対応

### TC-018-E01c: 認証ミドルウェアが全 /internal ルートに適用されている（複数ルートで401）🔵

  - **エラーケースの概要**: items 以外のルート（search/groups/episodes/files/PATCH）にも認証が掛かっているかの網羅確認。
  - **エラー処理の重要性**: 一部ルートだけ認証漏れがあると境界が破綻する。`.layer()` 適用が全ルートに効くことを保証する必要がある。
- **入力値**: 認証ヘッダーなしで以下を順に呼ぶ:

  - `PATCH /internal/items/{uuid}`
  - `POST /internal/items/{uuid}/groups`
  - `POST /internal/groups/{uuid}/episodes`
  - `POST /internal/items/{uuid}/files`

- **テストの目的**: ミドルウェアがルーター全体（individualルートではなくルーターlayer）に適用されていることを確認する。

- 🔵 信頼性レベル: 要件定義 3.1・4.2「/internal/* 配下の任意のエンドポイント」、TASK-0029.md 完了条件「全ルートで401」に対応
