### TC-019-01: pdf アップロードでファイル配置・相対パス保存・201（ルーター経由）

- **テスト名**: pdf バイナリアップロードで PDF ディレクトリに配置され 201 で ItemFile が返る
  - **何をテストするか**: `file_type="pdf"` + 有効バイナリの `multipart/form-data` を `POST /items/:id/files/upload` で送ると、PDF 用ベースディレクトリ配下にファイルが書き込まれ、相対パスが `item_files.path` に保存され、`{success:true, data:ItemFile}` が 201 で返ること。
  - **期待される動作**: ファイル書込 → DB INSERT の順で成功し、書込済みファイルと DB レコードが両方存在する。
- **入力値**:
  - パス: 事前に INSERT した実在 item の `:id`
  - multipart: `file=<PDFバイト列>`（filename `example.pdf`）, `file_type="pdf"`, `label="本編PDF"`
  - **入力データの意味**: 完了条件 L24-26 の最頻ユースケース（pdf 配置・相対パス保存）の代表値。
- **期待される結果**:
  - HTTP `201 CREATED`
  - レスポンス body: `success==true`、`data.file_type=="pdf"`、`data.item_id==:id`、`data.path` が PDF ベースディレクトリからの相対パス（絶対パス・`/srv` プレフィックスを含まない）かつ末尾拡張子 `.pdf`、`data.id` が UUID。
  - ファイルシステム: `PDF_STORAGE_PATH` 配下に `data.path` のファイルが実在しサイズ>0。
  - **期待結果の理由**: 完了条件 L24-26・L28（write-then-record 順序保証）、要件定義書 第2章出力仕様（相対パス保存・201固定）。
- **テストの目的**: 正常系のフルパス（multipart 解析→検証→item存在確認→一意名生成→書込→INSERT→201）が一気通貫で成立することの確認。
  - **確認ポイント**: `path` が**相対**であること（絶対パス漏れがないこと）、ファイルとレコードの両方が存在すること。
- **テスト分類**: ハンドラ統合（`#[tokio::test]` + `#[ignore]`、`DATABASE_URL` 必須、一時ストレージ root 使用）

### TC-019-03: 存在しない item_id → ITEM_NOT_FOUND（404）・書込なし

- **テスト名**: 存在しない item_id へのアップロードは 404 を返し、ファイルを書き込まない
  - **エラーケースの概要**: パスの `:id` が `items` テーブルに存在しない UUID。
  - **エラー処理の重要性**: 存在しない item への孤立ファイル生成を防ぐ。仕様上「ファイル書込は行わない」。
- **入力値**: `:id=Uuid::new_v4()`（DB 未登録）、`file=<PDFバイト列>`, `file_type="pdf"`
  - **不正な理由**: FK 先 item が存在しない。
  - **実際の発生シナリオ**: 削除済み item・誤った id 指定。
- **期待される結果**:
  - HTTP `404 NOT_FOUND`、`error.code=="ITEM_NOT_FOUND"`、`success==false`。
  - ファイルシステム: ストレージ root 配下に新規ファイルが**作られていない**（item 存在確認を書込前に実施）。
  - **エラーメッセージの内容**: 「指定されたアイテムが見つかりません」（既存 `create_item_file` メッセージ）。
  - **システムの安全性**: 無駄な I/O が発生せず、孤立ファイルが残らない。
- **テストの目的**: item 存在確認のタイミング（書込前）と 404 マッピングの確認。
  - **品質保証の観点**: 部分失敗（書込のみ成功）状態を作らないこと。
- **テスト分類**: ハンドラ統合（`#[ignore]`、`DATABASE_URL` 必須）。書込未発生はストレージ root のファイル数 0 で検証。
- 🔵 信頼性レベル: `TASK-0027.md` テストケース4（L80-83）・要件定義書 第4章（書込前 item 確認）に対応。既存 `post_item_file_with_nonexistent_item_returns_404` と対称。

### TC-019-E01: ファイルサーバー書込失敗 → FILE_STORAGE_WRITE_FAILED（500）・DBレコード未作成（EDGE-003）

- **テスト名**: 書込失敗時はレコードを作成せず 500 FILE_STORAGE_WRITE_FAILED を返す
  - **エラーケースの概要**: ディスク容量不足・権限エラー等で `tokio::fs` 書込が失敗する状況をフェイク注入で再現。
  - **エラー処理の重要性**: 書込失敗時に DB レコードを作って参照先ファイルが無い不整合（dangling record）を防ぐ。
- **入力値**: 実在 item、`file=<PDFバイト列>`, `file_type="pdf"`。ストレージ書込を**常に失敗**させる（書込不可パス注入、または `FileStorage` trait のフェイク実装で `Err(io::Error)` を返す）。
  - **不正な理由**: 物理ストレージ層の障害。クライアント入力は正当。
  - **実際の発生シナリオ**: バインドマウント未マウント・権限不足・容量超過。
- **期待される結果**:
  - HTTP `500 INTERNAL_SERVER_ERROR`、`error.code=="FILE_STORAGE_WRITE_FAILED"`、`success==false`。
  - DB: `item_files` に該当 item の新規レコードが**作られていない**（COUNT が試行前と同一）。
  - レスポンスメッセージは一般メッセージ（I/O 詳細・パス・権限情報を含まない）。詳細は `tracing::error!` のみ。
  - **エラーメッセージの内容**: 「ファイル書込に失敗しました」等の一般文言（情報漏洩防止）。
  - **システムの安全性**: write-then-record 順序により DB は無変更。
- **テストの目的**: EDGE-003 の書込失敗ロールバック（レコード未作成）と新規エラーコードのマッピング確認。
  - **品質保証の観点**: dangling DB record を絶対に残さないこと。
- **テスト分類**: 書込失敗注入。フェイク注入が可能なら DB なしのサービス／ハンドラ単体でも検証可。DB COUNT 検証部分は `#[ignore]`（`DATABASE_URL` 必須）。
- 🟡 信頼性レベル: `TASK-0027.md` テストケース3（L75-78）・完了条件 L27・`note.md` L69-74。フェイク注入手段は妥当推測。

### TC-019-E02: DB INSERT 失敗時のファイルクリーンアップ（EDGE-003 対称）

- **テスト名**: 書込成功後に DB INSERT が失敗したら書込済みファイルを削除する
  - **エラーケースの概要**: ファイル書込は成功したが、その後の `create_item_file()` が FK 違反・DB 障害等で失敗するケース。
  - **エラー処理の重要性**: ファイルだけ残り DB レコードが無い「孤立ファイル」を防ぐ（ロールバック対称性）。
- **入力値**: 書込は成功させ、`create_item_file()` を失敗させる（例: 統合テストで存在しない item_id を直接サービス層に渡す／DB をフェイクで `Err` 化）。
  - **不正な理由**: DB 側の制約違反・障害。
  - **実際の発生シナリオ**: 書込〜INSERT 間に item が削除された・一時的 DB 障害。
- **期待される結果**:
  - エラーレスポンス（INSERT 失敗内容に応じ `ITEM_NOT_FOUND` 404 もしくは `INTERNAL_ERROR` 500）。
  - ファイルシステム: いったん書き込んだファイルが `tokio::fs::remove_file()` で削除され、ストレージ root に残らない。
  - **システムの安全性**: ファイルと DB の双方とも痕跡を残さない（両方ロールバック）。
- **テストの目的**: 書込成功・DB失敗時のクリーンアップ（部分失敗解消）の確認。
  - **品質保証の観点**: ロールバックの対称性（write失敗→record無し／record失敗→file無し）。
- **テスト分類**: 統合（`#[tokio::test]` + `#[ignore]`、一時ストレージ root）。`TASK-0027.md` 統合テストケース2 に対応。
- 🟡 信頼性レベル: `TASK-0027.md` 統合テストケース2（L92-94）・`note.md` L71-73。挙動の一部は妥当推測。

### TC-019-E03: 不正な file_type → VALIDATION_ERROR（400）・書込なし

- **テスト名**: enum 外の file_type は 400 VALIDATION_ERROR となり書込を行わない
  - **エラーケースの概要**: `file_type` が `pdf`/`image`/`other` 以外（例 `"invalid"`、`photo` 不採用時も含む）。
  - **エラー処理の重要性**: 不正種別での誤配置・誤分岐を防ぐ。
- **入力値**: 実在 item、`file=<バイト列>`, `file_type="invalid"`
  - **不正な理由**: `FileType` enum のデシリアライズ／検証に失敗する値。
  - **実際の発生シナリオ**: クライアント実装ミス・タイポ。
- **期待される結果**: HTTP `400 BAD_REQUEST`、`error.code=="VALIDATION_ERROR"`、ファイル書込なし。
  - **エラーメッセージの内容**: file_type が不正である旨の検証エラー。
  - **システムの安全性**: 検証を書込前に行い、無駄な I/O を発生させない。

### TC-019-E06: ファイル名から親ディレクトリ参照（..）を含む値を弾く／無害化

- **テストの目的**: パストラバーサル防止の確認（完了条件 L29・注意事項 L109）。
  - **品質保証の観点**: クライアント filename を信頼しない設計の固定化。
- **テスト分類**: サービス単体（一時ディレクトリ、書込先 prefix を assert）
- 🟡 信頼性レベル: 要件定義書 第3章セキュリティ（パストラバーサル防止）・第6章。無害化/拒否の選択は実装方針依存。

### TC-019-E07: コンテナ内（アプリホーム）への書込禁止（REQ-402）

## 3. 境界値テストケース（最小値・最大値・null 等）

### TC-019-B01: 空ファイル（0 バイト）アップロードの扱い

- **テスト名**: 0 バイトの file の扱い（許容 or 400）を境界で固定する
  - **境界値の意味**: バイト数の最小境界（0）。空ファイルを許容するか拒否するかは第6章 未確定事項4。
  - **境界値での動作保証**: 0 バイトでも一貫した結果（成功なら配置・レコード、拒否なら 400）を返す。
- **入力値**: 実在 item、`file=<0バイト>`, `file_type="pdf"`
  - **境界値選択の根拠**: 要件定義書 第6章 未確定事項4（空ファイル扱い）。
  - **実際の使用場面**: 中身を持たないファイル・初期化漏れ。
- **期待される結果**:
  - 方針A（拒否）: `400 VALIDATION_ERROR`、書込・レコードなし。
  - 方針B（許容）: `201`、0 バイトファイル配置・レコード作成。
  - いずれの方針でも dangling record／部分失敗が無いこと。
  - **境界での正確性**: 0 バイト特有の書込分岐で例外を起こさない。

### TC-019-B02: ボディサイズ上限境界（上限ちょうど / 上限+1）

- **テスト名**: multipart ボディサイズ上限の内側で 201、上限超過で 413/400
  - **境界値の意味**: `DefaultBodyLimit::max(LIMIT)` の境界。`LIMIT` ちょうど → 受理、`LIMIT+1` → 拒否。
  - **境界値での動作保証**: 上限付近で受理/拒否が一貫すること。
- **入力値**:
  - (a) `LIMIT` バイト相当のファイル → 受理
  - (b) `LIMIT+1` バイト相当のファイル → 拒否
  - **境界値選択の根拠**: 要件定義書 第3章パフォーマンス・第6章3（上限値は実装時決定）、`note.md` L288。
  - **実際の使用場面**: 大容量 PDF アップロード。
- **期待される結果**:
  - (a) `201`（正常配置）。

  - **一貫した動作**: 上限の内側/外側で受理可否が反転すること。
- **テストの目的**: ボディサイズ上限設定の有効性確認。
  - **堅牢性の確認**: 大容量入力でメモリ枯渇・タイムアウトを起こさない。
- **テスト分類**: ハンドラ統合（`#[ignore]`）。`LIMIT` 確定後に実値で実装。サイズが大きい場合は重テスト扱い。
- 🟡 信頼性レベル: `TASK-0027.md` 注意事項 L108・`note.md` L288。上限値・応答コードは実装時決定（妥当推測）。

### TC-019-B03: 拡張子なしファイル名の境界

- **テスト名**: 拡張子のない元ファイル名でも安全に一意名を生成する
  - **境界値の意味**: 拡張子文字列が空（`README`、`scan` 等）という境界。
  - **境界値での動作保証**: 拡張子無しでも UUID 名で一意配置でき、パスに不正成分が入らない。

### TC-019-B04: label 空文字 / 最大長相当の境界

- **テスト名**: label が空文字・長文字列でも 201（許容）
  - **境界値の意味**: 任意フィールド label の境界（空文字、DB カラム長相当の最大長）。
  - **境界値での動作保証**: 空文字を null と区別しつつ受理し、長文字列でも DB 制約内なら成功。

- 🟡 信頼性レベル: `models/item_file.rs`（path のみ検証）からの妥当な推測。
