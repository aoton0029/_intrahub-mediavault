## タスク概要

Phase2〜5で実装された全13画面を対象に、基本的なWCAG 2.1 AA準拠（フォームのラベル付け・キーボード操作・コントラスト比）を確認・修正する（NFR-202）。主要フォーム（手動追加・編集・APIキー登録）の入力フィールドに適切な`<label>`/`aria-label`が付与されているか、Tab/Shift+Tabキーでの操作が全インタラクティブ要素に対して機能するか、shadcn/uiのデフォルトテーマでコントラスト比がAA基準を満たしているかを確認する。加えてモバイル表示（375px〜768px幅想定）でのレイアウト崩れ（カード一覧のオーバーフロー、フォームの操作不能領域、サイドバーナビの表示崩れ等）を確認・修正する。

## 完了条件

- [ ] 全フォーム（`ItemFormPage`手動追加・編集、`SettingsPage`APIキー登録タブ、`SearchAddPage`検索フォーム）の入力フィールドに`<label>`要素またはshadcn/ui `FormLabel`が関連付けられている
- [ ] 全フォームの入力フィールドに、ラベルのみで意図が伝わらない場合は`aria-label`または`aria-describedby`（エラーメッセージ関連付け）が付与されている
- [ ] 主要ナビゲーション（サイドバー、ヘッダー、ページネーション、タブ）の全インタラクティブ要素がTabキーでフォーカス可能であり、フォーカス順序が視覚的順序と一致する
- [ ] モーダル/ダイアログ（削除確認等）使用時、フォーカスがモーダル内にトラップされ、Escキーで閉じられる
- [ ] shadcn/uiテーマのテキスト・背景コントラスト比がWCAG 2.1 AA基準（通常テキスト4.5:1、大テキスト3:1）を満たす（ダークテーマ・ライトテーマ双方）
- [ ] モバイル幅（375px）で全13画面のレイアウトが崩れず、横スクロールが意図しない箇所で発生しない
- [ ] モバイル幅でサイドバーナビが折りたたみ/ハンバーガーメニュー等で適切に表示される
- [ ] 主要フォーム・ナビゲーションコンポーネントの単体テストでアクセシビリティ属性（`aria-label`, `role`, `htmlFor`等）の存在を確認するテストが追加されている

## 実装詳細

### 1. フォームラベル網羅確認・修正 🔵
**信頼性**: 🔵 *NFR-202「フォームのラベル付け」より*

`ItemFormPage.tsx`（手動追加・編集）、`SettingsPage.tsx`（APIキー登録タブ・インポートタブ）、`SearchAddPage.tsx`の各入力フィールドについて、react-hook-form + shadcn/ui `Form`コンポーネント使用箇所では`FormLabel`が`FormControl`と`htmlFor`/`id`で関連付けられているかを確認する。ネイティブ`<input type="file">`等shadcn/ui Formを使わない箇所には明示的な`<label>`または`aria-label`を付与する。

**実装ファイル**: `frontend/src/pages/ItemFormPage.tsx`, `frontend/src/pages/SettingsPage.tsx`, `frontend/src/pages/SearchAddPage.tsx`

### 2. キーボード操作対応 🔵
**信頼性**: 🔵 *NFR-202「キーボード操作」より*

サイドバーナビ（`components/layout/Sidebar.tsx`等）、ページネーション、フィルタUI（`FilterBar`）、カード一覧のカードリンクについて、すべてネイティブの`<a>`/`<button>`要素またはshadcn/ui標準コンポーネント（内部でネイティブ要素を使用）で実装されているかを確認し、`div`+`onClick`のみで実装されている箇所があれば`<button>`または`role="button"`+`tabIndex`+`onKeyDown`（Enter/Space対応）に修正する。モーダル（`Dialog`）はshadcn/ui（Radix UI基盤）の標準フォーカストラップ機能をそのまま利用する。

**実装ファイル**: `frontend/src/components/layout/Sidebar.tsx`, `frontend/src/components/FilterBar.tsx`, 各一覧画面のカードコンポーネント

### 3. コントラスト比確認・調整 🟡
**信頼性**: 🟡 *NFR-202「コントラスト比」から、shadcn/uiデフォルトテーマの確認作業として妥当な推測（具体的な数値検証手法は設計文書未記載）*

shadcn/uiのCSS変数（`--foreground`, `--background`, `--muted-foreground`等、TASK-0002で定義済みのダークテーマトークン）について、ブラウザDevToolsのコントラスト比チェッカーまたは`@adobe/leonardo-contrast-colors`等のツールでAA基準を満たすか確認する。基準を満たさない色（特に`--muted-foreground`系の薄いグレー）があれば、トークン値を調整する。

**実装ファイル**: `frontend/src/index.css`（CSS変数定義箇所）

### 4. レスポンシブレイアウト修正 🟡
**信頼性**: 🟡 *モバイル表示確認・修正の作業内容として一般的なTailwindブレークポイント運用から推測*

Tailwind CSSのブレークポイント（`sm:`/`md:`/`lg:`）を用いて、カード一覧（`grid-cols-1 sm:grid-cols-2 md:grid-cols-3`等）、サイドバー（モバイル時はDrawer/Sheetへの切り替え、shadcn/ui `Sheet`コンポーネント利用）、フォームレイアウト（モバイル時は縦積み）を確認・調整する。

**実装ファイル**: 全`pages/*.tsx`、`frontend/src/components/layout/Sidebar.tsx`

## 単体テスト要件

### テストケース1: 手動追加フォームの入力フィールドにラベルが関連付けられている 🔵
**Given** `ItemFormPage`（手動追加モード）をレンダリングする
**When** タイトル入力フィールドを`getByLabelText`相当のクエリで取得する
**Then** ラベルテキストに対応する入力フィールドが取得できる（`label`の`htmlFor`または`aria-labelledby`が機能している）

### テストケース2: APIキー登録フォームの入力フィールドにラベルが関連付けられている 🔵
**Given** `SettingsPage`のAPIキー登録タブをレンダリングする
**When** 各APIキー入力フィールドを`getByLabelText`で取得する
**Then** 各サービス名（TMDb/IGDB等）に対応する入力フィールドが取得できる

### テストケース3: サイドバーナビの各リンクがTabキーでフォーカス可能 🔵
**Given** `Sidebar`コンポーネントをレンダリングする
**When** 全ナビリンクを`getAllByRole('link')`で取得する
**Then** 各リンクがネイティブ`<a>`要素（または同等のフォーカス可能要素）としてレンダリングされている

### テストケース4: 削除確認モーダルがEscキーで閉じる 🟡
**Given** 削除確認`Dialog`が開いている状態
**When** Escキーを押下する
**Then** モーダルが閉じる 🟡 *shadcn/ui(Radix UI)標準機能の動作確認のため信頼性🟡*

### テストケース5: フィルタUIの各コントロールに適切なaria属性が付与されている 🔵
**Given** `FilterBar`コンポーネントをレンダリングする
**When** media_type/タグ/お気に入り等の各フィルタコントロールを取得する
**Then** 各コントロールに`aria-label`またはラベル関連付けが存在する

### テストケース6: エラーメッセージがフィールドにaria-describedbyで関連付けられている 🟡
**Given** `ItemFormPage`でバリデーションエラーが発生した状態
**When** エラーが表示されたフィールドの属性を確認する
**Then** フィールドの`aria-describedby`がエラーメッセージ要素のidを指している 🟡 *NFR-201/202から妥当な推測、具体実装はshadcn/ui Form標準機能に依存*

## 注意事項

- 本タスクは「基本的な」WCAG 2.1 AA準拠確認（NFR-202の文言通り）であり、専門のアクセシビリティ監査ツール（axe-core等）によるフル自動スキャン・全項目準拠を保証するものではない。重大な欠落（ラベル未設定、キーボード操作不能箇所）の検出・修正を優先する。
- コントラスト比調整でCSS変数（テーマトークン）を変更する場合、TASK-0002で確定したダークテーマの見た目に大きな変更を生じさせないよう、最小限の調整に留める。
- レスポンシブ修正により既存の単体テスト（DOM構造に依存するテスト）が破壊される可能性があるため、修正後は既存テストの再実行・確認を行う。
