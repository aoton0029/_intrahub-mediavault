## 実装詳細
### 1. リクエストDTO定義 🔵
**信頼性**: 🔵 *api-endpoints.md POST /items/import「リクエスト: 検索結果の選択データ + media_type」より*
```rust
#[derive(Debug, Deserialize)]
pub struct ImportItemRequest {
    pub media_type: MediaType,
    pub external_id: String,
    pub title: String,
    pub original_title: Option<String>,
    pub description: Option<String>,
    pub cover_image_url: Option<String>,
    pub release_date: Option<NaiveDate>,
    pub homepage_url: Option<String>,
    pub details: serde_json::Value, // メディア別詳細テーブル用データ
}
```
**実装ファイル**: `backend/mediavault-api/src/models/item_import.rs`

### 2. TASK-0009のitems作成処理の再利用 🔵
**信頼性**: 🔵 *タスク概要「Phase2のitems作成ロジック（TASK-0009）を再利用」より*
TASK-0009で実装された `services::items::create_item(CreateItemInput) -> Result<Item, AppError>`（トランザクション内で`items`+詳細テーブルをINSERTする想定）を、`source`・`external_id`をパラメータとして受け取れるよう拡張する。`POST /items`（`source=manual`, `external_id=None`）と`POST /items/import`（`source=api`, `external_id=Some(...)`）の両方から同一関数を呼び出す構成にする。
**実装ファイル**: `backend/mediavault-api/src/services/items.rs`

### 3. ハンドラ実装 🔵
**信頼性**: 🔵 *architecture.md レイヤードアーキテクチャ方針より*
`handlers::items::import_item` で `ImportItemRequest` を `CreateItemInput { source: ItemSource::Api, external_id: Some(req.external_id), .. }` に変換し、`services::items::create_item` を呼び出す。成功時は`201`で作成済みitemを返す。
**実装ファイル**: `backend/mediavault-api/src/handlers/items.rs`

### 4. external_id必須バリデーション 🔵
**信頼性**: 🔵 *api-endpoints.md「`source=api`, `external_id`必須」、REQ-002より*
`external_id`が空文字列または欠落している場合は`400 VALIDATION_ERROR`を返す。
**実装ファイル**: `backend/mediavault-api/src/handlers/items.rs`

### 5. 重複登録チェック 🟡
**信頼性**: 🟡 *要件定義・受け入れ基準に重複時の挙動の明記がないため妥当な推測（実装判断が必要）*
同一`media_type`+`external_id`の組み合わせが既に`items`テーブルに存在する場合の挙動（エラーを返す／既存レコードを返す／重複作成を許容する）を決定し実装する。本タスクでは安全側として既存レコードがあれば`409 ITEM_ALREADY_IMPORTED`相当のエラーを返す方針を提案するが、要件確定時に見直すこと。
**実装ファイル**: `backend/mediavault-api/src/services/items.rs`, `backend/mediavault-api/src/db/items.rs`

### 6. ルーティング登録 🔵
**信頼性**: 🔵 *api-endpoints.md「### 外部API検索・インポート」節より*
`POST /items/import` を `routes/items.rs` に登録する。
**実装ファイル**: `backend/mediavault-api/src/routes/items.rs`

## 単体テスト要件
### テストケース1: 検索結果からitem作成（TC-002-03） 🔵
**信頼性**: 🔵 *acceptance-criteria.md TC-002-03より*
**Given**: `media_type=anime`、`external_id="12345"`を含む有効なインポートリクエスト
**When**: `POST /items/import` を送信する
**Then**: `201`が返り、`items`テーブルに`source=api, external_id=12345`のレコード、対応する詳細テーブル（anime_details等）にもレコードが作成される

### テストケース2: external_id欠落時に400 🔵
**信頼性**: 🔵 *api-endpoints.md「external_id必須」より*
**Given**: `external_id`を含まないリクエスト
**When**: `POST /items/import` を送信する
**Then**: `400 VALIDATION_ERROR`が返り、`items`テーブルへの書き込みは発生しない

### テストケース3: 重複external_idのインポート 🟡
**信頼性**: 🟡 *要件定義に重複時挙動の明記がないため妥当な推測*
**Given**: 同一`media_type`+`external_id`のitemが既に存在
**When**: 同じデータで`POST /items/import` を再送する
**Then**: 重複作成は行われず、定義された方針（例: `409`エラー）に従ったレスポンスが返る

### テストケース4: TASK-0009ロジックとの一貫性 🟡
**信頼性**: 🟡 *「Phase2の処理を再利用」という指示から導出した検証観点であり、具体的なTC番号はないため妥当な推測*
**Given**: `POST /items`（manual）と`POST /items/import`（api）に同等の詳細データ
**When**: それぞれを呼び出す
**Then**: 両方とも同一のトランザクション処理（詳細テーブル作成含む）を経由し、`source`と`external_id`のみが異なるitemが作成される
