## タスク概要
`POST /items/:id/files` エンドポイントを実装し、ファイルサーバー上に既に存在するファイルのパスを指定して `item_files` レコードを作成する。本タスクではファイル本体の書き込みは行わず、呼び出し元（利用者または監視バッチ等）が指定した既存パスをそのままDBに登録する「パス指定方式」のみを対象とする（バイナリ直接アップロード方式はTASK-0027で実装）。リクエストボディは `path`, `label`, `file_type` を受け取る。

## 依存タスク
- **前提タスク**: [TASK-0008](TASK-0008.md)（itemsモデル）, [TASK-0004](TASK-0004.md)（マイグレーション）
- **後続タスク**: [TASK-0027](TASK-0027.md)（バイナリ直接アップロード）, [TASK-0028](TASK-0028.md)（calibre-link更新）

## 完了条件
- [ ] `POST /items/:id/files` が `path`, `label`, `file_type` を受け取り、`item_files` レコードを作成する
- [ ] `file_type` は `item_files` テーブルのenum制約に従い検証される（不正値は `VALIDATION_ERROR`）
- [ ] 対象の `item_id` が存在しない場合 `ITEM_NOT_FOUND`（404）を返す
- [ ] 成功時、作成された `item_files` レコードを201で返す

- [ ] TC-007-01（既存パス指定でitem_filesレコードが作成される）を満たす

## 実装詳細

### 1. CreateItemFileRequest（パス指定方式）DTO定義 🔵
**信頼性**: 🔵 *api-endpoints.md POST /items/:id/files リクエスト例より*

```json
{ "path": "/srv/files/pdf/example.pdf", "label": "本編PDF", "file_type": "pdf" }
```
`path`（必須, 非空文字列）, `file_type`（必須, item_filesのfile_type enumに準拠）, `label`（optional）を持つDTOを定義する。

**実装ファイル**: `mediavault-api/src/models/item_file.rs`

### 2. ハンドラ実装 🔵
**信頼性**: 🔵 *api-endpoints.md・architecture.mdのレイヤ構成より*

`item_id` の存在確認後、`item_files` テーブルへINSERTする。`calibre_book_id` は本タスクではNULL固定とする（TASK-0028で更新対象）。

**実装ファイル**: `mediavault-api/src/handlers/item_files.rs`, `mediavault-api/src/routes.rs`

### 3. file_type バリデーション 🟡
**信頼性**: 🟡 *database-schema.sqlのenum定義からの妥当な推測（pdf/photo等の想定）*

`file_type` がDB側のenum定義（例: `pdf`, `photo`等）に含まれない場合、`VALIDATION_ERROR`（400）を返す。

**実装ファイル**: `mediavault-api/src/models/item_file.rs`

### 4. リポジトリ層（DBアクセス） 🔵
**信頼性**: 🔵 *database-schema.sqlのitem_filesテーブル定義より*

`sqlx::query!`等を用いて `item_files(item_id, path, label, file_type, calibre_book_id, created_at)` へのINSERTを実装する。

**実装ファイル**: `mediavault-api/src/repositories/item_file_repository.rs`

## 単体テスト要件

### テストケース1: 正常系 - 既存パス指定でレコード作成（TC-007-01） 🔵
**Given** 存在する `item_id` と `{ "path": "/srv/files/pdf/example.pdf", "label": "本編PDF", "file_type": "pdf" }`
**When** `POST /items/:id/files` を実行する
**Then** 201が返り、`item_files` テーブルに指定パスのレコードが作成される

### テストケース2: item_id不存在 🔵
**Given** 存在しない `item_id`
**When** `POST /items/:id/files` を実行する
**Then** `ITEM_NOT_FOUND`（404）が返る

### テストケース3: file_type不正値 🟡
**Given** `file_type="invalid"` を含むリクエスト
**When** `POST /items/:id/files` を実行する
**Then** `VALIDATION_ERROR`（400）が返る

### テストケース4: pathが空文字 🟡
**Given** `path=""` を含むリクエスト
**When** バリデーションを実行する
**Then** `VALIDATION_ERROR`（400）が返る

## 注意事項
- ファイル本体はアプリコンテナ外のファイルサーバーHDDにバインドマウントされる前提（REQ-402）。本エンドポイントはパス文字列のみをDBに保存し、ファイル本体の存在確認・書込は行わない。
- 開発環境ではファイルサーバーのバインドマウントが存在しない場合があるため、本タスクのテストはパス文字列のDB保存検証に限定し、実ファイルI/Oには依存しない。
- `/internal/items/:id/files`（内部API、監視プロセス用）も同様の登録ロジックを共有する想定だが、認証方式が異なるため別タスクで扱う可能性がある（本タスクでは外部公開APIのみを対象とする）。
