## タスク概要
`POST /items/:id/files/upload` エンドポイントを実装し、`multipart/form-data` でバイナリファイルを直接受け取る。`file_type` に応じて `/srv/files/pdf` または `/srv/media/photos` にファイルを書き込み、配置後の相対パスを `item_files.path` に保存する。ファイル本体はアプリコンテナ内に保存してはならず（REQ-402）、バインドマウントされたファイルサーバー上のディレクトリにのみ書き込む。ファイルサーバーへの書込に失敗した場合は `item_files` レコードを作成しない（トランザクション/ロールバック、TC-019-E01、EDGE-003）。

## 依存タスク
- **前提タスク**: [TASK-0026](TASK-0026.md)（パス指定方式の基盤・item_filesモデル/リポジトリ）
- **後続タスク**: [TASK-0028](TASK-0028.md)（calibre-link更新、pdfアップロード後の連携先）

## 完了条件
- [ ] `POST /items/:id/files/upload` が `multipart/form-data`（file, file_type, label）を受け取る
- [ ] `file_type` が `pdf` の場合 `/srv/files/pdf` 配下に、`photo`等の場合 `/srv/media/photos` 配下にファイルを書き込む
- [ ] 書込成功後、配置後の相対パスを `item_files.path` として保存し、201でレコードを返す
- [ ] ファイルサーバーへの書込に失敗した場合、`item_files` レコードを作成せず `FILE_STORAGE_WRITE_FAILED`（500）を返す（TC-019-E01）
- [ ] 書込済みファイルとDBレコード作成の間で不整合が生じないよう、書込成功を確認してからDBへINSERTする順序を保証する
- [ ] ファイル名の重複・パストラバーサル等の不正な入力に対する基本的な安全対策を行う

## 実装詳細

### 1. multipart/form-data 受信処理 🔵
**信頼性**: 🔵 *api-endpoints.md POST /items/:id/files/upload リクエスト仕様より*

Axumの `Multipart` エクストラクタを用いて `file`（バイナリ）, `file_type`, `label` フィールドを受信する。`file_type` の値検証はTASK-0026のバリデーションロジックを再利用する。

**実装ファイル**: `mediavault-api/src/handlers/item_files.rs`

### 2. ファイルサーバーへの書き込み処理 🔵
**信頼性**: 🔵 *REQ-104・dataflow.md 機能5シーケンス図より*

`file_type` に応じて書込先ディレクトリを決定する（`pdf` → `/srv/files/pdf`, それ以外の画像系 → `/srv/media/photos`）。一意なファイル名（例: UUID + 元拡張子）を生成し、`tokio::fs` を用いて非同期に書き込む。書込先ベースディレクトリは環境変数で設定可能とする（開発環境ではローカルディレクトリに切替可能とする）。

**実装ファイル**: `mediavault-api/src/services/file_storage.rs`

### 3. 書込失敗時のロールバック（EDGE-003） 🟡
**信頼性**: 🟡 *EDGE-003・dataflow.md「データ整合性の保証」より*

書込処理が失敗した場合は `item_files` へのINSERTを行わず、エラーレスポンス `FILE_STORAGE_WRITE_FAILED`（500）を返す。書込→DB登録の順で処理し、書込が成功した後にDB登録が失敗した場合は書き込んだファイルを削除するクリーンアップ処理を行う（部分失敗の解消）。

**実装ファイル**: `mediavault-api/src/handlers/item_files.rs`, `mediavault-api/src/services/file_storage.rs`

### 4. 相対パスのDB保存 🟡
**信頼性**: 🟡 *REQ-104（既存パス規約からの妥当な推測）より*

書込先のベースディレクトリ（`/srv/files/pdf` 等）からの相対パスのみを `item_files.path` に保存し、絶対パスのベース部分はアプリ側設定として分離する想定とする。

**実装ファイル**: `mediavault-api/src/services/file_storage.rs`, `mediavault-api/src/repositories/item_file_repository.rs`

## 単体テスト要件

### テストケース1: 正常系 - バイナリアップロードでファイル配置・パス保存（TC-019-01） 🔵
**Given** `file_type="pdf"` と有効なバイナリファイルを含む `multipart/form-data`
**When** `POST /items/:id/files/upload` を実行する
**Then** `/srv/files/pdf` 配下にファイルが配置され、配置後の相対パスが `item_files.path` に保存され、201が返る

### テストケース2: file_typeに応じた配置先の切替 🔵
**Given** `file_type="photo"` を含むリクエスト
**When** `POST /items/:id/files/upload` を実行する
**Then** `/srv/media/photos` 配下にファイルが配置される

### テストケース3: 書込失敗時のロールバック（TC-019-E01, EDGE-003） 🟡
**Given** ファイルサーバーへの書込が失敗する状況（ディスク容量不足・権限エラー等を模したフェイク実装）
**When** `POST /items/:id/files/upload` を実行する
**Then** `item_files` レコードが作成されず、`FILE_STORAGE_WRITE_FAILED`（500）が返る

### テストケース4: item_id不存在 🔵
**Given** 存在しない `item_id`
**When** `POST /items/:id/files/upload` を実行する
**Then** `ITEM_NOT_FOUND`（404）が返る（ファイル書込は行わない）

## 注意事項
- ファイルサーバーパス（`/srv/files/pdf`, `/srv/media/photos`）はコンテナへのバインドマウント前提（REQ-402）。開発環境ではこれらのパスを環境変数で切替可能なローカルディレクトリに置き換えて検証する。
- アプリコンテナ内に一時的にもファイル本体を保持しないよう、ストリーミング書込（メモリ全展開を避ける）を検討する。
- 大容量ファイル（PDF等）のアップロードを想定し、Axumのmultipartボディサイズ上限設定を確認・調整する。
- ファイル名はクライアント指定のファイル名をそのまま使用せず、サーバー側で一意な名前を生成することでパストラバーサルや名前衝突を防止する。
