## タスク概要
巡回バッチ・ファイルサーバー監視プロセスなどの内部プロセスから利用される `/internal/*` ルート群を実装する。APIキー検証ミドルウェア（TASK-0006）を適用したルーターに、Phase2で実装済みのitems/groups/episodesハンドラロジック、Phase4で実装済みのファイル登録ロジックを再利用してマウントする。利用者向けエンドポイント（`/api/v1/*`）とは別のルーターグループとし、認証方式（APIキー1本）のみが異なる構成とする。

## 依存タスク
- **前提タスク**: TASK-0006（APIキー検証ミドルウェア）, TASK-0009〜TASK-0013（items/groups/episodes CRUD）, TASK-0018, TASK-0019（外部API連携）, TASK-0026（ファイル管理）
- **後続タスク**: TASK-0030（ブクログCSVインポート）, TASK-0031（Steamライブラリインポート）

## 完了条件
- [ ] `/internal/*` 配下の全ルートにTASK-0006のAPIキー検証ミドルウェアが適用されている
- [ ] `POST /internal/items` がアイテム新規登録（手動 or 外部API取得結果のインポート相当）を行う
- [ ] `PATCH /internal/items/:id` が既存アイテムのメタデータ部分更新を行う
- [ ] `GET /internal/items/search` がタイトル・media_type・タグ・外部IDなどの条件でアイテムを検索する
- [ ] `POST /internal/items/:id/groups` がグループの登録・更新を行う
- [ ] `POST /internal/groups/:group_id/episodes` がエピソードの登録・更新を行う
- [ ] `POST /internal/items/:id/files` がファイルサーバー上のパスを紐付け登録する
- [ ] APIキー未設定・不一致の場合、全ルートで `401 Unauthorized` を返す（TC-018-E01）
- [ ] 正常なAPIキーを伴うリクエストが対応するハンドラ処理を正しく実行する（TC-018-01）
- [ ] 存在しないitem_id/group_idを指定した場合に `404 Not Found` を返す（TC-018-E02）

## 実装詳細
### 1. 内部APIルーターのマウント構成 🔵
**信頼性**: 🔵 *api-endpoints.md「内部REST API」セクション、architecture.mdのルーター構成より*

`/internal` をプレフィックスとする専用の`Router`を定義し、TASK-0006で実装済みの`api_key_auth`ミドルウェア（`axum::middleware::from_fn_with_state`等）を`.layer()`で適用する。利用者向けルーター（`/api/v1`）とはAxumの`Router::merge`または`nest`で分離し、メインアプリケーションに統合する。内部APIはバージョンプレフィックスを付与しない（api-endpoints.md「APIバージョニング」より）。

**実装ファイル**: `mediavault-api/src/routes/internal.rs`, `mediavault-api/src/main.rs`（またはapp構築モジュール）

### 2. POST /internal/items・PATCH /internal/items/:id 🔵
**信頼性**: 🔵 *api-endpoints.md「POST /internal/items」「PATCH /internal/items/:id」より*

Phase2で実装済みの`create_item`/`update_item`ハンドラ（TASK-0009, TASK-0010相当）のサービス層関数を再利用する。リクエストボディは`CreateItemRequest`/`UpdateItemRequest`（TASK-0008で定義済み）をそのまま利用し、ハンドラ自体は内部API用に薄いラッパーとして実装するか、共通ハンドラを両ルーターから呼び出す形にする。

**実装ファイル**: `mediavault-api/src/handlers/internal_items.rs`

### 3. GET /internal/items/search 🔵
**信頼性**: 🔵 *api-endpoints.md「GET /internal/items/search」説明より*

タイトル（部分一致）・`media_type`・タグ・`external_id`をクエリパラメータとして受け取り、Phase2で実装済みの検索クエリロジック（TASK-0012相当）を再利用して条件検索を行う。クエリパラメータは全てoptionalとし、未指定時は全件（ページネーション付き）を返す。

**実装ファイル**: `mediavault-api/src/handlers/internal_items.rs`

### 4. POST /internal/items/:id/groups・POST /internal/groups/:group_id/episodes 🔵
**信頼性**: 🔵 *api-endpoints.md「グループ/エピソードの登録・更新（巡回バッチからの話数同期用）」より*

Phase2で実装済みのgroups/episodes CRUDロジック（TASK-0011, TASK-0013相当）を再利用する。巡回バッチからの利用を想定し、既存グループ・エピソードが存在する場合は更新、存在しない場合は新規作成するupsert的な振る舞いとする。

**実装ファイル**: `mediavault-api/src/handlers/internal_groups.rs`, `mediavault-api/src/handlers/internal_episodes.rs`

### 5. POST /internal/items/:id/files 🔵
**信頼性**: 🔵 *api-endpoints.md「ファイルサーバー上のパスを紐付け登録（監視プロセスからの新規ファイル検知時に使用）」より*

Phase4で実装済みのファイル登録ロジック（TASK-0026相当）のうち、「既存パス指定方式」（REQ-019）を利用する。バイナリ直接アップロードは利用者向けエンドポイントのみで提供し、内部APIではパス指定方式のみをサポートする。

**実装ファイル**: `mediavault-api/src/handlers/internal_files.rs`

## 単体テスト要件
### テストケース1: APIキー検証ミドルウェアの適用確認（TC-018-01） 🔵
**Given** 正しい`INTERNAL_API_KEY`を`Authorization: Bearer`ヘッダーに設定したリクエスト
**When** `POST /internal/items`を呼び出す
**Then** ミドルウェアを通過し、ハンドラが実行されて`201 Created`相当のレスポンスが返る

### テストケース2: APIキー不一致での401（TC-018-E01） 🔵
**Given** 誤った値または未設定の`Authorization`ヘッダー
**When** `/internal/*`配下の任意のエンドポイントを呼び出す
**Then** `401 Unauthorized`が返り、ハンドラ本体は実行されない

### テストケース3: 存在しないitem_idでの404（TC-018-E02） 🔵
**Given** 正しいAPIキーかつ存在しない`item_id`
**When** `PATCH /internal/items/:id`または`POST /internal/items/:id/groups`を呼び出す
**Then** `404 Not Found`が返る

### テストケース4: 検索クエリパラメータ未指定時の全件取得 🟡
**Given** 正しいAPIキーかつクエリパラメータなし
**When** `GET /internal/items/search`を呼び出す
**Then** ページネーションされた全件一覧が返る
