## 実装詳細

### 1. 擬似 worker ヘルパー 🟡

**信頼性**: 🟡 *テスト構成の設計（要件に明記なし）*

**実装ファイル**: `backend/mediavault-api/tests/extraction_concurrency.rs`（新規）

Python worker を待たずに worker の振る舞いを再現するヘルパーを作る。

```rust
struct FakeWorker {
    id: String,
    lease_token: Option<Uuid>,
    extraction_id: Option<Uuid>,
}

impl FakeWorker {
    async fn claim(&mut self, app: &Router) -> Option<ClaimResponse>;
    async fn heartbeat(&self, app: &Router, progress: (i32, i32)) -> Result<HeartbeatResponse, StatusCode>;
    async fn complete(&self, app: &Router, content: &str) -> Result<(), StatusCode>;
    async fn fail(&self, app: &Router, retryable: bool) -> Result<(), StatusCode>;
    async fn cancelled(&self, app: &Router) -> Result<(), StatusCode>;
}
```

これにより「worker A が claim → 分断 → worker B が再claim → worker A が復帰」といったシナリオを素直に書ける。

### 2. lease 失効の再現 🟡

**信頼性**: 🟡 *テスト手法の選択（要件に明記なし）*

lease 期間を待つとテストが遅くなる。DBの `lease_expires_at` を直接過去へ UPDATE して失効を再現する。

```rust
async fn expire_lease(pool: &PgPool, extraction_id: Uuid) {
    sqlx::query("UPDATE item_file_extractions SET lease_expires_at = CURRENT_TIMESTAMP - interval '1 hour' WHERE id = $1")
        .bind(extraction_id).execute(pool).await.unwrap();
}
```

時間依存のテストを排除でき、安定して速く動く。

### 3. テストの独立性 🟡

**信頼性**: 🟡 *既存テストの慣習からの妥当な推測*

並列テストがDB状態を共有すると干渉する。各テストで item / item_file を新規作成し、他テストのデータを参照しない。

## 統合テスト要件

**テストファイル**: `backend/mediavault-api/tests/extraction_concurrency.rs`（`#[ignore]`）

以下は PRD §8.8 の9項目と1対1で対応する。

### 統合テスト1: 同じ対象への未完了ジョブが冪等化される 🔵

**信頼性**: 🔵 *PRD §8.8-1・REQ-044・TC-001-B01 より*

**テスト内容**: 同一 `item_file_id` へ公開APIから `POST .../extraction` を10並列
**期待結果**: 1件が `201`、9件が `200`。DB上の未完了行は1件

並列数を増やしても収束することを確認する。

### 統合テスト2: 2台のworkerが同じジョブを同時にclaimできない 🔵

**信頼性**: 🔵 *PRD §8.8-2・EDGE-001・TC-020-B01 より*

**テスト内容**: `queued` が1件の状態で、5台の `FakeWorker` が同時に claim
**期待結果**: 1台のみが取得、4台が `data: null`。`SKIP LOCKED` により誰もブロックしない

**テスト内容（発展）**: `queued` が3件の状態で5台が同時に claim
**期待結果**: 3台がそれぞれ別の抽出を取得、2台が `null`。同一抽出の二重払い出しがない

### 統合テスト3: lease切れジョブを安全に再取得できる 🔵

**信頼性**: 🔵 *PRD §8.8-3・REQ-118・NFR-202・TC-020-B02 より*

**テスト内容**:
1. worker A が claim（`attempts=1`）
2. `expire_lease` で失効させる
3. worker B が claim

**期待結果**: worker B が同じ抽出を取得。`attempts=2`、`lease_token` が新しい値、`claimed_by` が worker B

### 統合テスト4: 古いworkerからのcompleteが拒否される 🔵

**信頼性**: 🔵 *PRD §8.8-4・REQ-407・EDGE-002・TC-024-E01・TC-EDGE-008-01 より*

**テスト内容**（[dataflow.md](../design/dataflow.md) フロー5そのもの）:
1. worker A が claim（token X）
2. lease 失効
3. worker B が claim（token Y）
4. worker B が complete → 成功
5. worker A が token X で complete

**期待結果**: ステップ5が `409 INVALID_LEASE_TOKEN`。`item_file_texts` には worker B の結果のみ

heartbeat / fail / cancelled でも旧トークンが拒否されることを併せて確認する。

### 統合テスト5: キャンセル要求がworkerへ伝わり、終端状態へ遷移する 🔵

**信頼性**: 🔵 *PRD §8.8-5・REQ-202・REQ-207・TC-003-02 より*

**テスト内容**:
1. worker が claim → `running`
2. 公開APIから cancel → `cancelling`
3. worker が heartbeat → `cancel_requested: true`
4. worker が cancelled → `cancelled`

**期待結果**: 各段階で期待どおりの状態。`item_file_texts` に行が作られない

**加えて**: ステップ3のあと worker が complete を送った場合に `409` になることを確認する（REQ-204・EDGE-003）。

### 統合テスト6: 抽出結果保存とジョブ成功が不整合にならない 🔵

**信頼性**: 🔵 *PRD §8.8-6・REQ-025・TC-024-01 より*

**テスト内容**: complete を実行し、直後に両テーブルを確認
**期待結果**: `item_file_texts` に行があり、抽出が `succeeded`。片方だけの状態が観測されない

**加えて**: UPSERT を失敗させたときに両方ロールバックされることを確認する。

### 統合テスト7: Item Text APIがチャンクと extraction_version を返す 🔵

**信頼性**: 🔵 *PRD §8.8-7・REQ-005・REQ-006 より*

**テスト内容**: worker 経由（`FakeWorker`）で complete したあと `GET /items/{id}/text`
**期待結果**: `chunk.index` / `total_chunks` / `label` / `extraction_version` が返る

[TASK-0009](TASK-0009.md) では手動 INSERT で検証したが、本テストは**内部API経由で保存されたデータ**で検証する点が異なる。

### 統合テスト8: 未抽出、ファイル不在、複数候補を異なるエラーとして返す 🔵

**信頼性**: 🔵 *PRD §8.8-8・REQ-115・REQ-116・NFR-501 より*

**テスト内容**: 3状況それぞれで `GET /items/{id}/text`
**期待結果**: `422 TEXT_NOT_EXTRACTED` / `404 FILE_NOT_FOUND` / `409 AMBIGUOUS_FILE`

[TASK-0010](TASK-0010.md) と重複するが、PRD 受け入れ条件のチェックリストとして本ファイルにも置く。

### 統合テスト9: 内部APIを無認証で呼び出せない 🔵

**信頼性**: 🔵 *PRD §8.8-9・NFR-101・TC-NFR-101-01 より*

**テスト内容**: claim / heartbeat / complete / fail / cancelled の5本すべてに、認証なし・誤ったキーでリクエスト
**期待結果**: すべて `401 UNAUTHORIZED`

**加えて**: 公開ルーター（`/api/v1/extractions/*`）から到達できないことを確認する（REQ-406）。

### 統合テスト10: heartbeat 途絶からの復旧 🟡

**信頼性**: 🟡 *EDGE-008（要件からの推測）*

**テスト内容**: worker A が claim したまま heartbeat を送らず放置 → lease 失効 → worker B が claim → 完遂
**期待結果**: worker B の結果で `succeeded`。worker A の残骸が残らない

### 統合テスト11: 試行上限到達後の掃除 🟡

**信頼性**: 🟡 *REQ-111・[TASK-0011](TASK-0011.md) §2 の sweeper（実行タイミングは設計で具体化）*

**テスト内容**: `attempts = max_attempts` かつ lease 切れの `running` 行を作り、claim を呼ぶ
**期待結果**: その行が `failed`（`kind: lease_expired`）へ遷移し、`running` のまま残らない

## 注意事項

- **本タスクは Phase 3 の品質ゲート**。ここを通過してから Phase 4（Python worker）へ進む
- **時間待ちでテストしない**。`lease_expires_at` を直接 UPDATE して失効を再現する。`sleep` を使うとテストが遅く不安定になる
- 並列テストは `tokio::join!` / `futures::future::join_all` で実装する。`SKIP LOCKED` の挙動は実DBでしか検証できないため、モックは使わない
- テスト間の干渉を避けるため、各テストで item を新規作成する。共有フィクスチャを使わない
- PRD §8.8 の9項目を**チェックリストとしてテスト名に対応づける**。後から「どの受け入れ条件が未検証か」を追える形にする
- `FakeWorker` は Phase 4 の Python worker が完成しても削除しない。api 単体のリグレッションテストとして残す価値がある
