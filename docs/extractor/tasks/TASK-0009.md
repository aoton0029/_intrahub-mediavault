## タスク概要

抽出済み全文をチャンク単位で返す公開APIを実装する。AIエージェントが作品内容を材料として扱う**唯一の経路**であり、本要件の最終的な価値の出口。

[item-text.md](../../backend/mediavault-api/item-text.md) に既存の完成した設計があり、本タスクはその実装である。設計フェーズでの変更点は `label` の扱いのみ（[architecture.md](../design/architecture.md) D-5）。

## 実装詳細

### 1. ハンドラの実装 🔵

**信頼性**: 🔵 *[item-text.md](../../backend/mediavault-api/item-text.md) §GET /items/{id}/text より*

**実装ファイル**: `backend/mediavault-api/src/handlers/item_text.rs`（新規）

```rust
pub async fn get_item_text_handler(
    State(state): State<AppState>,
    Path(item_id): Path<String>,
    Query(query): Query<ItemTextQuery>,
) -> Result<axum::response::Response, ApiError>
```

処理順序（[dataflow.md](../design/dataflow.md) フロー3）:
1. `item_id` の UUID 検証 → item 存在確認 → `404 ITEM_NOT_FOUND`
2. `parse_item_text_query` で `chunk_index` / `chunk_size` を検証（[TASK-0002](TASK-0002.md) 実装済み）
3. 対象ファイルの決定（`file_id` 指定 or 主ファイル解決）
4. `fetch_chunk` でチャンク取得
5. `chunk_index >= total_chunks` なら `400 VALIDATION_ERROR`
6. `boundaries` から `label` を合成

### 2. 抽出の状態を参照しない 🔵

**信頼性**: 🔵 *REQ-117・[item-text.md](../../backend/mediavault-api/item-text.md) §全文抽出との関係より*

本APIは `item_file_extractions` を**一切 SELECT しない**。判定は `item_file_texts` に行があるかどうかだけ。

| 抽出の状態 | 応答 |
|---|---|
| 未依頼 / `queued` / `running` / `failed` | `422 TEXT_NOT_EXTRACTED`（結果がないため） |
| `succeeded` | `200` |

この単純さが設計の要点。抽出の進捗は `GET .../extraction`（[TASK-0008](TASK-0008.md)）で見る。

### 3. label の合成 🔵

**信頼性**: 🔵 *[architecture.md](../design/architecture.md) D-5・設計ヒアリングQ2より*

[TASK-0002](TASK-0002.md) の `compose_chunk_label` を呼ぶ。

```rust
let chunk_start = validated.chunk_index * validated.chunk_size;
let chunk_end = chunk_start + row.chunk_text.chars().count() as i64;
let boundaries: Vec<TextBoundary> = serde_json::from_value(row.boundaries)?;
let label = compose_chunk_label(&boundaries, chunk_start, chunk_end);
```

`chunk_end` は**実際に取得した文字数**から算出する。末尾チャンクは `chunk_size` 未満になるため（EDGE-104）、`chunk_start + chunk_size` では範囲がずれる。

### 4. AMBIGUOUS_FILE の候補一覧 🔵

**信頼性**: 🔵 *REQ-115・NFR-502・[item-text.md](../../backend/mediavault-api/item-text.md) より*

共通の `ApiErrorBody { code, message }` に `candidates` を追加する必要がある。**本エンドポイントのみの拡張**であり、`ApiError` 型そのものは変更しない。

専用のレスポンス型を用意して直接 `IntoResponse` する方式とする 🟡（`ApiError` の構造を壊さないため）。

```json
{
  "success": false,
  "error": {
    "code": "AMBIGUOUS_FILE",
    "message": "複数のファイルが抽出済みです。file_id を指定してください",
    "candidates": [
      { "file_id": "...", "label": "本編PDF", "file_type": "pdf" }
    ]
  }
}
```

**推測で選んではならない**。候補を返してクライアントに選ばせる。

## 単体テスト要件

`compose_chunk_label` と `parse_item_text_query` は [TASK-0002](TASK-0002.md) でテスト済み。本タスクでは `chunk_end` 算出の単体テストを追加する。

### テストケース1: chunk_end が実文字数から算出される 🔵

**信頼性**: 🔵 *EDGE-104 より*

**Given**: `chunk_index=1`、`chunk_size=4000`、実際に取得した文字数が500
**Then**: `chunk_end = 4000 + 500 = 4500`（`4000 + 4000 = 8000` ではない）

label 合成の範囲がずれないことを保証する。

## AIエージェント向け要件

### 「材料が無い」と「まだ抽出していない」の区別 🔵

**信頼性**: 🔵 *NFR-501・NFR-503・[user-stories.md](../spec/user-stories.md) ストーリー3.4より*

この区別は**必須**。AIエージェントは前者を「別の情報源へ切り替える」、後者を「抽出を依頼すれば解決する」として扱い分ける。

`message` にも区別が現れる文言を入れる。

### 出典参照の安定性 🔵

**信頼性**: 🔵 *REQ-413・REQ-414・[user-stories.md](../spec/user-stories.md) ストーリー3.3より*

`extraction_version` を必ず返す。エージェントは保存済み出典と比較して失効を検知する。

### 候補提示による自己解決 🔵

**信頼性**: 🔵 *NFR-502 より*

`AMBIGUOUS_FILE` では `candidates` を返し、エージェントが `file_id` を指定して再試行できるようにする。エラーで行き止まりにしない。

## 注意事項

- **`item_file_extractions` を SELECT しない**。REQ-117 の要求であり、本APIを抽出の状態から独立させる設計判断
- `chunk_end` は実取得文字数から算出する。末尾チャンクで label がずれる
- `candidates` 付きレスポンスは `ApiError` 型を変更せず、専用型で返す
- 本タスク完了時点で、DBへ手動 INSERT した `item_file_texts` を使ってAPIを検証できる。worker 完成を待つ必要がない
- `total_chunks` が0のとき `chunk_index=0` を `VALIDATION_ERROR` にするかは要検討 🟡。統合テスト11で挙動を固定する
