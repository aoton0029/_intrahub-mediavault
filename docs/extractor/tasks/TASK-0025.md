## タスク概要

`enqueue_job` / `get_job` / `list_jobs` / `cancel_job` の4ツール（設計のみ・未実装）を、抽出系3ツールへ再定義して実装する。

| 旧ツール | 新ツール |
|---|---|
| `enqueue_job` | `request_extraction(item_id, file_id)` |
| `get_job` / `list_jobs` | `get_extraction_status(item_id, file_id)` |
| `cancel_job` | `cancel_extraction(item_id, file_id)` |

**4→3 に減る理由** 🔵: 抽出対象が常に `(item_id, file_id)` で一意に決まるため、ジョブIDを別途扱う必要がなくなり、`get_job` と `list_jobs` の区別が消えた。

本タスク完了により、AIエージェントが抽出を自己完結で依頼・監視・キャンセルできるようになる。

## 実装詳細

### 1. request_extraction 🔵

**信頼性**: 🔵 *REQ-080・[api-endpoints.md](../design/api-endpoints.md) より*

**実装ファイル**: `backend/mediavault-mcp/src/tools/`（既存構成に従う）

`POST /api/v1/items/{id}/files/{file_id}/extraction` を呼ぶ。

**旧設計との最大の違い** 🔵: 旧 `enqueue_job` は `POST /internal/jobs`（内部API）を呼ぶ設計で、mcp が `INTERNAL_API_KEY` を保持する必要があった。新設計では**公開API**を呼ぶため、mcp が内部APIキーを使う場面が**なくなる**。

`201`（新規）と `200`（既存を返却）はどちらも成功として扱い、エージェントには「抽出が受け付けられた」と伝える。冪等性は api 側（部分UNIQUE index）が担保しているため、mcp 側で重複チェックをしない。

### 2. get_extraction_status 🔵

**信頼性**: 🔵 *REQ-081より*

`GET /api/v1/items/{id}/files/{file_id}/extraction` を呼ぶ。

エージェントが判断に使える形へ整形する。

| 状態 | エージェントへの意味 |
|---|---|
| `queued` / `running` | 進行中。待てばよい |
| `succeeded` | 完了。`get_item_text` で読める |
| `failed` + `retryable: true` + `attempts < max` | 自動再試行される。待てばよい |
| `failed`（上限到達 or non-retryable） | 諦める。再依頼しても無駄 |
| `cancelling` / `cancelled` | キャンセル済み |

進捗（`progress_current` / `progress_total`）も返す。

### 3. cancel_extraction 🔵

**信頼性**: 🔵 *REQ-082より*

`POST /api/v1/items/{id}/files/{file_id}/extraction/cancel` を呼ぶ。

`409 EXTRACTION_ALREADY_FINISHED` は「すでに終わっている」として、エラーではなく状態の報告として扱う 🟡。エージェントがキャンセルを試みたときに完了していた、というのは失敗ではない。

### 4. エラー翻訳 🔵

**信頼性**: 🔵 *NFR-503・[dataflow.md](../design/dataflow.md) §AIエージェント視点でのエラー識別より*

| api レスポンス | エージェントへの意味 |
|---|---|
| `404 FILE_NOT_FOUND` | 材料が無い |
| `422 UNSUPPORTED_FILE_TYPE` | この材料は抽出できない。依頼を繰り返さない |
| `404 EXTRACTION_NOT_FOUND` | まだ依頼していない |
| `409 EXTRACTION_ALREADY_FINISHED` | すでに終わっている |
| 到達不能 | `MCP_API_UNREACHABLE`。復旧待ち |

### 5. jobs 系4ツールの不在 🔵

**信頼性**: 🔵 *REQ-090・TC-080-05 より*

`enqueue_job` / `get_job` / `list_jobs` / `cancel_job` は**実装されていない**（設計のみ存在した）。したがって削除するコードはないが、以下を確認する。

- ツール一覧に現れない
- `src/tools/` に該当ファイルがない
- ツール名の文字列が残っていない

### 6. ツール説明文 🔵

**信頼性**: 🔵 *mcp NFR-201・NFR-202より*

3ツールの関係と使い分けを説明文に書く。

- `get_item_text` が `not_extracted` を返したら `request_extraction` を呼ぶ
- 抽出は非同期。`request_extraction` の直後に読めるわけではない
- `get_extraction_status` で `succeeded` を確認してから `get_item_text` を再試行する
- 同じ依頼を繰り返しても二重処理されない（冪等）

## AIエージェント向け要件

### 抽出の自己完結 🔵

**信頼性**: 🔵 *REQ-083・NFR-503・[user-stories.md](../spec/user-stories.md) エピック1・2より*

本タスク完了により、エージェントは以下を人手なしで行える。

1. 材料が未抽出であることを検知する
2. 抽出を依頼する
3. 完了を待つ（進捗が見える）
4. 完了後に読む
5. 失敗したら諦めるか待つかを判断する
6. 長すぎる処理をキャンセルする

### 冪等性の明示 🔵

**信頼性**: 🔵 *REQ-101・mcp PRD §6 原則6「冪等にできる操作は冪等にする」より*

`request_extraction` は再送しても二重処理されない。ツール説明文でこれを明示し、エージェントがタイムアウト時に安心して再送できるようにする。

### 非同期であることの明示 🔵

**信頼性**: 🔵 *PRD §3「長時間処理をジョブとして実行し」より*

`request_extraction` の直後に `get_item_text` を呼んでも読めない。ツール説明文で「抽出は非同期であり、`get_extraction_status` で完了を確認してから読む」ことを明記する。

これを書かないと、エージェントが即座に読もうとして `not_extracted` → `request_extraction` の無限ループに陥りうる。
