## タスク概要

worker からの失敗報告とキャンセル確認を受け取る内部API 2本を実装する。これにより状態遷移図（[dataflow.md](../design/dataflow.md) フロー4）のすべての辺が実装済みになる。

fail の要点は**再試行判定**。「一時的な失敗は再投入し、恒久的な失敗は即終了する」（REQ-110）を `retryable` フラグと `attempts` の組み合わせで表現する。

cancelled の要点は**部分結果を保存しないこと**（REQ-204・REQ-207）。

## 実装詳細

### 1. fail の遷移判定 🟡

**信頼性**: 🟡 *REQ-110 は 🔵 だが、REQ-111・REQ-112 の分岐は PRD §8.5 状態遷移図からの推測*

**実装ファイル**: `backend/mediavault-api/src/repositories/item_extraction_repository.rs`（追加）

| `retryable` | `attempts` vs `max_attempts` | 遷移後 | 根拠 |
|---|---|---|---|
| `false` | — | `failed` | REQ-110（無限再試行しない） |
| `true` | `attempts < max_attempts` | `queued` | REQ-112 |
| `true` | `attempts >= max_attempts` | `failed` | REQ-111 |

```sql
UPDATE item_file_extractions
SET state = CASE
        WHEN $3 = false THEN 'failed'::extraction_state
        WHEN attempts < max_attempts THEN 'queued'::extraction_state
        ELSE 'failed'::extraction_state
    END,
    error = $4,
    lease_token = NULL,
    lease_expires_at = NULL
WHERE id = $1 AND lease_token = $2 AND state IN ('running', 'cancelling')
RETURNING *;
```

**`attempts` を加算しない** 🔵: 加算は claim 時に行っている（[TASK-0011](TASK-0011.md)）。fail で再度加算すると二重計上になる。

**lease をクリアする** 🔵: `queued` へ戻す場合、`chk_item_file_extractions_lease` 制約は `running`/`cancelling` 以外で lease を要求しないため、NULL にしておく。これにより次の claim がクリーンな状態から始まる。

### 2. fail は抽出結果に触れない 🔵

**信頼性**: 🔵 *REQ-206・PRD §8.2「失敗・キャンセル時に既存の成功結果を削除してはならない」・TC-026-04より*

`item_file_texts` への操作を**一切書かない**。これが REQ-206 の実装そのもの。

再抽出が失敗しても `GET /items/{id}/text` は従来の結果を返し続ける。ユーザーは実験的な再抽出を安心して試せる（[user-stories.md](../spec/user-stories.md) ストーリー2.3）。

### 3. 構造化エラーの保存 🔵

**信頼性**: 🔵 *REQ-026・NFR-503より（`kind` の値域は 🟡）*

```json
{ "kind": "ocr_failed", "message": "全ページのOCRに失敗しました", "retryable": false }
```

`error` jsonb へそのまま保存する。`GET .../extraction`（公開API）で読めるようになる。

`kind` の想定値 🟡: `unsupported_format` / `corrupt_file` / `file_not_found` / `size_limit_exceeded` / `ocr_failed` / `api_unreachable` / `lease_expired` / `internal`

**サイズ上限** 🟡: `message` にも上限（`MAX_ERROR_MESSAGE_CHARS`）を設ける（REQ-408）。worker が巨大なスタックトレースを送ってきてもDBを圧迫しない。

### 4. cancelled の実装 🔵

**信頼性**: 🔵 *REQ-027・REQ-202・[api-endpoints.md](../design/api-endpoints.md) §cancelled より*

```sql
UPDATE item_file_extractions
SET state = 'cancelled', lease_token = NULL, lease_expires_at = NULL
WHERE id = $1 AND lease_token = $2 AND state = 'cancelling'
RETURNING *;
```

**`state = 'cancelling'` に限定する** 🔵: worker がキャンセル要求を受けていないのに `cancelled` を送ってくるのは異常。`running` からの直接 `cancelled` は許可しない。

**結果を保存しない** 🔵: cancelled ハンドラは `item_file_texts` に触れない。リクエストボディも `lease_token` のみで、`content` を受け取らない（[interfaces.rs](../design/interfaces.rs) `CancelledRequest`）。部分結果を送る余地を型レベルで断つ。

### 5. ハンドラとルーター 🔵

**信頼性**: 🔵 *[api-endpoints.md](../design/api-endpoints.md) より*

```rust
.route("/internal/extractions/{id}/fail", post(fail_handler))
.route("/internal/extractions/{id}/cancelled", post(cancelled_handler))
```

## 単体テスト要件

### テストケース1: 遷移判定ロジック 🟡

**信頼性**: 🟡 *§1 の判定表（REQ-111・REQ-112 からの推測）*

判定を純粋関数として切り出してテストする。

```rust
fn next_state_on_fail(retryable: bool, attempts: i32, max_attempts: i32) -> ExtractionState
```

| 入力 | 期待 |
|---|---|
| `(false, 0, 3)` | `Failed` |
| `(true, 1, 3)` | `Queued` |
| `(true, 3, 3)` | `Failed` |
| `(true, 2, 3)` | `Queued` |

SQL の CASE 式と同じロジックを Rust 側にも持つことになるが、判定の意図をテストで固定できる価値が重複を上回る 🟡。

### 統合テスト1: 一時的失敗で queued へ戻る 🟡

### 統合テスト2: 上限到達で failed 🟡

**信頼性**: 🟡 *REQ-111・TC-026-02 より*

**Given**: `attempts=3, max_attempts=3`
**When**: fail（`retryable: true`）
**Then**: `state: failed`（終端）

**信頼性**: 🔵 *REQ-110・PRD FR-009・TC-026-03 より*

**Given**: `attempts=0, max_attempts=3`
**When**: fail（`retryable: false`）
**Then**: `state: failed`。`attempts` に関わらず即終了

### 統合テスト4: 既存の成功結果が消えない 🔵

**信頼性**: 🔵 *REQ-206・TC-026-04 より*

**Then**: `item_file_texts` の行はそのまま。`GET /items/{id}/text` が `200` で `pdf-v1` を返す

### 統合テスト5: 再投入後の再claim 🔵

**信頼性**: 🔵 *REQ-112・claim の実装との連携*

**Given**: fail（retryable）で `queued` へ戻った抽出
**When**: claim
**Then**: 再取得され `attempts` が2になる

fail → claim のサイクルが回ることを確認する。

### 統合テスト6: cancelled への遷移 🔵

**信頼性**: 🔵 *REQ-027・REQ-202・PRD §8.8「キャンセル要求がworkerへ伝わり、終端状態へ遷移する」・TC-003-02 より*

**Given**: `cancelling` 状態
**When**: cancelled（有効な lease token）
**Then**: `state: cancelled`（終端）。`item_file_texts` に行が作られない

### 統合テスト7: running からの直接 cancelled を拒否 🟡

**信頼性**: 🟡 *§4 の設計判断（要件に明記なし）*

**Given**: `running`（キャンセル要求なし）
**When**: cancelled
**Then**: `409 INVALID_LEASE_TOKEN`（`state='cancelling'` 条件を満たさない）

### 統合テスト8: 古い lease token の拒否 🔵

**信頼性**: 🔵 *REQ-407・EDGE-002 より*

fail・cancelled の両方で、旧トークンが `409 INVALID_LEASE_TOKEN` になる。

### 統合テスト9: 終端状態への fail / cancelled 🔵

**信頼性**: 🔵 *REQ-203 より*

**Given**: `succeeded` / `failed` / `cancelled`
**Then**: すべて `409`。終端状態が上書きされない

### 統合テスト10: 状態遷移図の全辺を到達 🔵

**信頼性**: 🔵 *[dataflow.md](../design/dataflow.md) フロー4より*

**テスト内容**: 状態遷移図の各辺を1つずつ実行する

| 辺 | 実行方法 |
|---|---|
| `queued → running` | claim |
| `queued → cancelled` | 公開API cancel |
| `running → succeeded` | complete |
| `running → queued` | fail(retryable, 上限未満) |
| `running → failed` | fail(non-retryable) |
| `running → cancelling` | 公開API cancel |
| `cancelling → cancelled` | cancelled |
| `running → running` | heartbeat |
| lease失効 → 再claim | 時間経過後の claim |

**期待結果**: すべての辺が到達可能で、図にない遷移（例: `succeeded → running`）が拒否される

### 統合テスト11: エラーメッセージのサイズ上限 🟡

**信頼性**: 🟡 *REQ-408 からの推測*

**Given**: 上限を超える `message`
**Then**: `422` または切り詰めて保存（実装方針を統合テストで固定する）

## AIエージェント向け要件

### 失敗理由の識別可能性 🔵

**信頼性**: 🔵 *NFR-503・[user-stories.md](../spec/user-stories.md) ストーリー2.1より*

`error.kind` と `error.retryable` により、AIエージェントは以下を判断できる。

| `retryable` | エージェントの解釈 |
|---|---|
| `true` かつ `attempts < max_attempts` | まだ自動再試行される。待てばよい |
| `false` または上限到達 | この材料は使えない。再依頼しても無駄 |

`message` は日本語で、原因が読み取れる文言にする。スタックトレースやファイルパスは含めない（NFR-104）。

## 注意事項

- **fail で `attempts` を加算しない**。加算は claim 時（[TASK-0011](TASK-0011.md)）。二重計上すると上限に早く到達する
- **fail / cancelled が `item_file_texts` に触れない**ことがコード上で明白であること。REQ-206 の実装は「書かないこと」
- `CancelledRequest` は `lease_token` のみを持つ。`content` を受け取れる型にしない（部分結果保存の余地を型で断つ）
- `next_state_on_fail` を Rust と SQL の両方に持つのは重複だが、テスト可能性を優先する。将来 SQL 側を単純化して Rust 側で判定した結果を渡す形へリファクタリングしてもよい
- 統合テスト10（全辺到達）は Phase 3 の総仕上げ。ここが通れば状態遷移の実装が完了する
