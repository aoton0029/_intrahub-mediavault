## 実装詳細

### 1. テスト環境の構成 🟡

**信頼性**: 🟡 *テスト構成の設計（要件に明記なし）*

`docker compose` で db + api + extractor を起動し、ホストから api を叩いて検証する。

```bash
docker compose -f docker-compose.test.yml --env-file .env.test up -d db
docker compose up -d --build mediavault-api mediavault-extractor
```

テストスクリプトは Python（pytest）でも shell でもよい。**worker のログを検証に使う**ため、`docker compose logs` を読める形にする 🟡。

### 2. fixture の準備 🔵

**信頼性**: 🔵 *[tech-stack.md](../tech-stack.md) §テスト構成・[prep.md](../spec/prep.md) §必須より*

**実装ファイル**: `extractor/tests/fixtures/`

| ファイル | 用途 |
|---|---|
| `text_layer.pdf` | テキストレイヤーあり（数ページ） |
| `scanned.pdf` | スキャン画像のみ（数ページ） |
| `mixed.pdf` | 一部ページのみスキャン |
| `japanese.png` | 日本語テキストを含む画像 |
| `corrupt.pdf` | 破損ファイル |
| `fake.pdf` | 中身はPNGだが拡張子が .pdf |

**小さいファイルにする** 🔵（リポジトリサイズを抑えるため）。処理時間計測用の大きなPDFは fixture に含めず、[prep.md](../spec/prep.md) §必須で用意した実データを使う。

### 3. 処理時間の計測 🔵

**信頼性**: 🔵 *NFR-003・TC-NFR-003-01・[prep.md](../spec/prep.md) §推奨より*

CPU実行時のOCR処理時間を計測する。PRD に数値目標がないため、**計測して初期値を決める**のが本タスクの役割。

| 計測項目 | 用途 |
|---|---|
| 1ページあたりのOCR時間（軽量モデル） | `EXTRACTOR_LEASE_SECONDS` の下限 |
| 1ページあたりのOCR時間（通常モデル） | 軽量モデルとの精度・速度比較 |
| 実運用最大クラスのPDFの総処理時間 | `EXTRACTOR_JOB_TIMEOUT_SEC` |

**lease 期間の決め方** 🔵: 「1ページのOCR時間 × 安全係数」を下回ってはならない。処理中に失効すると二重実行になる。heartbeat 間隔は lease 期間の 1/3 〜 1/5 程度が目安 🟡。

計測結果を [prep.md](../spec/prep.md) または本タスクの成果として記録し、暫定値を更新する。

## 統合テスト要件

### 統合テスト1: テキストレイヤーPDFの一巡 🔵

**信頼性**: 🔵 *[user-stories.md](../spec/user-stories.md) ストーリー1.1・3.1より*

**テスト内容**:
1. `POST /items/{id}/files` で `text_layer.pdf` を登録
2. `GET /items/{id}/text` → `422 TEXT_NOT_EXTRACTED`
3. `POST .../extraction` → `201 queued`
4. worker が自動で claim・処理（ポーリング間隔ぶん待つ）
5. `GET .../extraction` → `succeeded`
6. `GET /items/{id}/text` → `200`、本文とチャンク情報

**期待結果**: 本文が読める。`extractor.method == "embedded_text"`、`ocr == null`

### 統合テスト2: スキャンPDFの一巡 🔵

**信頼性**: 🔵 *REQ-106・REQ-107より*

**テスト内容**: `scanned.pdf` で同様
**期待結果**: `method == "ocr"`、`ocr.device == "cpu"`、`ocr.engine == "yomitoku"`、`ocr.model` が非空。日本語テキストが取れる

### 統合テスト3: 混在PDF 🔵

**信頼性**: 🔵 *REQ-105・REQ-106・TC-060-02 より*

**テスト内容**: `mixed.pdf`（10ページ中3ページがスキャン）

**テスト内容**: `japanese.png`
**期待結果**: `method == "ocr"`、テキストが取れる

### 統合テスト5: ページ番号ラベル 🔵

## 計測項目（DIRECT的作業）

### 計測1: CPU OCR の処理時間 🔵

**信頼性**: 🔵 *NFR-003・TC-NFR-003-01 より*

| 対象 | 記録する値 |
|---|---|
| 軽量モデル・1ページ | 秒 |
| 通常モデル・1ページ | 秒 |
| 実データ最大PDF・全体 | 秒 |

**目標値は未定**（PRD に数値目標がない）。計測結果から以下を決める。

- `EXTRACTOR_LEASE_SECONDS`: 1ページ時間 × 安全係数（例: 5倍）
- `EXTRACTOR_HEARTBEAT_INTERVAL_SEC`: lease の 1/3 〜 1/5 🟡
- `EXTRACTOR_JOB_TIMEOUT_SEC`: 最大PDFの処理時間 × 安全係数

### 計測2: 軽量モデルと通常モデルの精度比較 🔵

**信頼性**: 🔵 *PRD FR-011「CPU実行ではyomitokuの軽量モデルを使用し、通常モデルとの差異と精度・速度を実データで評価する」より*

**方法** 🟡: 同一のスキャンPDFを両モデルで処理し、抽出テキストを目視比較する。定量評価（文字誤り率）は原文の正解データが必要なため、MVPでは目視とする。

### 計測3: OCRフォールバック閾値の妥当性 🟡

**信頼性**: 🟡 *[architecture.md](../design/architecture.md) D-7・[prep.md](../spec/prep.md) §確認事項*

**方法**: 実データの各ページで、埋め込みテキストの文字密度を記録する。誤ってOCRされたページ・OCRすべきだったのにされなかったページがないかを確認し、`EXTRACTOR_OCR_FALLBACK_MIN_CHARS_PER_PAGE`（暫定50）を調整する。

## AIエージェント向け要件

### エンドツーエンドでの利用可能性 🔵

**信頼性**: 🔵 *[user-stories.md](../spec/user-stories.md) エピック1・3より*

本タスク完了時点で、AIエージェントは（MCP ツールを除けば）api 直接呼び出しで以下ができる状態になる。

1. 未抽出を検知（`422 TEXT_NOT_EXTRACTED`）
2. 抽出を依頼（`POST .../extraction`）
3. 完了を待つ（`GET .../extraction`）
4. 全文をチャンクで読む（`GET /items/{id}/text`）
5. `label` で出典ページを示す
6. `extraction_version` で出典の失効を検知

MCP ツール化は [TASK-0024](TASK-0024.md)・[TASK-0025](TASK-0025.md) で行う。
