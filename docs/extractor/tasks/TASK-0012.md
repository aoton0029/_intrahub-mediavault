## タスク概要

lease 延長・進捗更新・キャンセル要求の取得を**1リクエストで**行う内部APIを実装する。

3つの機能を1エンドポイントにまとめる理由は、worker の heartbeat スレッドが定期的に1回だけ通信すればよくなるためである。分けると通信回数が3倍になり、キャンセル検知の遅延も生じる。

## 実装詳細

### 1. heartbeat クエリ 🔵

**信頼性**: 🔵 *REQ-023・[api-endpoints.md](../design/api-endpoints.md) §heartbeat より*

**実装ファイル**: `backend/mediavault-api/src/repositories/item_extraction_repository.rs`（追加）

```sql
UPDATE item_file_extractions
SET lease_expires_at = CURRENT_TIMESTAMP + ($3 || ' seconds')::interval,
    progress_current = COALESCE($4, progress_current),
    progress_total   = COALESCE($5, progress_total)
WHERE id = $1
  AND lease_token = $2
  AND state IN ('running', 'cancelling')
RETURNING state, lease_expires_at;
```

**`state IN ('running','cancelling')` が重要** 🔵: `cancelling` を含めないと、キャンセル要求後に heartbeat が失敗し、worker がキャンセルを検知できなくなる。

0行なら lease token 不一致か終端状態 → `409 INVALID_LEASE_TOKEN`。

### 2. 部分更新 🔵

**信頼性**: 🔵 *[interfaces.rs](../design/interfaces.rs) `HeartbeatRequest` の `Option` フィールドより*

`progress_current` / `progress_total` / `lease_seconds` はすべて省略可能。`COALESCE` で「省略時は現在値を維持」とする。

- **lease 延長のみ**: 進捗が変わらない長時間処理（1ページのOCRが数十秒かかる場合）
- **進捗のみ**: 実質的には lease も延長される（`lease_seconds` 省略時は既定値を使う）

### 3. キャンセル要求の返却 🔵

**信頼性**: 🔵 *REQ-202・REQ-207・TC-023-03より*

```json
{ "state": "cancelling", "cancel_requested": true, "lease_expires_at": "..." }
```

`cancel_requested` は `state == Cancelling` のときのみ `true`。worker はこれを検知してページ境界で中断する。

**`state` をそのまま返す理由** 🟡: `cancel_requested` だけでも worker は動けるが、`state` も返すことで worker のログに実際の状態を記録でき、障害調査がしやすくなる（NFR-401）。

### 4. ハンドラとルーター 🔵

**信頼性**: 🔵 *[api-endpoints.md](../design/api-endpoints.md) より*

```rust
// routes/internal.rs
.route("/internal/extractions/{id}/heartbeat", post(heartbeat_handler))
```

### 5. 運用メトリクスへの寄与 🟡

**信頼性**: 🟡 *NFR-402 からの妥当な推測*

`updated_at` がトリガーで自動更新されるため、heartbeat のたびに更新時刻が動く。「最後に heartbeat を受けた時刻」として障害調査に使える。専用カラムは追加しない。

## AIエージェント向け要件

### 進捗の可視性 🔵

**信頼性**: 🔵 *[user-stories.md](../spec/user-stories.md) ストーリー2.1より*

heartbeat で更新された進捗は、AIエージェントが `get_extraction_status` で読む値そのものである。worker が数十ページを処理する間、`progress_current` が動き続けることで「止まっていない」ことが外から分かる。

heartbeat 間隔が長すぎると進捗が飛び飛びになる。`EXTRACTOR_HEARTBEAT_INTERVAL_SEC`（既定30秒 🟡）は lease 期間との兼ね合いで決める（[prep.md](../spec/prep.md) §確認事項）。

## 注意事項

- **`state IN ('running','cancelling')` とする**。`running` のみにすると、キャンセル要求後に heartbeat が失敗して worker がキャンセルを検知できず、`cancelling` のまま lease 失効を待つことになる（統合テスト4で固定）
- lease 期間は worker から渡される。api 側で固定値を持たない設計により、[prep.md](../spec/prep.md) の値確定を後回しにできる
- `COALESCE` による部分更新は、worker 側が「進捗が変わらないときは送らない」最適化をできるようにするため
