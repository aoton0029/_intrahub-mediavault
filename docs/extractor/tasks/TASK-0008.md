## タスク概要

抽出の状態取得とキャンセル要求の公開エンドポイントを実装する。

キャンセルは「即座に終端へ送る」のではなく、`running` の場合は `cancelling` を経由して worker の確認を待つ2段階遷移である点が要点（REQ-202）。この設計により「キャンセル後に成功結果が確定する」事故を防ぐ。

## 実装詳細

### 1. GET ハンドラ 🔵

**信頼性**: 🔵 *REQ-002・[architecture.md](../design/architecture.md) D-2より*

**実装ファイル**: `backend/mediavault-api/src/handlers/item_extractions.rs`（[TASK-0007](TASK-0007.md) で作成したファイルへ追加）

```rust
pub async fn get_extraction_handler(
    State(state): State<AppState>,
    Path((item_id, file_id)): Path<(String, String)>,
) -> Result<ApiOk<ExtractionResponse>, ApiError>
```

履歴を残す設計（D-2）のため、`find_latest_by_file` で `created_at DESC LIMIT 1` を取る。0件なら `404 EXTRACTION_NOT_FOUND`。

ファイルの存在・帰属検証は [TASK-0007](TASK-0007.md) と同じ順序で行う（`FILE_NOT_FOUND` と `EXTRACTION_NOT_FOUND` を区別するため）。共通ヘルパーとして切り出す。

### 2. レスポンスから内部情報を落とす 🔵

**信頼性**: 🔵 *[api-endpoints.md](../design/api-endpoints.md) §GET .../extraction より*

`ExtractionResponse::from(ItemFileExtraction)` により `lease_token` / `lease_expires_at` / `claimed_by` を除く。[TASK-0002](TASK-0002.md) で実装済みの `From` を使うだけだが、テストで固定する。

### 3. 進捗とエラーの表現 🔵

**信頼性**: 🔵 *REQ-002・REQ-301より*

| フィールド | 意味 |
|---|---|
| `progress_current` / `progress_total` | ページ単位。`progress_total` は総数未確定時 `null` |
| `attempts` / `max_attempts` | 試行回数と上限 |
| `error` | 構造化エラー（`kind` / `message` / `retryable`）。成功時は `null` |

`error` の JSON がパース不能でもレスポンス全体を失敗させない（[interfaces.rs](../design/interfaces.rs) の `From` 実装）🟡。観測性のためのフィールドであり必須情報ではないため。

### 4. cancel ハンドラ 🔵

**信頼性**: 🔵 *REQ-003・REQ-201・REQ-202・REQ-205・[api-endpoints.md](../design/api-endpoints.md) §状態別の挙動より*

| 現在の state | 遷移後 | HTTP |
|---|---|---|
| `queued` | `cancelled` | 200 |
| `running` | `cancelling` | 200 |
| `cancelling` | `cancelling`（変化なし） | 200 |
| `succeeded` / `failed` / `cancelled` | 変化なし | **409** |

[TASK-0003](TASK-0003.md) の `request_cancel` を呼び、0行だった場合に最新1件を取得して終端状態であることを確認してから `409 EXTRACTION_ALREADY_FINISHED` を返す。

**`running → cancelling` にする理由** 🔵: worker が処理中のため、即座に `cancelled` にすると worker が後から `complete` を送ってきたときに終端状態が上書きされうる。`cancelling` を経由し、worker の確認（[TASK-0014](TASK-0014.md) の `cancelled` エンドポイント）を待つ。

### 5. ルーター登録 🔵

**信頼性**: 🔵 *既存 `routes/mod.rs` のパターンより*

```rust
.route(
    "/items/{id}/files/{file_id}/extraction",
    post(request_extraction_handler).get(get_extraction_handler),
)
.route(
    "/items/{id}/files/{file_id}/extraction/cancel",
    post(cancel_extraction_handler),
)
```

`/extraction` と `/extraction/cancel` はリテラルパスのため衝突しない。

**信頼性**: 🔵 *REQ-301・TC-002-02 より*

**Given**: 恒久的失敗で終わった抽出
**Then**: `state: "failed"`、`error.kind` / `error.message` / `error.retryable` が含まれる、`attempts` が上限値

### 統合テスト3: 最新1件が返る 🔵

**信頼性**: 🔵 *D-2より*

**Given**: 同一ファイルに `succeeded`（古い）と `running`（新しい）がある
**Then**: `running` が返る

### 統合テスト4: 抽出が未作成 🟡

**信頼性**: 🟡 *TC-002-E01（新規エラーコードの定義からの推測）*

**Given**: 抽出を一度も依頼していないファイル
**Then**: `404 EXTRACTION_NOT_FOUND`

`404 FILE_NOT_FOUND`（ファイル自体がない）と区別されることを確認する。

### 統合テスト5: queued の即時キャンセル 🔵

**信頼性**: 🔵 *REQ-201・TC-003-01 より*

**Given**: `queued` の抽出
**When**: cancel
**Then**: `200`、`state: "cancelled"`（終端）。`lease_token` は NULL のまま

### 統合テスト6: running のキャンセルは cancelling 止まり 🔵

**信頼性**: 🔵 *REQ-202・TC-003-02 より*

**Given**: `running` の抽出
**When**: cancel
**Then**: `200`、`state: "cancelling"`。**`cancelled` にはならない**

worker の確認を待つことをここで固定する。

### 統合テスト7: 二重キャンセルが冪等 🟡

**信頼性**: 🟡 *EDGE-010・TC-003-E03（状態遷移図からの推測）*

**Given**: `cancelling` の抽出
**When**: 再度 cancel
**Then**: `200`、`state: "cancelling"`。エラーにしない

### 統合テスト8: 終端状態への cancel 🟡

**信頼性**: 🟡 *REQ-205・TC-003-E01（既存 `JOB_ALREADY_FINISHED` からの移植）*

**Given**: `succeeded` の抽出
**Then**: `409 EXTRACTION_ALREADY_FINISHED`

`failed` / `cancelled` でも同様。

### 統合テスト9: 終端状態が上書きされない 🔵

**信頼性**: 🔵 *REQ-203 より*

**Given**: `cancelled` の抽出
**When**: cancel を複数回
**Then**: 常に `409`。state は `cancelled` のまま変化しない

## AIエージェント向け要件

### ポーリングでの利用 🔵

**信頼性**: 🔵 *[user-stories.md](../spec/user-stories.md) ストーリー2.1より*

AIエージェントは `get_extraction_status` から完了を待つか諦めるかを判断する。そのために以下が読み取れる必要がある。

- **まだ進む見込みがあるか**: `state` が `queued` / `running` かどうか
- **どれくらい進んだか**: `progress_current` / `progress_total`
- **失敗したか、再試行の余地があるか**: `state: failed` と `attempts` / `max_attempts` の関係

`progress_total` が `null` の期間（worker がファイルを開く前）があることを、レスポンス例とドキュメントで明示する。

## 注意事項

- **`running → cancelled` に直接遷移させない**。worker の確認を待つ2段階が REQ-202 の要求であり、これを守らないと [TASK-0013](TASK-0013.md) の complete 拒否ロジックが機能しない
- `FILE_NOT_FOUND` と `EXTRACTION_NOT_FOUND` の区別を守る。前者は「ファイルがない」、後者は「ファイルはあるが抽出を依頼していない」
- ファイル存在・帰属の検証は [TASK-0007](TASK-0007.md) と共通のため、ヘルパー関数へ切り出して重複を避ける
- 本タスク完了時点で公開API 3本が揃うが、worker がいないため `queued` のまま滞留する。これは正常な状態（NFR-201: 分離）
