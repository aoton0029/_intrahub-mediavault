## タスク概要

`item_files.path` から worker 向けの `FileRef { root, relative_path }` を解決するサービスを実装する。

`path` は登録経路によって意味が異なる（リンク=絶対パス / アップロード=`STORAGE_ROOT` からの相対パス。[item-files.md](../../backend/mediavault-api/item-files.md) §2つの登録経路）。この差を api 側で吸収し、worker のマウントパスに依存しない形式へ正規化する。

あわせて「実体が存在し読み取り可能か」の検証（REQ-004）とファイルサイズ取得（REQ-022）を行う。

## 実装詳細

### 1. path の2経路判定 🔵

**信頼性**: 🔵 *[item-files.md](../../backend/mediavault-api/item-files.md) §2つの登録経路より*

**実装ファイル**: `backend/mediavault-api/src/services/file_ref.rs`

| 経路 | `item_files.path` | 実体の場所 | `FileRef.root` |
|---|---|---|---|
| リンク | 絶対パス（`/srv/anime/...`） | 実データ領域 | `library` |
| アップロード | 相対パス（`{item_id}/{uuid}.pdf`） | `STORAGE_ROOT` + `STORAGE_SUBDIR_FILES` | `storage` |

判定は `Path::new(path).is_absolute()` で行う。

```rust
pub struct ResolvedFile {
    pub file_ref: FileRef,
    pub absolute_path: PathBuf,  // api 側での存在確認に使う。worker へは返さない
    pub size_bytes: i64,
}

pub fn resolve(path: &str, config: &FileRefConfig) -> Result<ResolvedFile, ApiError>
```

### 2. root からの相対パス算出 🔵

**信頼性**: 🔵 *[architecture.md](../design/architecture.md) D-3より*

`FileRef.relative_path` は**許可ルートからの相対**でなければならない。

- **storage 経路**: `item_files.path` がそのまま `STORAGE_SUBDIR_FILES` 配下の相対パス。ただし worker 側の `EXTRACTOR_STORAGE_ROOT` は `STORAGE_ROOT` に対応するため、`{STORAGE_SUBDIR_FILES}/{path}` を `relative_path` とする
- **library 経路**: 絶対パスから library ルートを除いた相対部分を取る

**設計上の前提** 🟡: library ルートは api 側の設定（環境変数）で与える。worker の `EXTRACTOR_LIBRARY_ROOT` と対応させる必要がある。api 側の環境変数名は実装時に決める（`LIBRARY_ROOT` を想定）。

### 3. 旧レイアウトへのフォールバック 🟡

**信頼性**: 🟡 *[item-files.md](../../backend/mediavault-api/item-files.md) §旧レイアウトから妥当な推測*

アップロード領域には旧レイアウト（`STORAGE_ROOT` 直下の file_type 別サブディレクトリ、`path` は `{uuid}.{ext}`）で保存されたファイルが残っている可能性がある。既存 `services/file_storage.rs` の `resolve_legacy_base_dir` が DELETE 時のフォールバックに使われている。

同じフォールバックを本サービスでも行う。現行レイアウトに実体がなければ旧レイアウトを探す。

**注意**: [prep.md](../spec/prep.md) §必須「`item_files.path` の実データ分布の確認」でフォールバックが実際に必要かを事前に確認する。不要と判明したら実装を省く。

### 4. パス安全性の検証 🔵

**信頼性**: 🔵 *REQ-402・[architecture.md](../design/architecture.md) §セキュリティより*

api 側でも `..` を含むパスを拒否する。worker 側でも検証するが（[TASK-0018](TASK-0018.md)）、api が不正な `relative_path` を返さないことを保証する。

```rust
if candidate.is_absolute() || candidate.components().any(|c| c == Component::ParentDir) {
    return Err(ApiError::new(ApiErrorCode::ValidationError, "不正なパスです"));
}
```

### 5. 存在確認とサイズ取得 🔵

**信頼性**: 🔵 *REQ-004・REQ-022・PRD §8.3「読み取り可能性を検証してからジョブを作成する」より*

`std::fs::metadata` で存在・ファイルであること・サイズを確認する。存在しなければ `UNPROCESSABLE_ENTITY`（EDGE-004）。

**同期I/O について** 🟡: `std::fs::metadata` は Axum の async ハンドラ内でブロッキングする。メタデータ取得は極めて短時間のため実害は小さいが、厳密には `tokio::fs::metadata` を使うのが望ましい。既存 `file_storage.rs` の実装方式に合わせる。

## 注意事項

- **既存 `services/file_storage.rs` と役割を分ける**。`file_storage` はアップロードの保存・削除を担う。本サービスは「読み取り用の参照解決」であり、書き込みは行わない。共通化できるヘルパー（`resolve_legacy_base_dir` 等）は再利用する
- api 側の library ルート設定は新規の環境変数が必要になる。[prep.md](../spec/prep.md) §必須「共有ボリュームの read-only マウント構成の確定」で「実データ領域が複数マウントに分かれているか」を確認してから実装する。複数に分かれる場合、`FileRefRoot` を2値から拡張する設計変更が必要になりうる
- worker へ返すのは `FileRef` のみ。`absolute_path` は api 内部の検証にのみ使い、レスポンスへ含めない
