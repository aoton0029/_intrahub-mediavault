## タスク概要

抽出リクエストの公開エンドポイントを実装する。本要件の入口となるAPI。

**処理順序が仕様の一部**である点が本タスクの要点。検証を行う順序によって、同じ入力に対して返るエラーコードが変わる（`404 FILE_NOT_FOUND` か `422 UNSUPPORTED_FILE_TYPE` か）。[api-endpoints.md](../design/api-endpoints.md) が定めた5段階の順序を守る。

## 実装詳細

### 1. ハンドラの実装 🔵

**信頼性**: 🔵 *[api-endpoints.md](../design/api-endpoints.md) §処理順序より*

**実装ファイル**: `backend/mediavault-api/src/handlers/item_extractions.rs`（新規）

既存 `handlers/item_files.rs` と同じ構造で書く。

```rust
pub async fn request_extraction_handler(
    State(state): State<AppState>,
    Path((item_id, file_id)): Path<(String, String)>,
) -> Result<axum::response::Response, ApiError> {
    // 1. UUID形式検証 → 400 VALIDATION_ERROR
    // 2. item_files を id + item_id で取得 → 0件なら 404 FILE_NOT_FOUND
    // 3. file_type が pdf / image か → 422 UNSUPPORTED_FILE_TYPE
    // 4. FileRef 解決＋実体確認 → 不可なら 422 UNPROCESSABLE_ENTITY
    // 5. create_extraction → Created なら 201、Existing なら 200
}
```

**リクエストボディはない**。抽出対象は `file_id` から一意に決まる（REQ-402: ホストパスを受け取らない）。

### 2. 検証順序 🔵

**信頼性**: 🔵 *[api-endpoints.md](../design/api-endpoints.md) §処理順序・[dataflow.md](../design/dataflow.md) フロー1より*

| 順 | 検証 | 失敗時 |
|---|---|---|
| 1 | UUID形式 | `400 VALIDATION_ERROR` |
| 2 | `id = file_id AND item_id = {id}` で取得 | `404 FILE_NOT_FOUND` |
| 3 | `is_extractable(file_type)` | `422 UNSUPPORTED_FILE_TYPE` |
| 4 | `file_ref::resolve` で実体確認 | `422 UNPROCESSABLE_ENTITY` |
| 5 | `create_extraction` | — |

**ステップ2で `item_id` も条件に含める**のが重要。`file_id` だけで引くと、他Itemのファイルに対して抽出を作れてしまう（TC-001-E02）。

`ITEM_NOT_FOUND` と `FILE_NOT_FOUND` の使い分け 🟡: item が存在しない場合に `404 ITEM_NOT_FOUND` を返すか `404 FILE_NOT_FOUND` を返すかは設計で明示していない。既存 `item_files.rs` のパターンに合わせ、item 存在確認を先に行って `ITEM_NOT_FOUND` を返す方式とする。

### 3. ステータスコードの出し分け 🔵

**信頼性**: 🔵 *既存 `src/handlers/item_files.rs:46` のパターンより*

`ApiOk<T>` の `IntoResponse` は常に `200` を返すため、`201` は明示する。

```rust
match outcome {
    CreateOutcome::Created(row) => Ok(
        (StatusCode::CREATED, Json(ApiOk::new(ExtractionResponse::from(row))))
            .into_response()
    ),
    CreateOutcome::Existing(row) => Ok(
        ApiOk::new(ExtractionResponse::from(row)).into_response()
    ),
}
```

### 4. ルーター登録 🔵

**信頼性**: 🔵 *既存 `src/routes/mod.rs:77` のパターンより*

**実装ファイル**: `backend/mediavault-api/src/routes/mod.rs`

```rust
.route(
    "/items/{id}/files/{file_id}/extraction",
    post(request_extraction_handler),
)
```

既存の `/items/{id}/files/{file_id}/calibre-link` と同じ階層のため、パス衝突は起きない。

### 5. 自動キューを行わないことの確認 🔵

**信頼性**: 🔵 *REQ-401・ヒアリングQ6（要件定義フェーズ）より*

`POST /items/{id}/files` と `POST /items/{id}/files/upload` に抽出キューを**追加しない**。既存ハンドラを変更しないことがこの要件の実装そのものだが、テストで明示的に確認する（TC-401-01 / TC-401-02）。

「実装しないこと」を要件として持つため、テストがないと将来誰かが良かれと思って追加してしまう。

**Then**: `404 FILE_NOT_FOUND`

### 統合テスト6: 他Itemに属するファイル 🔵

**信頼性**: 🔵 *REQ-004・TC-001-E02 より*

**Given**: `file_id` は存在するが `item_id` が別のItem
**Then**: `404 FILE_NOT_FOUND`

**セキュリティ上重要**。Item をまたいだ操作を許さない。

### 統合テスト7: 非対応形式 🟡

**信頼性**: 🟡 *REQ-410・TC-001-E03（PRD §4.2 からの推測）*

**Given**: `file_type: video` のファイル
**Then**: `422 UNSUPPORTED_FILE_TYPE`。抽出行は作られない

`audio` / `archive` / `other` でも同様。

### 統合テスト8: 実体が存在しない 🔵

**信頼性**: 🔵 *REQ-004・EDGE-004・TC-001-E04 より*

**Given**: DBには登録があるがボリューム上に実体がない
**Then**: `422`。抽出行は作られない（作ってから worker が失敗するのではなく、事前に弾く）

### 統合テスト9: 並列リクエストの収束 🔵

**信頼性**: 🔵 *REQ-044・TC-001-B01 より*

**When**: 同一 `file_id` へ `POST` を2並列
**Then**: 片方 `201`、片方 `200`。DB上の未完了行は1件

**本タスクで最も重要なテスト**。部分UNIQUE index による冪等化が並列でも壊れないことを実証する。

### 統合テスト10: ファイル登録が抽出をキューしない 🔵

**信頼性**: 🔵 *REQ-401・TC-401-01 / TC-401-02 より*

**When**: `POST /items/{id}/files`（PDF）と `POST /items/{id}/files/upload`（PDF）
**Then**: `item_file_extractions` に行が作られない

## AIエージェント向け要件

### エラーの識別可能性 🔵

**信頼性**: 🔵 *NFR-503・[dataflow.md](../design/dataflow.md) §AIエージェント視点でのエラー識別より*

AIエージェントが次の行動を決められるよう、エラーを明確に分ける。

| 応答 | エージェントの解釈 |
|---|---|
| `404 FILE_NOT_FOUND` | 材料が無い。別の情報源へ |
| `422 UNSUPPORTED_FILE_TYPE` | この材料は使えない。依頼を繰り返さない |
| `422 UNPROCESSABLE_ENTITY` | 一時的な問題かもしれない。時間をおいて再試行 |

`message` は日本語で、原因が読み取れる文言にする。DB内部情報やファイルパスは含めない（NFR-104）。

## 注意事項

- **検証順序を守る**。順序が変わるとエラーコードが変わり、受け入れ基準を満たさなくなる
- ステップ4（実体確認）は同期I/Oを含む。[TASK-0005](TASK-0005.md) の実装方針に従う
- `201` は明示的に構築する。`ApiOk` を返すだけでは `200` になる
- REQ-401（自動キューしない）は「何も実装しない」ことが実装。テストで固定する
- 公開APIは認証なし（単一ユーザー・セルフホスト）。抽出リクエストにも認証を追加しない
