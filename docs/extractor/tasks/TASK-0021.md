## タスク概要

3つの小さなモジュールをまとめて実装する。いずれも純粋関数が中心で、テストが書きやすくカバレッジを高くできる。

- **image.py**: 画像ファイルのOCR（PDFより単純。1ページ扱い）
- **normalize.py**: 文字コード・改行・空白・制御文字の正規化（FR-005）
- **boundaries.py**: ページ・章境界の構築ヘルパー（FR-006）

正規化の要点は「**やりすぎないこと**」。原文の意味を変える校正やLLMによる書き換えを行ってはならない（REQ-064）。

## 実装詳細

### 1. 画像抽出器 🔵

**信頼性**: 🔵 *REQ-107・PRD FR-004「画像ファイルはOCR対象とする」より*

**実装ファイル**: `extractor/src/mediavault_extractor/extractors/image.py`

PDFより単純。1ファイル = 1ページとして扱う。

```python
class ImageExtractor:
    def extract(self, path, ocr, progress) -> ExtractionOutcome:
        if progress.is_cancelled():
            raise CancelledError()
        image = Image.open(path)
        text = normalize(ocr.ocr(image).text)
        progress.report(1, 1)
        return ExtractionOutcome(
            content=text,
            boundaries=(TextBoundary(0, len(text), "p.1"),),
            extraction_version="image-v1",
            extractor=ExtractorMetadata(
                method=ExtractionMethod.OCR, embedded_text_pages=0, ocr_pages=1,
                ocr=OcrMetadata(ocr.engine_name, ocr.device, ocr.model_id),
            ),
        )
```

**`label` を `"p.1"` とするか** 🟡: 単一画像に「ページ」の概念があるかは微妙。`"p.1"` にしておけばPDFと同じ扱いになり、`compose_chunk_label`（[TASK-0002](TASK-0002.md)）が一貫して動く。境界なし（`boundaries=()`）にして `label: null` を返す選択肢もある。**`"p.1"` を採る**。

**Pillow で開けない画像** 🔵: `PermanentError(CORRUPT_FILE)`。

### 2. 正規化 🔵

**信頼性**: 🔵 *REQ-063・PRD FR-005・[tech-stack.md](../tech-stack.md) §正規化より*

**実装ファイル**: `extractor/src/mediavault_extractor/normalize.py`

標準ライブラリ `unicodedata`（NFKC）＋ 自前の改行・空白・制御文字処理。**決定的な変換のみ**に限る。

| 処理 | 内容 | 根拠 |
|---|---|---|
| 文字コード | NFKC 正規化（全角英数 → 半角、互換文字の統一） | REQ-063 |
| 改行 | `\r\n` / `\r` → `\n` に統一 | REQ-063 |
| 連続空白 | 3行以上の空行を2行へ、行内の連続スペースを1つへ 🟡 | REQ-063 |
| 制御文字 | `\t` `\n` 以外の C0/C1 制御文字を除去 | REQ-063 |

**行わないこと** 🔵（REQ-064）:
- 誤字脱字の修正
- 表記ゆれの統一（「サーバ」→「サーバー」等）
- LLMによる書き換え・要約
- 改行位置の再構成（OCRが分断した文の再結合）

最後の項目は判断が分かれる。OCRは行末で不自然に改行することがあり、再結合したくなる。しかし**どこが本来の改行かを機械的に判定できない**ため、原文の改行を保持する。

**正規化の強度について** 🟡: 「連続空白の圧縮」がどこまで許されるかは PRD に明記がない。空白の削減は意味を変えないと判断して実施するが、行内の1つのスペースは保持する。

### 3. 正規化の冪等性 🔵

**信頼性**: 🔵 *NFR-601「同一ファイル＋同一 extraction_version から同等の本文が再生成できる」より*

`normalize(normalize(x)) == normalize(x)` が成り立つこと。NFKC は冪等であり、他の処理も冪等になるよう実装する。

冪等でないと、正規化を通す回数によって結果が変わり、`extraction_version` の意味が壊れる。

### 4. 境界構築ヘルパー 🔵

**信頼性**: 🔵 *REQ-068・[architecture.md](../design/architecture.md) D-5より*

**実装ファイル**: `extractor/src/mediavault_extractor/boundaries.py`

ページごとのテキストから連続した境界列を作る。

```python
def build_boundaries(segments: Sequence[tuple[str, str]]) -> tuple[tuple[TextBoundary, ...], str]:
    """(正規化済みテキスト, ラベル) の列から boundaries と連結本文を作る。

    Returns: (boundaries, content)
    """
    boundaries: list[TextBoundary] = []
    parts: list[str] = []
    cursor = 0
    for text, label in segments:
        boundaries.append(TextBoundary(cursor, cursor + len(text), label))
        parts.append(text)
        cursor += len(text)
    return tuple(boundaries), "".join(parts)
```

**境界と本文を同時に返す設計** 🔵: 別々に作ると位置がずれる余地が生まれる。1つの関数で両方を作ることで、`boundaries[-1].end == len(content)` が構造的に保証される。

これにより [TASK-0013](TASK-0013.md) の api 側検証（EDGE-107）を必ず通過する。

### 5. EPUB 拡張への備え 🔵

**信頼性**: 🔵 *REQ-304・PRD FR-006・[tech-stack.md](../tech-stack.md)「境界データ構造は EPUB を後から足せる形で設計する」より*

`TextBoundary.label` は自由文字列のため、`"第3章"` を表現できる。`build_boundaries` は `(text, label)` のタプル列を受け取るだけで、ページか章かを知らない。

EPUB 対応時は章ごとのテキストを渡すだけで済み、`boundaries.py` の変更は不要。

**注意** 🟡: `compose_chunk_label`（[TASK-0002](TASK-0002.md)）の範囲表記は `"p.1-3"` のように数値部を取る。`"第1章-第3章"` のような非数値ラベルではラベル全体を使う実装になっている（[TASK-0002](TASK-0002.md) テストケース4）。EPUB 導入時に表示を見直す余地がある。
