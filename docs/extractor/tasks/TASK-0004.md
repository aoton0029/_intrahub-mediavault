## タスク概要

`item_file_texts` に対するDB操作を実装する。中心は「全文をアプリメモリへ載せずにチャンクを切り出す」クエリ（REQ-008・NFR-001）と、「主ファイルの解決」（REQ-115）である。

`content` は最大500万文字になりうるため、`SELECT *` で行全体を取る実装をしてはならない。この制約が本タスクの設計を規定する。

## 実装詳細

### 1. チャンク切り出し 🔵

**信頼性**: 🔵 *REQ-008・NFR-001・[item-text.md](../../backend/mediavault-api/item-text.md) §実装上の注意より*

**実装ファイル**: `backend/mediavault-api/src/repositories/item_file_text_repository.rs`

本タスクで最も重要な実装。**`content` 全体を Rust 側へ持ってこない。**

```rust
pub struct ChunkRow {
    pub extraction_version: String,
    pub extracted_at: NaiveDateTime,
    pub boundaries: JsonValue,
    pub total_chunks: i64,
    pub chunk_text: String,
}

// SELECT
//     t.extraction_version,
//     t.extracted_at,
//     t.boundaries,
//     CEIL(CHAR_LENGTH(t.content)::numeric / $2)::bigint AS total_chunks,
//     SUBSTRING(t.content FROM ($1 * $2 + 1) FOR $2) AS chunk_text
// FROM item_file_texts t
// WHERE t.item_file_id = $3
```

**2つの落とし穴**:
1. `CHAR_LENGTH`（文字数）を使う。`OCTET_LENGTH`（バイト長）では日本語で `total_chunks` がずれる（EDGE-103）
2. `SUBSTRING ... FROM` は**1起点**。`chunk_index` は0起点のため `$1 * $2 + 1` とする

`boundaries` はページ数ぶんの小さな jsonb なので、行ごと取得して構わない。

### 2. 抽出結果の UPSERT 🔵

**信頼性**: 🔵 *REQ-103・[database-schema.sql](../design/database-schema.sql) §complete より*

```sql
INSERT INTO item_file_texts
    (item_file_id, content, boundaries, extraction_version, extractor, extracted_at)
VALUES ($1, $2, $3, $4, $5, $6)
ON CONFLICT (item_file_id) DO UPDATE SET
    content = EXCLUDED.content,
    boundaries = EXCLUDED.boundaries,
    extraction_version = EXCLUDED.extraction_version,
    extractor = EXCLUDED.extractor,
    extracted_at = EXCLUDED.extracted_at
```

再抽出時に行を置き換え、行数は常に1件に保つ。この関数は [TASK-0013](TASK-0013.md)（complete）でトランザクション内から呼ぶため、**`&mut PgConnection` を受け取る形**にしておく（`&PgPool` だと同一トランザクションに参加できない）。

### 3. 主ファイルの解決 🔵

**信頼性**: 🔵 *REQ-115・REQ-116・[item-text.md](../../backend/mediavault-api/item-text.md) §主ファイルの解決より*

```rust
pub enum PrimaryFileResolution {
    Single(Uuid),                              // 1件 → 採用
    NoFiles,                                   // ファイル自体がない → 404 FILE_NOT_FOUND
    NoneExtracted,                             // ファイルはあるが未抽出 → 422 TEXT_NOT_EXTRACTED
    Ambiguous(Vec<AmbiguousFileCandidate>),    // 2件以上 → 409 AMBIGUOUS_FILE
}
```

**推測で選んではならない**（REQ-115）。抽出済み候補が2件以上のときは候補一覧を返し、クライアントに選ばせる。

`NoFiles` と `NoneExtracted` の区別のため、`item_files` の件数と `item_file_texts` を結合した件数の両方を見る必要がある。

```sql
-- 抽出済み候補
SELECT f.id, f.label, f.file_type
FROM item_files f
INNER JOIN item_file_texts t ON t.item_file_id = f.id
WHERE f.item_id = $1
ORDER BY f.created_at;

-- ファイル自体の有無
SELECT COUNT(*) FROM item_files WHERE item_id = $1;
```

### 4. 抽出結果の存在確認 🔵

**信頼性**: 🔵 *REQ-116・REQ-117より*

`file_id` を明示された場合に使う。**`item_file_extractions` は参照しない**（REQ-117）。抽出が `running` でも `failed` でも、結果がなければ `TEXT_NOT_EXTRACTED`。

## 統合テスト要件

**テストファイル**: `backend/mediavault-api/src/repositories/item_file_text_repository.rs` の `#[cfg(test)] mod tests`（すべて `#[ignore]`）

### 統合テスト1: 先頭チャンクの取得 🔵

**信頼性**: 🔵 *[acceptance-criteria.md](../spec/acceptance-criteria.md) TC-005-01 より*

**Given**: `content` が48000文字
**When**: `chunk_index=0, chunk_size=4000`
**Then**: `total_chunks=12`、先頭4000文字

### 統合テスト2: 日本語で境界がずれない 🔵

**信頼性**: 🔵 *EDGE-103・TC-005-B04 より*

**Given**: 日本語8000文字（UTF-8で約24000バイト）
**When**: `chunk_size=4000`
**Then**: `total_chunks=2`（バイト長基準なら6になってしまう）

**最重要テスト**。`CHAR_LENGTH` と `OCTET_LENGTH` の取り違えをここで検出する。

### 統合テスト3: 末尾チャンク 🔵

**信頼性**: 🔵 *EDGE-104・TC-005-B05 より*

**Given**: `content` が4500文字
**When**: `chunk_index=1, chunk_size=4000`
**Then**: 500文字が返る

### 統合テスト4: 空の抽出結果 🟡

**信頼性**: 🟡 *EDGE-105・TC-005-B06（要件からの妥当な推測）*

**Given**: `content` が空文字列（抽出は成功したがテキストが取れなかった）
**Then**: `total_chunks=0`。行は存在するため「未抽出」とは区別される

### 統合テスト5: UPSERT による置き換え 🔵

**信頼性**: 🔵 *REQ-103・TC-024-03 より*

**Given**: `extraction_version="pdf-v1"` の行がある
**When**: `extraction_version="pdf-v2"` で `upsert_text`
**Then**: 行は1件のまま、内容が置き換わる

### 統合テスト6: 主ファイル解決 — 4パターン 🔵

**信頼性**: 🔵 *REQ-115・TC-005-06 / E02 / E03 より*

| 前提 | 期待 |
|---|---|
| 抽出済み1件 | `Single` |
| ファイル0件 | `NoFiles` |
| ファイル2件・抽出済み0件 | `NoneExtracted` |
| 抽出済み2件 | `Ambiguous`（候補2件、`label` と `file_type` 付き） |

### 統合テスト7: 巨大 content でメモリが増えない 🔵

**信頼性**: 🔵 *NFR-001・TC-NFR-001-01 より*

**テスト内容**: 500万文字の `content` に対し `chunk_size=4000` で取得
**期待結果**: 取得した `chunk_text` が4000文字。処理時間が本文長に比例して増大しない

厳密なメモリ測定は難しいため、「`SELECT *` を使っていないこと」をコードレビューで担保し、テストでは応答が返ることと文字数のみ確認する 🟡。

## 注意事項

- **`SELECT *` を書かない**。`content` が500万文字ある行を丸ごと取る実装になり NFR-001 に反する
- `upsert_text` は `&mut PgConnection`（または `&mut Transaction`）を受け取る。[TASK-0013](TASK-0013.md) で同一トランザクション内から呼ぶため
- `CHAR_LENGTH` vs `OCTET_LENGTH` の取り違えは日本語テストでしか検出できない。統合テスト2を必ず書く
- `SUBSTRING FROM` の1起点オフセットに注意。オフバイワンは境界テストで検出する
- 主ファイル解決で `AMBIGUOUS_FILE` を返す際、候補一覧の構築には既存 `FileType` を使う
