### 3. エラーコード網羅の確認 🔵

**信頼性**: 🔵 *[api-endpoints.md](../design/api-endpoints.md) §追加・削除するエラーコードより*

[TASK-0002](TASK-0002.md) で追加した6件が、実際に返されるパスを持つことを確認する。

| コード | 到達させるテスト |
|---|---|
| `EXTRACTION_NOT_FOUND` | 抽出未依頼のファイルへ `GET .../extraction` |
| `EXTRACTION_ALREADY_FINISHED` | `succeeded` へ cancel |
| `UNSUPPORTED_FILE_TYPE` | `video` ファイルへ抽出リクエスト |
| `TEXT_NOT_EXTRACTED` | 未抽出ファイルへ `GET /items/{id}/text` |
| `AMBIGUOUS_FILE` | 抽出済み2件で `file_id` 省略 |
| `INVALID_LEASE_TOKEN` | **Phase 3 で到達**（本タスクでは未到達を許容） |

`INVALID_LEASE_TOKEN` は内部APIでのみ返るため、本タスクでは「定義済みだが未到達」となる。[TASK-0015](TASK-0015.md) でカバーする。

## 統合テスト要件

### 統合テスト1: 抽出依頼 → 状態確認 → 全文取得の一巡 🔵

**信頼性**: 🔵 *[user-stories.md](../spec/user-stories.md) ストーリー1.1・2.1・3.1より*

**テスト内容**:
1. `GET /items/{id}/text` → `422 TEXT_NOT_EXTRACTED`
2. `POST .../extraction` → `201`、`queued`
3. `GET .../extraction` → `200`、`queued`
4. （worker を模して DB へ直接 `item_file_texts` を INSERT し、抽出を `succeeded` へ UPDATE）
5. `GET .../extraction` → `200`、`succeeded`
6. `GET /items/{id}/text` → `200`、本文とチャンク情報

**期待結果**: 各段階で期待どおりの応答。Phase 3 完成前でも、DBを直接操作すれば公開APIの一巡を検証できる。

### 統合テスト2: 冪等リクエストのシナリオ 🔵

**信頼性**: 🔵 *REQ-101・TC-001-02 より*

**テスト内容**: 同じ `POST` を3回連続で送る
**期待結果**: 1回目 `201`、2〜3回目 `200`。すべて同じ `id`。DB上の行は1件

### 統合テスト3: キャンセルシナリオ 🔵

**信頼性**: 🔵 *REQ-201・REQ-202・[user-stories.md](../spec/user-stories.md) ストーリー2.2より*

**テスト内容**:
1. `POST .../extraction` → `queued`
2. `POST .../extraction/cancel` → `cancelled`
3. `POST .../extraction/cancel` → `409 EXTRACTION_ALREADY_FINISHED`
4. `POST .../extraction` → `201`（終端後なので新規作成）

### 統合テスト4: 既存結果が消えないシナリオ 🔵

**信頼性**: 🔵 *REQ-206・[user-stories.md](../spec/user-stories.md) ストーリー2.3より*

**テスト内容**:
1. 抽出済み（`extraction_version: "pdf-v1"`）の状態を作る
2. 再抽出をリクエスト → `201`
3. キャンセル → `cancelled`
4. `GET /items/{id}/text` → **`200`、`pdf-v1` のまま**

キャンセル・失敗が既存結果を壊さないことを確認する。

### 統合テスト5: 複数ファイルの曖昧性シナリオ 🔵

**信頼性**: 🔵 *REQ-115・[user-stories.md](../spec/user-stories.md) ストーリー3.5より*

**テスト内容**:
1. 1つのItemに本編PDFと付録PDFを登録し、両方を抽出済みにする
2. `GET /items/{id}/text`（`file_id` 省略）→ `409 AMBIGUOUS_FILE`、候補2件
3. `candidates[0].file_id` を指定して再試行 → `200`

エラーが行き止まりにならず、自己解決できることを検証する。

### 統合テスト6: エラーコード網羅 🔵

**信頼性**: 🔵 *§3 の表より*

**テスト内容**: 5件のエラーコードそれぞれへ到達するリクエストを送る
**期待結果**: コード文字列とHTTPステータスが [api-endpoints.md](../design/api-endpoints.md) の表と一致する

### 統合テスト7: 自動キューが起きない 🔵

**テスト内容**: `POST /items/{id}/files` と `/upload` を実行し、`item_file_extractions` の件数を確認

## AIエージェント向け要件

### エラー分類の一貫性 🔵

**信頼性**: 🔵 *NFR-503・[dataflow.md](../design/dataflow.md) §AIエージェント視点でのエラー識別より*

Phase 2 完了時点で、AIエージェントが区別すべき5つの状況すべてに異なるコードが割り当てられていることを確認する。

| 状況 | コード | エージェントの行動 |
|---|---|---|
| 材料が無い | `FILE_NOT_FOUND` | 別の情報源へ |
| まだ抽出していない | `TEXT_NOT_EXTRACTED` | 抽出を依頼 |
| この材料は使えない | `UNSUPPORTED_FILE_TYPE` | 依頼を繰り返さない |
| 対象が絞れない | `AMBIGUOUS_FILE` | 候補から選んで再試行 |
| 抽出を依頼していない | `EXTRACTION_NOT_FOUND` | 抽出を依頼 |

## 注意事項

- **本タスクは Phase 2 の品質ゲート**。ここを通過してから Phase 3（worker 内部API）へ進む
- worker がまだ存在しないため、`succeeded` 状態はDBへの直接 UPDATE で作る。これは正当な検証手段であり、Phase 3 完成後に worker 経由のテスト（[TASK-0015](TASK-0015.md)）へ置き換わるわけではなく、両方を残す
- テストは並列実行されるとDB状態が干渉しうる。item を毎回新規作成し、テスト間でデータを共有しない
- `INVALID_LEASE_TOKEN` は本タスクでは未到達。「定義済みだが呼ばれない」状態を許容し、[TASK-0015](TASK-0015.md) でカバーすることを明記しておく
