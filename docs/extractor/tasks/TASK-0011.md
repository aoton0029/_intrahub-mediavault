## タスク概要

worker が実行可能な抽出を1件だけ排他的に取得する内部APIを実装する。Phase 3 の起点であり、以降の heartbeat / complete / fail はすべて claim が発行した `lease_token` に依存する。

`FOR UPDATE SKIP LOCKED` による排他制御と、lease 失効による自動復旧（NFR-202）の2つを1つのクエリで実現する点が要点。

## 実装詳細

### 1. claim クエリ 🔵

**信頼性**: 🔵 *[database-schema.sql](../design/database-schema.sql) §claim・EDGE-001・REQ-118より*

**実装ファイル**: `backend/mediavault-api/src/repositories/item_extraction_repository.rs`（追加）

```sql
WITH claimable AS (
    SELECT id FROM item_file_extractions
    WHERE (state = 'queued'
           OR (state IN ('running','cancelling') AND lease_expires_at < CURRENT_TIMESTAMP))
      AND attempts < max_attempts
    ORDER BY created_at
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE item_file_extractions e
SET state = 'running',
    attempts = e.attempts + 1,
    claimed_by = $1,
    lease_token = gen_random_uuid(),
    lease_expires_at = CURRENT_TIMESTAMP + ($2 || ' seconds')::interval
FROM claimable c
WHERE e.id = c.id
RETURNING e.*;
```

**3つの設計判断**:

1. **`SKIP LOCKED`**: 2台の worker が同時に呼んでもブロックせず、別々の行を取る（EDGE-001）。`FOR UPDATE` だけでは片方が待たされる
2. **lease 切れの `running` / `cancelling` も対象**: worker 異常終了からの復旧を claim が兼ねる（REQ-118・NFR-202）。専用の復旧処理を持たない
3. **`attempts < max_attempts`**: 上限到達行を claim 対象から外す。`chk_item_file_extractions_attempts` 制約により、上限を超える UPDATE は失敗するため必須

### 2. 試行上限に達した lease 切れ行の掃除 🟡

**信頼性**: 🟡 *REQ-111・[database-schema.sql](../design/database-schema.sql) §sweeper（実行タイミングは設計で未確定）*

上限到達行は claim 対象外のため、放置すると `running` のまま残る。sweeper で `failed` へ落とす。

```sql
UPDATE item_file_extractions
SET state = 'failed', lease_token = NULL, lease_expires_at = NULL,
    error = jsonb_build_object(
        'kind', 'lease_expired',
        'message', 'workerが応答しないまま試行上限に達しました',
        'retryable', false
    )
WHERE state IN ('running','cancelling')
  AND lease_expires_at < CURRENT_TIMESTAMP
  AND attempts >= max_attempts;
```

**実行タイミング** 🟡: claim ハンドラの冒頭で毎回実行する方式を採る。専用のバックグラウンドタスクを持たずに済み、claim が呼ばれる頻度（ポーリング間隔ごと）で十分な頻度になる。UPDATE 対象がない場合のコストは index により小さい。

### 3. FileRef の解決 🔵

**信頼性**: 🔵 *REQ-022・[architecture.md](../design/architecture.md) D-3より*

claim した抽出の `item_file_id` から `item_files` を引き、[TASK-0005](TASK-0005.md) の `file_ref::resolve` で `FileRef` を組み立てる。

```json
{
  "extraction_id": "...", "item_file_id": "...", "item_id": "...",
  "file_type": "pdf", "size_bytes": 12345678, "attempts": 1,
  "lease_token": "...", "lease_expires_at": "2026-08-14T09:35:00",
  "file_ref": { "root": "storage", "relative_path": "files/{item_id}/{uuid}.pdf" }
}
```

**解決に失敗した場合** 🟡: 実体が消えている等で `file_ref::resolve` が失敗したら、その抽出を即 `failed`（`kind: file_not_found`, `retryable: false`）にして、**次の候補を claim する**。worker へエラーを返すのではなく、api 側で処理する。worker は「取得なし」または次の抽出を受け取る。

### 4. 取得なしの表現 🟡

**信頼性**: 🟡 *[api-endpoints.md](../design/api-endpoints.md) §claim（`204` ではなく `data: null` とする判断）*

```json
{ "success": true, "data": null }
```

`ApiOk<Option<ClaimResponse>>` を返す。worker 側のデシリアライズ経路を1本にできる。

## 注意事項

- **`SKIP LOCKED` を省かない**。`FOR UPDATE` だけでは並列 claim がブロックし、worker のスループットが落ちる
- **`attempts < max_attempts` を WHERE に含める**。含めないと CHECK 制約違反でクエリが失敗する
- lease 期間の既定値は暫定（[prep.md](../spec/prep.md) §確認事項）。worker からの `lease_seconds` を受け取る設計にしておき、値の確定を後回しにできるようにする
- 並列テストは実DBでないと意味がない。モックでは `SKIP LOCKED` の挙動を再現できない
- sweeper を claim 内で実行する方式のため、claim のレイテンシがわずかに増える。単一ユーザー規模では問題にならない
