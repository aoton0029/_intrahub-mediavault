## タスク概要

OCRエンジンの差し替え境界（`OcrEngine` Protocol）と、その MVP 実装である yomitoku ラッパーを実装する。

要点は2つ。**yomitoku 固有型を境界の外へ出さないこと**（REQ-069）と、**`cuda` 指定時にGPUが使えなければ claim 前に起動失敗すること**（REQ-113・REQ-412）。

後者は「暗黙のCPUフォールバックに依存しない」（REQ-412）という要求から来る。yomitoku が黙ってCPUで動くと、GPUで処理したつもりの結果が実はCPUだったという状況になり、`extractor` メタデータが嘘になる。

## 実装詳細

### 1. OcrEngine Protocol 🔵

**信頼性**: 🔵 *REQ-069・[interfaces.py](../design/interfaces.py)・[tech-stack.md](../tech-stack.md) §OCR より*

**実装ファイル**: `extractor/src/mediavault_extractor/ocr/base.py`

```python
@dataclass(frozen=True, slots=True)
class OcrResult:
    text: str
    confidence: float | None

class OcrEngine(Protocol):
    @property
    def engine_name(self) -> str: ...
    @property
    def model_id(self) -> str: ...
    @property
    def device(self) -> OcrDeviceReport: ...
    def ocr(self, image: Image) -> OcrResult: ...
```

**入力は `PIL.Image`、出力は `OcrResult` に固定する** 🔵。yomitoku の内部型（推論結果オブジェクト等）をこの境界の外へ漏らさない。

[tech-stack.md](../tech-stack.md) §OCR が言及する「OCRエンジンをmockした単体テスト」は、**この Protocol の存在そのものと等価**である（同文書内の NFR-006 は tech-stack.md 独自の採番であり、[requirements.md](../spec/requirements.md) の NFR 番号とは別体系）。本要件では REQ-069 が対応する。

### 2. yomitoku ラッパー 🔵

**信頼性**: 🔵 *PRD §12・[tech-stack.md](../tech-stack.md) §OCR より*

**実装ファイル**: `extractor/src/mediavault_extractor/ocr/yomitoku.py`

```python
class YomitokuOcrEngine:
    def __init__(self, device: OcrDeviceSetting) -> None:
        _verify_device_available(device)   # 起動時検証（REQ-113）
        self._device = device
        self._analyzer = ...  # yomitoku の初期化

    @property
    def device(self) -> OcrDeviceReport:
        return (OcrDeviceReport.GPU if self._device is OcrDeviceSetting.CUDA
                else OcrDeviceReport.CPU)
```

**モデルの選択** 🔵 *PRD FR-011より*: CPU実行では yomitoku の**軽量モデル**を使う。通常モデルとの精度・速度差は実データで評価する（[prep.md](../spec/prep.md) §推奨）。

`model_id` にはどちらのモデルを使ったかが分かる識別子を入れる。これにより、後から `item_file_texts.extractor` を見て「どのモデルで抽出したか」を追える（[user-stories.md](../spec/user-stories.md) ストーリー4.2）。

### 3. デバイス可用性の起動時検証 🔵

**信頼性**: 🔵 *REQ-113・REQ-412・PRD §8.9・TC-NFR-301-03 より*

```python
def _verify_device_available(device: OcrDeviceSetting) -> None:
    if device is OcrDeviceSetting.CUDA:
        import torch
        if not torch.cuda.is_available():
            raise OcrDeviceUnavailableError(
                "EXTRACTOR_OCR_DEVICE=cuda が指定されましたが CUDA GPU を利用できません"
            )
```

**この検証は `__main__.py` の起動時、claim ループに入る前に実行する** 🔵。PRD §8.9 の受け入れ条件が「ジョブを claim する前に起動エラーとなる」と明記している。

途中でCPUへフォールバックしない（REQ-412）。中途半端に動くより、起動を失敗させて設定ミスを明示する。

### 4. 未知のデバイス値 🔵

**信頼性**: 🔵 *REQ-114・PRD FR-011より*

`OcrDeviceSetting` を enum にしてあるため、`EXTRACTOR_OCR_DEVICE=metal` のような値は pydantic-settings のパース時点で `ValidationError` になる。追加の実装は不要だが、テストで固定する。

### 5. デバイスは起動時に確定 🔵

**信頼性**: 🔵 *REQ-411・PRD FR-011・TC-NFR-301-04 より*

`YomitokuOcrEngine` はコンストラクタでデバイスを受け取り、以後変更しない（`frozen` 相当）。実行中の抽出でデバイスが変わる余地を型で断つ。

切り替えには worker の再起動が必要（設定変更 → `docker compose restart`）。

### 6. ヘルスチェックへの追加 🔵

**信頼性**: 🔵 *NFR-403・REQ-303・TC-NFR-403-01 より*

[TASK-0016](TASK-0016.md) で作ったヘルスチェックに「OCRバックエンド到達性」を追加する。プロセス生存・api到達性と**区別できる**シグナルにする。

初期化済みの `OcrEngine` が存在し、デバイスが利用可能であることを返す。

### 7. GPU運用の前提 🔵

**信頼性**: 🔵 *NFR-301・NFR-302・[tech-stack.md](../tech-stack.md) §GPU制約より*

MVPは `cpu` が既定。vLLM が `--gpu-memory-utilization 0.90` でGPUを常時予約しているため、GPU同時利用可能とはみなさない。

`cuda` で運用する場合は vLLM の VRAM 上限を下げる運用変更とセットで行う（[prep.md](../spec/prep.md) §確認事項）。**VRAM不足時の自動切り替えは行わない**（NFR-302）。

## 注意事項

- **`cuda` → 報告値は `gpu`**。設定値をそのまま報告しない。型を分けてあるのはこのため
- **暗黙のCPUフォールバックに依存しない**（REQ-412）。yomitoku が内部でフォールバックする挙動があっても、その前に自前で検証して失敗させる
- 起動時検証は `__main__.py` の claim ループに入る前に呼ぶ。PRD §8.9 の「claim する前に」が要求
- `import yomitoku` を `ocr/yomitoku.py` の中に閉じる。モジュールトップレベルの import が他ファイルに漏れると Protocol 境界の意味が失われる
- yomitoku のモデルロードは初回に時間がかかる。起動時に一度だけ行い、抽出ごとに再ロードしない
- GPU テストは環境依存。CI がない前提（ヒアリングで決定）なので、ローカルでの手動実行を想定する
