# MediaVault Extractor 全文抽出 ユーザストーリー

**作成日**: 2026-08-14
**関連要件定義**: [requirements.md](requirements.md)
**ヒアリング記録**: [interview-record.md](interview-record.md)

**【信頼性レベル凡例】**:
- 🔵 **青信号**: PRD・設計文書・ユーザヒアリングを参考にした確実なストーリー
- 🟡 **黄信号**: PRD・設計文書・ユーザヒアリングから妥当な推測によるストーリー
- 🔴 **赤信号**: PRD・設計文書・ユーザヒアリングにない推測によるストーリー

## 登場するユーザー種別

| 種別 | 説明 |
|---|---|
| AIエージェント | `intrahub-mastra`。mediavault-mcp 経由で MediaVault を利用し、作品内容を材料に調査・執筆する |
| 蔵書管理者 | MediaVault の唯一の人間ユーザー（単一ユーザー・セルフホスト） |
| 運用者 | homelab を保守する立場。蔵書管理者と同一人物だが、関心が異なるため分けて記述する |

## エピック1: テキスト抽出を依頼する

### ストーリー 1.1: PDFの全文抽出を依頼する 🔵

**信頼性**: 🔵 *PRD §3・§6 FR-001、ヒアリングQ1より*

**私は** AIエージェント **として**
**登録済みPDFの全文抽出を依頼したい**
**そうすることで** 作品の内容を調査・執筆の材料として読めるようになる

**関連要件**: REQ-001, REQ-004, REQ-060, REQ-105

**詳細シナリオ**:
1. `get_item_text` を呼ぶが、対象ファイルは未抽出のため `not_extracted` が返る
2. エラーメッセージに従い `request_extraction(item_id, file_id)` を呼ぶ
3. api が対象ファイルの存在・Itemへの帰属・対応形式・読み取り可能性を検証する
4. `item_file_extractions` に `queued` の行が作られ、`201` が返る
5. worker がポーリングで claim し、抽出を開始する

**前提条件**:
- 対象 `item_file` が登録済みで、共有ボリューム上に実体がある
- `file_type` が `pdf` または `image`

**制約事項**:
- ホストパスを指定した抽出はできない。指定できるのは `item_file_id` のみ（REQ-402）
- ファイル登録時に自動で抽出は始まらない（REQ-401）

**優先度**: Must Have

### ストーリー 1.2: 同じファイルへ重複して依頼しても壊れない 🔵

**信頼性**: 🔵 *PRD §8.1 重複禁止要求・§8.8、ヒアリングQ1より*

**私は** AIエージェント **として**
**リトライやタイムアウトで同じ抽出依頼を複数回送ってしまっても、二重に処理されないことを保証してほしい**
**そうすることで** 呼び出しの失敗時に安全に再送できる

**関連要件**: REQ-044, REQ-101, REQ-102

**詳細シナリオ**:
1. `request_extraction` を送るが、レスポンス受信前にタイムアウトする
2. 同じ引数で再送する
3. api は未完了の抽出が既にあることを検知し、新規作成せず既存を `200` で返す
4. worker は1回だけ抽出を実行する

**前提条件**: 同一 `item_file_id` に対する呼び出しであること

**制約事項**: 冪等性は `dedup_key` ではなく、未完了状態に対する部分UNIQUE indexで担保される

**優先度**: Must Have

---

### ストーリー 1.3: 対象外の形式を依頼したときに理由がわかる 🟡

**信頼性**: 🟡 *PRD FR-003・§4.2 と item-files.md の file_type 分類から妥当な推測*

**私は** AIエージェント **として**
**動画ファイルなど抽出できない対象を依頼したとき、明確な理由を受け取りたい**
**そうすることで** 無駄なポーリングをせず、別の材料を探す判断ができる

**関連要件**: REQ-004, REQ-410

**詳細シナリオ**:
1. `file_type: video` のファイルに対し `request_extraction` を呼ぶ
2. api は抽出を作成せず、`422 UNSUPPORTED_FILE_TYPE` を返す
3. エージェントは「この材料は使えない」と判断し、依頼を繰り返さない

**優先度**: Must Have

**備考**: MVPの対象形式を pdf / image に限る判断はPRDに明記がなく、§4.2「動画・音声の文字起こしは対象外」からの推測。archive（cbz等）の扱いは設計フェーズで再確認が望ましい。

## エピック2: 進捗を確認し、必要なら止める

### ストーリー 2.1: 抽出の進捗を確認する 🔵

**信頼性**: 🔵 *PRD §3・§8.3、mcp PRD §7.2 US-11より*

**私は** AIエージェント **として**
**依頼した抽出が今どの段階にあるかを知りたい**
**そうすることで** 完了を待つべきか、失敗したので諦めるべきかを判断できる

**関連要件**: REQ-002, REQ-023, REQ-066, REQ-081, REQ-301

**詳細シナリオ**:
1. `get_extraction_status(item_id, file_id)` を呼ぶ
2. api は状態（`queued` / `running` / `succeeded` / `failed` / `cancelling` / `cancelled`）と進捗（処理済ページ数 / 総ページ数）を返す
3. worker はページ境界ごとに heartbeat で進捗を更新しているため、値は処理中も更新される
4. `failed` の場合は構造化されたエラー理由と試行回数が含まれる

**前提条件**: 対象ファイルに抽出が1件以上存在する

**優先度**: Must Have

---

### ストーリー 2.2: 長すぎる抽出をキャンセルする 🔵

**信頼性**: 🔵 *PRD FR-008・§8.5、mcp PRD §5 US-11より*

**私は** 蔵書管理者 **として**
**数百ページのスキャンPDFのOCRが想定より長引いたとき、途中で止めたい**
**そうすることで** CPUを他の処理へ回せる

**関連要件**: REQ-003, REQ-202, REQ-204, REQ-207, REQ-082

**詳細シナリオ**:
1. `POST /items/{id}/files/{file_id}/extraction/cancel` を呼ぶ
2. `running` の抽出は `cancelling` へ遷移する（即座に `cancelled` にはしない）
3. worker は次の heartbeat でキャンセル要求を受け取る
4. worker はページ境界で処理を中断し、`cancelled` エンドポイントへ確認を送る
5. 抽出が `cancelled`（終端）へ遷移する。**部分結果は成功として確定されない**

**前提条件**: 抽出が `queued` または `running` である

**制約事項**:
- `queued` の抽出は worker の確認を待たず直接 `cancelled` へ遷移してよい
- 終端状態への cancel は `409 EXTRACTION_ALREADY_FINISHED`

**優先度**: Must Have

---

### ストーリー 2.3: キャンセルしても既存の抽出結果が消えない 🔵

**信頼性**: 🔵 *PRD §8.2より*

**私は** 蔵書管理者 **として**
**再抽出を試して途中でやめたとき、以前の抽出結果が残っていてほしい**
**そうすることで** 実験的な再抽出を安心して試せる

**関連要件**: REQ-206, REQ-103

**詳細シナリオ**:
1. 既に成功済みの抽出結果があるファイルに対し、再抽出を依頼する
2. 途中でキャンセル、または失敗する
3. `item_file_texts` の既存行はそのまま残り、`GET /items/{id}/text` は従来どおり `200` を返す

**優先度**: Must Have

## エピック3: 抽出済みテキストを材料として使う

### ストーリー 3.1: 全文をチャンク単位で読む 🔵

**信頼性**: 🔵 *item-text.md・mastra-integration.md・PRD §8.6より*

**私は** AIエージェント **として**
**作品の全文を、形式によらず同じ構造のチャンクとして順に読みたい**
**そうすることで** PDF・EPUB・画像の違いを意識せず調査ロジックを1本化できる

**関連要件**: REQ-005, REQ-006, REQ-007, REQ-413, REQ-414

**詳細シナリオ**:
1. `get_item_text(item_id, chunk_index: 0)` を呼ぶ
2. `total_chunks: 12` と先頭4000文字、`extraction_version: "pdf-v1"` が返る
3. `chunk_index` を 1, 2, ... と進めて全文を読む
4. 引用したい箇所を `(itemId, fileId, chunkIndex, extraction_version)` として保存する

**前提条件**: 対象ファイルの抽出が完了している

**制約事項**:
- 1レスポンスに全文は入らない。`chunk_size` の上限は 20000
- `index` は形式非依存の0起点連番。ページ番号ではない

**優先度**: Must Have

---

### ストーリー 3.2: 引用箇所のページ番号を表示する 🔵

**信頼性**: 🔵 *PRD FR-006・ヒアリングQ5より*

**私は** AIエージェント **として**
**引用したチャンクが原典の何ページに当たるかを知りたい**
**そうすることで** 生成した文書に「p.42」のような人間が検証できる出典を付けられる

**関連要件**: REQ-042, REQ-068, REQ-006

**詳細シナリオ**:
1. `get_item_text` のレスポンスに `label: "p.42"` が含まれる
2. `label` は worker が保存した `boundaries`（文字範囲とラベルの対応）から解決される
3. チャンク境界がページ境界に対応づかない場合、`label` は `null` となる

**前提条件**: 抽出時に境界情報が保存されていること（MVPから対応）

**優先度**: Must Have

**備考**: 当初 item-text.md は「MVPでは `label` を常に null」としていたが、後から追加すると全ファイルの再抽出が必要になるため、ヒアリングQ5でMVP対応に変更した。

---

### ストーリー 3.3: 保存済みの出典が古くなったことを検知する 🔵

**信頼性**: 🔵 *item-text.md §extraction_version・PRD FR-010より*

**私は** AIエージェント **として**
**以前保存した出典参照が、再抽出によって別の箇所を指すようになったことを検知したい**
**そうすることで** 誤った引用を生成せずに済む

**関連要件**: REQ-103, REQ-104, REQ-414

**詳細シナリオ**:
1. 保存済み出典 `(fileId, chunkIndex, extraction_version: "pdf-v1")` を持っている
2. ファイルが再抽出され、`extraction_version` が `"pdf-v2"` に変わる
3. `get_item_text` のレスポンスの `extraction_version` と保存値を比較し、不一致を検知する
4. 当該出典を失効として扱い、再取得する

**前提条件**: 抽出ロジックまたはチャンク境界の変更時に worker が `extraction_version` を変更していること

**優先度**: Must Have

---

### ストーリー 3.4: 「材料が無い」と「まだ抽出していない」を区別する 🔵

**信頼性**: 🔵 *item-text.md §エラーの使い分け・api-tool-mapping.md §エラー分類より*

**私は** AIエージェント **として**
**テキストが得られない理由が「ファイルが無い」のか「まだ抽出していない」のかを区別したい**
**そうすることで** 前者は諦め、後者は抽出を依頼するという正しい次の行動が取れる

**関連要件**: REQ-116, REQ-117, REQ-083, NFR-501, NFR-503

**詳細シナリオ**:
1. `get_item_text` が `422 TEXT_NOT_EXTRACTED` を返す
2. mcp はこれを `not_extracted` として返し、`request_extraction` での解決を促すメッセージを含める
3. エージェントは抽出を依頼し、完了後に再取得する
4. 一方 `404 FILE_NOT_FOUND` の場合は、材料自体が存在しないため別の情報源へ切り替える

**優先度**: Must Have

---

### ストーリー 3.5: 複数の抽出済みファイルがあるとき勝手に選ばれない 🔵

**信頼性**: 🔵 *item-text.md §主ファイルの解決より*

**私は** AIエージェント **として**
**1つのItemに本編PDFと付録PDFがあるとき、どちらが使われたか曖昧なまま結果を受け取りたくない**
**そうすることで** 誤ったファイルからの引用を防げる

**関連要件**: REQ-115, NFR-502

**詳細シナリオ**:
1. `file_id` を省略して `get_item_text` を呼ぶ
2. 抽出済みファイルが2件あるため `409 AMBIGUOUS_FILE` が返る
3. レスポンスの `candidates` から適切なファイルを選び、`file_id` を明示して再試行する

**優先度**: Must Have

## エピック4: 抽出をやり直す

### ストーリー 4.1: OCR精度を上げるために再抽出する 🔵

**信頼性**: 🔵 *PRD FR-010・FR-011より*

**私は** 運用者 **として**
**CPUの軽量モデルで抽出した文書を、GPUの通常モデルで抽出し直したい**
**そうすることで** 精度と処理時間のトレードオフを実データで評価できる

**関連要件**: REQ-103, REQ-104, REQ-043, REQ-411

**詳細シナリオ**:
1. `EXTRACTOR_OCR_DEVICE=cuda` に変更して worker を再起動する
2. 同じファイルに対して抽出を再依頼する
3. 完了時に `item_file_texts` の該当行が置き換えられ、`extractor` メタデータに `device: gpu`・エンジン・モデル識別子が記録される
4. 抽出方式が変わったため `extraction_version` も更新される

**前提条件**: CUDA GPU が利用可能で、vLLM の VRAM 使用上限が調整済みであること

**制約事項**:
- 実行方式は起動時に確定し、処理中の抽出では変わらない（REQ-411）
- VRAM不足時の自動CPU切り替えは行わない（NFR-302）

**優先度**: Should Have

---

### ストーリー 4.2: 抽出方式ごとの結果を比較できる 🔵

**信頼性**: 🔵 *PRD FR-007・§8.9より*

**私は** 運用者 **として**
**各抽出結果がどの方式（埋め込みテキスト / OCR）・どのデバイス・どのモデルで得られたかを知りたい**
**そうすることで** 品質問題が起きたときに原因を切り分けられる

**関連要件**: REQ-043, REQ-065

**優先度**: Must Have

---

## エピック5: 障害から復旧する

### ストーリー 5.1: worker が落ちても抽出が失われない 🔵

**信頼性**: 🔵 *PRD §8.1・§8.8より*

**私は** 運用者 **として**
**worker コンテナが異常終了しても、処理中だった抽出が永久に `running` のまま残らないでほしい**
**そうすることで** 手動でDBを触らずに復旧できる

**関連要件**: REQ-021, REQ-118, NFR-202

**詳細シナリオ**:
1. worker が抽出を claim し、`running` になる
2. worker が OOM 等で異常終了し、heartbeat が止まる
3. `lease_expires_at` を過ぎる
4. 再起動した worker（または別 worker）が同じ抽出を再claimできる
5. `attempts` が加算され、上限に達すれば `failed` となる

**優先度**: Must Have

---

### ストーリー 5.2: 古い worker の結果に上書きされない 🔵

**信頼性**: 🔵 *PRD §8.5・§8.8より*

**私は** 運用者 **として**
**lease 失効後にゾンビ化した旧 worker が、新しい試行の結果を上書きしないことを保証してほしい**
**そうすることで** 抽出結果の一貫性が保たれる

**関連要件**: REQ-407, EDGE-002

**詳細シナリオ**:
1. worker A が claim し lease token X を得るが、ネットワーク分断で heartbeat が途絶える
2. lease が失効し、worker B が再claimして token Y を得る
3. 復帰した worker A が token X で complete を送る
4. api は token 不一致を検出し `409 INVALID_LEASE_TOKEN` で拒否する
5. worker B の結果のみが保存される

**優先度**: Must Have

---

### ストーリー 5.3: Extractor が壊れても MediaVault は動く 🔵

**信頼性**: 🔵 *PRD NFR-001・§2より*

**私は** 蔵書管理者 **として**
**OCR が失敗し続けたり Extractor が停止していても、蔵書の検索・登録・更新が普段どおり使えてほしい**
**そうすることで** 抽出は「あると便利な付加機能」に留まり、日常利用を阻害しない

**関連要件**: NFR-201, NFR-203

**優先度**: Must Have

---

### ストーリー 5.4: 障害の切り分けができる 🔵

**信頼性**: 🔵 *PRD NFR-004より*

**私は** 運用者 **として**
**抽出が進まないとき、worker が死んでいるのか、api に届いていないのか、OCRバックエンドが応答しないのかを区別したい**
**そうすることで** 復旧の当たりを素早くつけられる

**関連要件**: REQ-303, NFR-401, NFR-403, NFR-402

**詳細シナリオ**:
1. ヘルスチェックがプロセス生存・api到達性・OCRバックエンド到達性を別々のシグナルとして返す
2. 構造化ログから抽出ID・ファイルID・処理時間・終了状態を追える
3. 待機中の抽出数・待機時間・成功率・lease切れ回数から傾向を把握できる
4. ログにAPIキー・抽出本文・画像は出力されていない

**優先度**: Should Have

---

## エピック6: 設計文書の整合性を保つ

2. index.md / internal-api.md / item-text.md / data-model.md を改訂する
3. mcp 側6ファイルの jobs 記述を extraction へ差し替える
4. 存在しない `docs/basic-design/04_jobs-and-agent-integration.md` への参照も除去する
5. `grep -rn "jobs.md\|enqueue_job\|job_type" docs/` で残存参照がゼロになることを確認する

**優先度**: Must Have
