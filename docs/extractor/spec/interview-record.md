# MediaVault Extractor 全文抽出 ヒアリング記録

**作成日**: 2026-08-14
**ヒアリング実施**: step4 既存情報ベースの差分ヒアリング

## ヒアリング目的

[PRD.md](../PRD.md)、[tech-stack.md](../tech-stack.md)、mediavault-api / mediavault-mcp の既存設計文書と実装を確認し、以下を明確化するためヒアリングを実施した。

1. 「jobsを廃止してextractor用のエンドポイントを再設計する」という指示に対し、代替となるリソース設計を確定する
2. PRD §11「要調整事項」の5項目のうち、要件定義に影響する項目を決定する
3. 改訂スコープ（mediavault-mcp を含めるか）を確定する

### ヒアリング前の事前調査で判明した事実

| 調査項目 | 結果 | 意味 |
|---|---|---|
| `docs/backend/mediavault-api/jobs.md` | **存在しない**。6ファイルからリンク切れ参照 | jobs は「仕様の断片と参照だけが先行した状態」 |
| `jobs` テーブル | migration に存在しない（`init_schema` 1本のみ） | DB移行不要 |
| jobs ハンドラ・MCPツール | 実装なし | コード変更なしで廃止可能 |
| `/import/booklog/jobs/*` | 存在するが Booklog インポート専用の別機構 | 本要件の対象外・廃止しない |

この調査により「jobs廃止」が**破壊的変更を一切伴わない**ことが確定し、以降の質問を「どう代替するか」に集中できた。

---

## 質問と回答

### Q1: jobs廃止後、抽出ジョブの公開リソースをどう表現しますか？

**質問日時**: 2026-08-14
**カテゴリ**: 既存設計の妥当性・過不足確認
**背景**: PRD §8.1 は `job_type` / `dedup_key` / 型なし `payload` を持つ汎用 `jobs` テーブルを要求していた。しかしMVPの `job_type` は `extract_text` 1種のみであり、抽出対象は常に `item_file` 1件である。汎用性のために払うコスト（dedup_key設計、payload検証、job_type分岐）に見合う需要が現時点で存在しないため、代替表現を確認する必要があった。

**選択肢**:
- ファイル従属の抽出リソース（`/items/{id}/files/{file_id}/extraction`）
- 独立コレクション（`/extractions`）
- 両方

**回答**: **ファイル従属の抽出リソース**

**信頼性への影響**:
- REQ-001〜004、REQ-101、REQ-102 を新規追加（信頼性 🔵）
- REQ-044（部分UNIQUE index による未完了1件保証）を追加し、PRD §8.1 の `dedup_key` 要求を置き換え。冪等性の担保方法が 🔴（未定）→ 🔵 へ確定
- PRD §8.1 のフィールド表から `job_type` / `dedup_key` / `target_item_id` を除去する根拠が確定
- REQ-090、REQ-091（jobs記述の除去、`extraction.md` の新規作成）を追加

### Q2: workerへのファイル受け渡し方式は？（PRD §11-3）

**質問日時**: 2026-08-14
**カテゴリ**: 未定義・曖昧部分の詳細化
**背景**: PRD §11-3 が「共有ボリューム or 内部APIストリーミング」を未決としていた一方、[tech-stack.md](../tech-stack.md) §ファイルアクセスは既に read-only 共有ボリュームを前提に compose 定義まで書いていた。文書間で決定状態が食い違っており、要件として確定させる必要があった。

**回答**: **read-only 共有ボリューム**（PRD の第一候補・tech-stack.md の前提と一致）

**信頼性への影響**:
- REQ-022（claim レスポンスに検証済みファイル参照を含める）が 🟡 → 🔵 へ
- REQ-403、REQ-404、NFR-102、NFR-103 の根拠が確定
- PRD §11-3 と tech-stack.md の不整合が解消

---

### Q3: 内部APIのパス規約はどちらに統一しますか？（PRD §11-2）

**質問日時**: 2026-08-14
**カテゴリ**: 既存機能への影響範囲確認
**背景**: mediavault-api の実装は `/internal/*`、mediavault-mcp の内部APIキー判定は `/api/v1/internal/*` を前提としており、両者が食い違っていた。worker 内部API 5本を追加する前に規約を統一しないと、不整合が5本ぶん拡大する。

**回答**: **`/api/v1/internal/*` に統一**（既存 `/internal/*` 5本も移設）

**信頼性への影響**:
- REQ-029 を新規追加（信頼性 🔵）。既存内部API 5本の移設が要件として確定
- 内部API 5本の追加パスが `/api/v1/internal/extractions/*` に確定し、REQ-020〜027 の信頼性が 🟡 → 🔵 へ
- mediavault-mcp 側の判定ロジック改修が不要であることが確定（api側を合わせるため）
- **影響範囲**: 既存の `/internal/*` を呼ぶクライアントがあれば移行が必要。現状 mediavault-mcp のみが利用しており、同 crate 内で追随可能

---

### Q4: 抽出結果の送信方式は？（PRD §11-4）

**質問日時**: 2026-08-14
**カテゴリ**: 未定義・曖昧部分の詳細化
**背景**: PRD §11-4 が未決。段階送信は大容量文書に強いが、部分結果のクリーンアップと「ジョブ成功と結果保存を同一トランザクションで確定」（PRD §8.2）の両立が難しくなる。

**回答**: **完了時に一括送信**

**信頼性への影響**:
- REQ-025（同一トランザクション）、REQ-067（一括送信）が 🟡 → 🔵 へ
- 部分結果の中間テーブル・クリーンアップ処理が不要と確定し、データモデルから該当要件が削除された
- 代わりに EDGE-009（保存サイズ上限超過時の complete 拒否）が必要となり追加（🟡）

---

### Q5: ページ・章の境界情報（boundaries）はMVPで保存しますか？（PRD §11-5）

**質問日時**: 2026-08-14
**カテゴリ**: 既存設計の妥当性・過不足確認
**背景**: PRD FR-006 は出典位置の保持を求めているが、[item-text.md](../../backend/mediavault-api/item-text.md) §データモデルへの要求は「初期実装では `label` を常に `null` とし、区切り位置の保持は後続の課題とする」と明記しており、**PRDと設計書が矛盾**していた。後から入れる場合は全ファイルの再抽出が必要になるため、早期の決着が必要だった。

**回答**: **MVPから保存する**（jsonb で `[{start, end, label}]`）

**信頼性への影響**:
- REQ-042、REQ-068 が新規追加（信頼性 🔵）
- item-text.md の「`label` 常に null」記述が**改訂対象**として確定
- REQ-413（chunk index は0起点連番のまま変えない）を明示的に追加。boundaries 導入が intrahub-mastra の出典参照規約を崩さないことを制約として固定
- EDGE-107（boundaries の整合性検証）を追加（🟡）

---

### Q6: ファイル登録時の自動抽出は？

**質問日時**: 2026-08-14
**カテゴリ**: 追加・変更要件の特定
**背景**: PRD に記載がない論点。`POST /items/{id}/files` と `/upload` に自動キューを仕込むかどうかで、Booklog / Steam の一括インポート時の負荷特性が大きく変わる。

**回答**: **手動起動のみ**

**信頼性への影響**:
- REQ-401（自動キュー禁止）を制約要件として追加（🔵）。仕様外の推測実装を防ぐ
- 大量インポート時のOCR負荷スパイクという非機能リスクが要件段階で排除された

---

### Q7: mediavault-mcp 側のツール再設計も今回の要件に含めますか？

**質問日時**: 2026-08-14
**カテゴリ**: 優先順位・スコープ調整
**背景**: mcp 側は `enqueue_job` / `get_job` / `list_jobs` / `cancel_job` の4ツールを「設計済み・未実装」として PRD §7.2・mcp-tools.md・api-tool-mapping.md に記載している。api 側の jobs を廃止すると、これらは宛先を失う。スコープに含めなければ、設計書が壊れたまま残る。

**回答**: **含める**

**信頼性への影響**:
- REQ-080〜083 を新規追加（信頼性 🔵）。4ツール → 3ツールへの再定義が確定（`get_job` と `list_jobs` は、対象が1ファイル1件になったため `get_extraction_status` に統合）
- mcp 側6ファイルが改訂対象として [note.md](note.md) §4 に列挙された

---

### Q8: 要件定義の作業規模と出力先

**質問日時**: 2026-08-14
**カテゴリ**: 優先順位・スコープ調整
**背景**: kairo-requirements の必須確認事項。既存 spec は `docs/backend/mediavault-mcp/spec/` に置かれており、kairo 既定の `docs/spec/` とは異なる。

**回答**: **フル機能開発 / `docs/extractor/spec/`**（既存プロジェクトの配置慣習に合わせる）

**信頼性への影響**: 成果物の構成が確定。user-stories.md と acceptance-criteria.md を分離ファイルとして作成する。

## ヒアリング結果サマリー

### 確認できた事項

- 汎用jobsは実装が存在せず、廃止は破壊的変更を伴わない（事前調査）
- 抽出リソースはファイル従属とし、`dedup_key` は不要（Q1）
- ファイル受け渡しは read-only 共有ボリューム。PRD と tech-stack.md の不整合が解消（Q2）
- 内部APIは `/api/v1/internal/*` へ統一。既存5本も移設（Q3）
- 結果は完了時一括送信、同一トランザクションで確定（Q4）
- boundaries は MVP から保存。item-text.md の記述を改訂（Q5）
- 自動抽出は行わない（Q6）
- mcp のツール再定義もスコープに含む（Q7）

### 追加/変更要件

| 種別 | 内容 |
|---|---|
| 追加 | REQ-029（既存内部API 5本の `/api/v1/internal/*` への移設） |
| 追加 | REQ-044（部分UNIQUE index による未完了1件保証）— `dedup_key` の代替 |
| 追加 | REQ-042 / REQ-068（boundaries の MVP 保存） |
| 追加 | REQ-401（ファイル登録時の自動抽出禁止） |
| 追加 | REQ-080〜083（MCP ツール3本の再定義） |
| 追加 | REQ-090 / REQ-091（jobs記述の除去、`extraction.md` の新規作成） |
| 変更 | PRD §8.1 のフィールド表から `job_type` / `dedup_key` / `target_item_id` を除去 |
| 変更 | item-text.md の「`label` は常に null」記述を撤回 |
| 変更 | mcp の jobs 系4ツール → extraction 系3ツール |
| 削除 | エラーコード `JOB_NOT_FOUND` / `JOB_ALREADY_FINISHED` |

### 残課題

以下は要件段階では確定せず、設計フェーズ（kairo-design）または実測後に決定する。

1. **OCRフォールバック判定の品質基準**（FR-004 の「品質基準を満たさないページ」の閾値）。実データでの評価が必要
2. **`EXTRACTOR_JOB_TIMEOUT_SEC` の初期値**。CPU実行時のOCR処理時間の実測に依存（NFR-003）
3. **抽出本文・エラーの保存サイズ上限値**（REQ-408・EDGE-009）。実データのサイズ分布を見て決定
4. **`max_attempts` の既定値**（REQ-111・REQ-112）
5. **lease 期間と heartbeat 間隔の具体値**（REQ-021・REQ-023）
6. **`item_files.path` の2経路（絶対パス / `STORAGE_ROOT` 相対）を、claim レスポンスでどう正規化して worker へ渡すか**の具体形式
7. **既存 `/internal/*` パスの移行方法**（即時切替か、暫定 alias を経るか）

### 信頼性レベル分布

**ヒアリング前**（PRD・設計文書のみから起草した場合の想定）:
- 🔵 青信号: 約 55%（PRD に明記された FR / NFR 由来）
- 🟡 黄信号: 約 30%（jobs 廃止後の代替設計、PRD §11 の未決事項）
- 🔴 赤信号: 約 15%（リソース設計、MCP スコープ、自動抽出の有無）

**ヒアリング後**（[requirements.md](requirements.md) 実測。要件項目125件）:
- 🔵 青信号: 88%（110件）
- 🟡 黄信号: 12%（15件）
- 🔴 赤信号: 0%（0件）

8問の回答により、PRD §11 の要調整事項5件すべてと、jobs 廃止後のリソース設計・スコープが確定し、🔴 が消滅した。
