## タスク概要

`mediavault-mcp` を独立した Docker イメージとしてビルドし、`docker-compose.yml` にサービスとして追加する。

別コンテナ構成により、mediavault-api とは障害分離され、個別に再起動できる（REQ-121）。

## 実装詳細

### 1. Dockerfile 🔵

**信頼性**: 🔵 *[tech-stack.md](../tech-stack.md)「マルチステージビルド（cargo build --release -p mediavault-mcp）」より*

**実装ファイル**: `backend/mediavault-mcp/Dockerfile`（または既存 `backend/Dockerfile` にターゲット追加）

マルチステージ構成:

1. **builder**: Rust イメージで `cargo build --release -p mediavault-mcp`
2. **runtime**: debian-slim 等に実行バイナリのみコピー

**既存 `backend/Dockerfile` との関係を確認する** 🟡

**信頼性**: 🟡 *`backend/Dockerfile` が既に存在することから導かれる実装上の判断*

既存 Dockerfile が mediavault-api 用に書かれている。以下から選ぶ:

| 案 | 内容 |
|---|---|
| A. 別ファイル | `mediavault-mcp/Dockerfile` を新設。独立性が高い |
| B. マルチターゲット | 既存 Dockerfile に `--target` で分岐。依存ビルドを共有できる |

workspace 全体をコピーする必要がある点は共通。実装時に既存 Dockerfile を読んで判断する。

**ビルドキャッシュの最適化** 🟡

**信頼性**: 🟡 *Rust の Docker ビルド一般のプラクティス*

`Cargo.toml` / `Cargo.lock` を先にコピーして依存だけビルドし、ソース変更時の再ビルドを短縮する。

### 2. docker-compose サービス定義 🔵

**信頼性**: 🔵 *[prep.md](../spec/prep.md) PREP-07・[architecture.md](../design/architecture.md) システム構成図より*

**実装ファイル**: `docker-compose.yml`

```yaml
mediavault-mcp:
  build:
    context: ./backend
    dockerfile: mediavault-mcp/Dockerfile
  environment:
    MCP_BIND_ADDR: 0.0.0.0:8081
    MCP_AUTH_TOKEN: ${MCP_AUTH_TOKEN:?MCP_AUTH_TOKEN is required}
    MEDIAVAULT_API_BASE_URL: http://mediavault-api:8080
    INTERNAL_API_KEY: ${INTERNAL_API_KEY}
    RUST_LOG: ${RUST_LOG:-info}
  ports:
    - "8081:8081"
  depends_on:
    - mediavault-api
  restart: unless-stopped
  healthcheck:
    test: ["CMD", "curl", "-f", "http://localhost:8081/healthz"]
    interval: 30s
    timeout: 3s
    retries: 3
```

**`depends_on` に `condition: service_healthy` を付けない** 🔵

**信頼性**: 🔵 *REQ-121「api が停止していても MVP のメタデータ検索・登録・整理は利用可能とする」の趣旨より*

api の起動を待つ設定にすると、api 障害時に mcp まで巻き添えで停止する。順序付けのみの `depends_on` に留める。

**ヘルスチェックが `/healthz` である理由** 🔵

**信頼性**: 🔵 *[architecture.md](../design/architecture.md) 可用性より*

`/healthz` は MediaVault-api の状態に依存しない（TASK-0007）。api 障害時にコンテナが unhealthy 判定されて再起動ループへ陥ることを防ぐ。

**信頼性**: 🔵 *完了条件より*

### 確認4: トークン未設定で起動失敗 🔵

**信頼性**: 🔵 *REQ-122・完了条件より*

`MCP_AUTH_TOKEN` を空にして `docker compose up` する。コンテナが起動失敗し、ログに原因が出ることを確認する（値は出ないこと）。

### 確認5: api 停止時の独立動作 🔵

**信頼性**: 🔵 *REQ-121・完了条件より*

```bash

# health ツール → api.reachable: false

```

**信頼性**: 🔵 *完了条件・[prep.md](../spec/prep.md) PREP-08 より*

## 注意事項

- **`depends_on` に `condition: service_healthy` を付けないこと**。REQ-121 の障害分離が壊れる
- ヘルスチェックに `curl` を使う場合、runtime イメージに `curl` が必要になる。distroless などを使う場合は別の方法（バイナリ自身に `--health-check` サブコマンドを持たせる等）を検討する 🟡
- `MCP_AUTH_TOKEN` を compose の `${VAR:?message}` 形式にすることで、未設定時に compose 側でも早期に失敗させられる 🟡
- ポート 8081 が既存サービスと衝突しないか、インフラ側のデプロイ・ルーティング設計と実機で確認する 🟡
- 外部公開（リバースプロキシ経由）は PREP-11 が未確定のため本タスクの範囲外
