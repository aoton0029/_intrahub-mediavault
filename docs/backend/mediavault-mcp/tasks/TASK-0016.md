## 実装詳細

### 1. ツール定義 🔵

**信頼性**: 🔵 *[mcp-tools.md](../design/mcp-tools.md) 10. より*

**実装ファイル**: `backend/mediavault-mcp/src/tools/collection_overview.rs`

- 引数: `recent_limit: Option<u32>`（1..=50、既定10）🟡 *[interfaces.rs](../design/interfaces.rs)「パラメータは要件に明記がないため設計上の判断」*
- annotation: `readOnlyHint: true` 🔵
- 説明文（AI向け）:
  > コレクション全体の統計と最近の動きを取得する。「何を見るか」を相談される前に呼ぶと、候補を絞る条件を立てやすい。

### 2. api 呼び出し 🔵

**信頼性**: 🔵 *TASK-0004 の成果・[prep.md](../spec/prep.md) PREP-04 より*

```
GET /api/v1/collection/overview?recent_limit={}
```

単一呼び出しで完結する。`GET /items/counts-by-media-type` は使わない（status別が取れないため）🔵

### 3. CountEntry への変換 🔵

**信頼性**: 🔵 *[interfaces.rs](../design/interfaces.rs) `CountEntry`・[mcp-tools.md](../design/mcp-tools.md) のレスポンス例より*

api が `MediaTypeCounts`（`{"anime": 42, "movie": 10, ...}`）のようなオブジェクト形式で返す場合、`[{"key": "anime", "count": 42}]` の配列へ変換する。

**配列形式にする理由** 🟡: 件数の多い順に並べ替えて返せる。AI が「一番多いのは漫画で87件」と答えやすい。

**0件の media_type を含めるか** 🟡: 既存 `counts-by-media-type` は全種別を返す（0を含む）。0件の種別は除外して返すほうが AI にとってノイズが少ない。実装時に判断してよい。

### 4. 最近の Item の縮約 🔵

**信頼性**: 🔵 *設計決定 D-04・TASK-0012 の成果より*

`recently_added` / `recently_updated` を `ItemSummary` へ縮約する。`description` を含めない。

### 5. recent_limit のバリデーション 🔵

**信頼性**: 🔵 *REQ-143・[mcp-tools.md](../design/mcp-tools.md)「1..=50、既定 10」より*

`search_library` と同じ規約に揃える。51以上はバリデーションエラー（丸めない）🟡

### 6. エラーの扱い 🔵

**信頼性**: 🔵 *EDGE-002・受け入れ基準 TC-090-E01 より*

集計API が 500 を返した場合、`outcome: error` にする。**件数0の成功として返さない**（EDGE-002「空の成功結果を返さない」）。

「コレクションが空」と「取得に失敗」は利用者への意味がまったく異なる。

## AIエージェント向け要件

### 候補相談の入口として 🔵

**信頼性**: 🔵 *US-09・[user-stories.md](../spec/user-stories.md) ストーリー 1.3 より*

AI が以下の流れを取れること:

1. `collection_overview` で全体像を掴む（「未視聴が90件、漫画が87件」）
2. 利用者の希望を聞く
3. `search_library` で条件を絞って候補を取得する

そのため、**次にどう絞ればよいかが分かる粒度**の統計であること。

### 推測値を返さない 🔵

**信頼性**: 🔵 *US-09「未登録の属性を推測値として返さない」・REQ-144 より*

MCP は集計結果をそのまま返し、推薦や傾向分析を行わない。「あなたはSFが好きなようです」といった解釈は AI 側の仕事。

### 空と失敗の区別 🔵

**信頼性**: 🔵 *EDGE-002 より*

AI が「コレクションは空です」と「統計の取得に失敗しました」を言い分けられること。
