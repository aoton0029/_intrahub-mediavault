## タスク概要

視聴・読了・プレイ状況を1回の呼び出しで更新する。`status` / `consumed_date` / `rating` / `is_favorite` の4項目を扱う（PRD §15.1 で確定）。

**設計上の要点は2つ**:
- 対象は `item_id`（UUID）のみ。タイトル指定を受け付けない（REQ-142 / 設計決定 D-02）
- 更新前後の値を返す（REQ-051 / NFR-203）

## 実装詳細

### 1. ツール定義 🔵

**信頼性**: 🔵 *[mcp-tools.md](../design/mcp-tools.md) 6.・[interfaces.rs](../design/interfaces.rs) `UpdateConsumptionParams` より*

**実装ファイル**: `backend/mediavault-mcp/src/tools/update_consumption.rs`

| 引数 | 型 | 必須 |
|---|---|---|
| `item_id` | `Uuid` | ✔ 🔵 REQ-142 |
| `status` | `Option<ItemStatus>` | — 🔵 |
| `consumed_date` | `Option<NaiveDate>` | — 🔵 |
| `rating` | `Option<f32>` | — 🔵 |
| `is_favorite` | `Option<bool>` | — 🔵 |

- annotation: `readOnlyHint: false`、`destructiveHint: false` 🔵
- 説明文（AI向け）:
  > 視聴・読了・プレイの状況を記録する。`item_id` は `search_library` で**先に一意に特定**しておくこと。日付は `YYYY-MM-DD` に変換してから渡すこと（「昨日」などの表現は受け付けない）。

### 2. 型による安全性 🔵

**信頼性**: 🔵 *REQ-142 / 設計決定 D-02・受け入れ基準 TC-142-E01 より*

- `item_id` は `Uuid` 型。文字列を受け取らない
- **`title` / `query` などの引数を定義しない**。「タイトルでも指定できたら便利」という拡張を入れない
- `status` は `ItemStatus` enum。`on_hold` などの3値以外はスキーマ段階で拒否される（EDGE-106）🔵
- `consumed_date` は `NaiveDate`。`"昨日"` はデシリアライズ時点で失敗する（REQ-052）🔵

これらにより NFR-301（誤書き込み0件）が型レベルで保証され、テストは入力スキーマの列挙で機械的に検証できる。

### 3. 更新前の値の取得 🔵

**信頼性**: 🔵 *REQ-051・[dataflow.md](../design/dataflow.md) 機能5 ステップ2 より*

```
1. GET /api/v1/items/{id}     ← 更新前の値と title を取得
   → 404 なら更新せず not_found で終了（REQ-110）
2. PATCH /api/v1/items/{id}   ← 指定された項目のみ送る
3. before/after の差分を組み立てる
```

GET を1回追加するコストを払ってでも「更新前後を返す」ことを優先する（REQ-051 の明示要件）。

### 4. PATCH /items/{id} を使う 🔵

**信頼性**: 🔵 *`backend/mediavault-api/src/models/item.rs:225-236` の `UpdateItemRequest` 実装で確認済み*

`UpdateItemRequest` は `status` / `consumed_date` / `rating` / `is_favorite` の**4項目すべてを Optional で含む**。したがって1リクエストで完結する。

```rust
pub struct UpdateItemRequest {
    pub title: Option<String>,
    // ...
    pub status: Option<ItemStatus>,        // ← 含まれる
    pub consumed_date: Option<NaiveDate>,
    pub rating: Option<f32>,
    pub is_favorite: Option<bool>,
}
```

`PATCH /items/{id}/status`（`UpdateStatusRequest` = status必須 + consumed_date）は**使わない**。使うと `rating` / `is_favorite` に別リクエストが必要になり、REQ-050「1回の呼び出しで更新」に反するうえ部分失敗が発生する。

### 5. changes の組み立て 🔵

**信頼性**: 🔵 *REQ-051・[interfaces.rs](../design/interfaces.rs) `FieldChange` より*

```json
{
  "changes": [
    { "field": "status", "before": "in_progress", "after": "completed" },
    { "field": "consumed_date", "before": null, "after": "2026-08-06" }
  ]
}
```

**変化がなかったフィールドは含めない** 🟡 *[interfaces.rs](../design/interfaces.rs) の設計上の判断*

例: `is_favorite` が既に true で、`is_favorite: true` を指定した場合は `changes` に含めない。AI が「何が変わったか」だけを読めるようにするため。

### 6. rating の扱い 🟡

**信頼性**: 🟡 *EDGE-104・[prep.md](../spec/prep.md) PREP-10「api 仕様に記載がない」より*

MCP 側で範囲検証を**しない**。api のバリデーションに委ね、エラーをそのまま透過する（REQ-146）。

実データ上は 8.5 のような小数が使われている（[items.md](../../mediavault-api/items.md) のサンプル）。範囲が判明したらスキーマへ反映してよい。

## AIエージェント向け要件

### 一意に特定してから呼ぶ導線 🔵

**信頼性**: 🔵 *REQ-142・PRD §6 原則3 より*

- スキーマが `Uuid` のみを受け付けることで、AI は必ず `search_library` を経由する
- 説明文で「先に一意に特定しておくこと」と明示する
- 候補が複数のとき更新しないのは、AI 側の判断ではなく**構造的に不可能**であること

### 日付変換の責務 🔵

**信頼性**: 🔵 *REQ-052・PRD §5 US-05「自然言語の日付はMCPクライアントが解釈し、ツールには確定した日付を渡す」より*

「昨日見終わった」→ `2026-08-06` の変換は AI の仕事。説明文で明示し、エラーメッセージでも形式を示す。

### 変更内容の提示 🔵

**信頼性**: 🔵 *REQ-051・NFR-203・US-05「更新前後の値を返す」より*

AI が「『作品A』を視聴完了にしました（進行中 → 完了、評価 7.0 → 8.0）」と伝えられること。`title` と `changes` の両方が必要。

## 注意事項

- **`title` 引数を追加しないこと**。「ID を調べるのが面倒」という理由での追加は REQ-142 と NFR-301 を壊す。設計決定 D-02 は明示的な判断
- `PATCH /items/{id}` が4項目すべてを受け付けることは `models/item.rs:225-236` で確認済み。2本立てにする必要はない 🔵
- `status` の3値（`not_started` / `in_progress` / `completed`）は DB の ENUM 制約。「中断」「積読」といった状態は表現できない。利用者が求めた場合はタグで代替する（`organize_item`）🔵
- 更新前の GET を省略して `changes` を返さない実装にしないこと。REQ-051 は明示要件
