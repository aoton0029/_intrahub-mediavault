## 実装詳細

### 1. GitHub Actions ワークフロー 🔵

**信頼性**: 🔵 *[tech-stack.md](../tech-stack.md)「CI/CD: GitHub Actions（fmt → clippy → test → build）」より*

**実装ファイル**: `.github/workflows/` 配下

```yaml
- cargo fmt --check
- cargo clippy -p mediavault-mcp --all-targets -- -D warnings
- cargo test -p mediavault-mcp
- cargo build --release -p mediavault-mcp
```

**既存ワークフローとの関係を確認する** 🟡: mediavault-api 用のワークフローが既にある場合、workspace 全体を対象にするジョブへ統合するか、mcp 専用ジョブを追加するかを判断する。

**mediavault-mcp のテストは DB 不要** 🔵 *NFR-303・wiremock 方式（NFR-302）より*: mediavault-api のテストは PostgreSQL サービスコンテナを要するが、mcp は不要。ジョブを分けることで CI が速くなる。

### 2. DB 非依存チェック 🔵

**信頼性**: 🔵 *NFR-303・受け入れ基準 TC-NFR-303-01・TASK-0023 実装項目5 より*

```bash
if cargo tree -p mediavault-mcp | grep -q '^.*sqlx'; then
  echo "ERROR: mediavault-mcp must not depend on sqlx (NFR-303)"
  exit 1
fi
```

TASK-0023 で定義した検証を CI ジョブとして常設する。

**信頼性**: 🔵 *自宅インフラのドキュメント3層構造（設計/デバイス/ランブック）の規約より*

**実装ファイル**: リポジトリのランブック配置規約に従う 🟡

| 項目 | 内容 |
|---|---|
| 起動・停止・再起動 | compose コマンド 🔵 |
| ヘルスチェック | `/healthz` と MCPツール `health` の使い分け 🔵 |
| ログの見方 | `docker compose logs mediavault-mcp`、`RUST_LOG` の調整 🟡 |

**よくある障害と対処** 🟡:

| 症状 | 原因 | 対処 |
|---|---|---|
| コンテナが起動しない | `MCP_AUTH_TOKEN` 未設定 | `.env` を確認（REQ-122）|
| 全ツールが `MCP_API_UNREACHABLE` | api 停止 / URL誤り | `health` ツールで確認 → api を再起動 |
| クライアントが 401 | トークン不一致 | クライアント設定と `.env` を照合 |
| 外部検索が 422 | プロバイダAPIキー未設定 | MediaVault の設定画面で登録（PREP-06）|

- **既存の CI ワークフローを壊さないこと**。workspace にクレートを追加したことで、既存ジョブのビルド対象が変わる可能性がある

- 第2段階（`get_item_text` / jobs / stdio）は本タスクの範囲外。README に「将来提供予定」として記載するに留める 🔵
