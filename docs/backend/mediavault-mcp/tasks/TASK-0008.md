## タスク概要

MediaVault-api を呼び出す HTTP クライアント層を実装する。MCP のすべてのデータアクセスがこの層を通る。

3種のエラー分類（接続 / 認証 / 業務）を確立し、MediaVault-api の `code` と `message` を失わずに上位へ伝える（REQ-146）。

## 実装詳細

### 1. ApiEnvelope（レスポンス封筒）🔵

**信頼性**: 🔵 *`backend/mediavault-api/src/models/response.rs` の `ApiOk<T>` / `ApiError` 実装より*

**実装ファイル**: `backend/mediavault-mcp/src/api/envelope.rs`

MediaVault-api は成功時 `{"success": true, "data": T}`、失敗時 `{"success": false, "error": {"code", "message"}}` を返す。一覧系はさらに `pagination` を含む。

```rust
#[derive(Deserialize)]
#[serde(untagged)]
pub enum ApiEnvelope<T> {
    Ok { success: bool, data: T, pagination: Option<ApiPagination> },
    Err { success: bool, error: ApiErrorBody },
}
```

**`untagged` の落とし穴** 🟡

**信頼性**: 🟡 *serde の仕様から導かれる実装上の注意*

`untagged` はバリアントを順に試すため、`T` が緩い型（`serde_json::Value` など）だと `Err` のJSONが `Ok` として通ってしまう。`success` フィールドで先に分岐する実装（一度 `Value` で受けて `success` を見る、またはカスタム `Deserialize`）のほうが安全。実装時に検証する。

### 2. ApiClientError 🔵

**信頼性**: 🔵 *[interfaces.rs](../design/interfaces.rs)・[architecture.md](../design/architecture.md) エラー分類表・REQ-120 より*

**実装ファイル**: `backend/mediavault-mcp/src/api/error.rs`

| バリアント | 発生条件 | 上位での扱い |
|---|---|---|
| `Connection(String)` | 接続失敗・タイムアウト・DNS失敗 | `MCP_API_UNREACHABLE`、`retriable: true` 🔵 |
| `Auth` | 内部API呼び出しで 401 | `MCP_INTERNAL_AUTH_FAILED`、`retriable: false` 🔵 |
| `Api { code, message, status }` | api の業務エラー | code/message をそのまま透過 🔵 REQ-146 |
| `Decode(String)` | デシリアライズ失敗 | 🟡 実装上必要な分類 |

**`Auth` バリアントに値を含めない** 🔵

**信頼性**: 🔵 *REQ-145「APIキーをログに出力してはならない」より*

`#[error("内部APIの認証に失敗しました")]` とし、キー値やヘッダー内容を一切含めない。

### 3. HTTPクライアント 🔵

**信頼性**: 🔵 *[architecture.md](../design/architecture.md) ApiClient層・NFR-006 より*

**実装ファイル**: `backend/mediavault-mcp/src/api/client.rs`

```rust
pub struct ApiClient {
    http: reqwest::Client,      // コネクションプールを保持
    base_url: Url,
    internal_api_key: SecretString,
}
```

- `reqwest::Client` は単一インスタンスを `Arc` で共有する（コネクションプール再利用）🔵
- タイムアウト: 接続3秒 / 全体15秒。外部カタログ検索用に30秒の別メソッドを用意する 🟡 *[architecture.md](../design/architecture.md) より*

**提供するメソッド** 🔵

**信頼性**: 🔵 *REQ-141「削除ツールを公開しない」を層レベルで担保する設計判断（[architecture.md](../design/architecture.md) アーキテクチャ制約）より*

```rust
pub async fn get<T: DeserializeOwned>(&self, path: &str, query: &[(&str, String)]) -> Result<ApiResponse<T>, ApiClientError>;
pub async fn post<B: Serialize, T: DeserializeOwned>(&self, path: &str, body: &B) -> Result<T, ApiClientError>;
pub async fn post_empty<T: DeserializeOwned>(&self, path: &str) -> Result<T, ApiClientError>;
pub async fn patch<B: Serialize, T: DeserializeOwned>(&self, path: &str, body: &B) -> Result<T, ApiClientError>;
```

**`delete` は実装しない**。誤って削除系ツールが作られることを型レベルで防ぐ。

### 4. 内部APIの識別 🔵

**信頼性**: 🔵 *NFR-103・`backend/mediavault-api/src/routes/internal.rs` のパス（`/api/v1/internal/*`）より*

パスが `/api/v1/internal/` で始まる場合のみ `Authorization: Bearer {INTERNAL_API_KEY}` を付与する。公開API（`/api/v1/*`）には付けない（api 側が無認証のため不要であり、送る意味がない）🟡

### 5. リトライ方針 🟡

**信頼性**: 🟡 *[architecture.md](../design/architecture.md) 可用性「冪等な GET のみ最大1回」より*

- GET: 接続エラー時のみ1回リトライ
- POST / PATCH: **リトライしない**（二重登録防止）

### 6. ページネーション情報の伝搬 🔵

**信頼性**: 🔵 *[items.md](../../mediavault-api/items.md) の pagination 仕様・REQ-130 より*

`get` の戻り値を `ApiResponse<T> { data: T, pagination: Option<ApiPagination> }` とし、上位（TASK-0013）でカーソルへ変換できるようにする。

## 注意事項

- **`api/models.rs` には必要なレスポンス型だけを定義する**。mediavault-api の全型を写経しない。ツール実装（Phase 2・3）で必要になった時点で追加する 🟡
- `api-client-lib` は外部カタログ（Jikan/TMDb 等）専用であり、MediaVault-api 自身のクライアントは持たない。本タスクで自前実装する 🔵 *[tech-stack.md](../tech-stack.md)「api-client-lib との関係」より*
- **`delete` メソッドを追加しないこと**。REQ-141 を層レベルで担保する設計であり、後続タスクで「必要になったから」と追加してはならない
- wiremock のテストは Phase 2・3 の全ツールテストの基盤になる。共通のフィクスチャ（モック起動、`ApiClient` 構築）を `tests/common/mod.rs` へ切り出す 🟡
