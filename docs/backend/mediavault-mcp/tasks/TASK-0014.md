## タスク概要

1つの Item について、詳細・関連情報をまとめて取得する。9本の api 呼び出しを**並列に合成**し、1回のツール呼び出しで作品コンテキストを返す（NFR-002）。

集約APIを新設せず MCP 側で合成する（設計決定 D-05、PRD §15.2 の残課題を解消した決定）。

**このツールの要点は「未登録」と「取得失敗」を区別すること**（REQ-021）。9本のうち一部が失敗しても、取得できた情報は返す。

## 実装詳細

### 1. ツール定義 🔵

**信頼性**: 🔵 *[mcp-tools.md](../design/mcp-tools.md) 2. get_item_context より*

**実装ファイル**: `backend/mediavault-mcp/src/tools/get_item_context.rs`

- 引数: `item_id: Uuid` のみ 🔵
- annotation: `readOnlyHint: true` 🔵
- 説明文（AI向け）:
  > 1つの作品について、詳細・タグ・カテゴリ・ファイル・リンク・関連作品・スタッフ・キャストなどをまとめて取得する。作品について詳しく答える前に呼ぶこと。

### 2. 並列合成 🔵

**信頼性**: 🔵 *設計決定 D-05・NFR-005・[dataflow.md](../design/dataflow.md) 機能2 より*

**実装ファイル**: `backend/mediavault-mcp/src/services/context.rs`

**必須（1本）**:

| エンドポイント | 取得内容 |
|---|---|
| `GET /api/v1/items/{id}` | Item本体 + detail + タグ + カテゴリ + 配信リンク + 画像 + Calibre連携 🔵 |

**追加（8本、並列）**:

| エンドポイント | セクション |
|---|---|
| `GET /items/{id}/relations` | `relations` 🔵 |
| `GET /items/{id}/mylists` | `mylists` 🔵 |
| `GET /items/{id}/groups` | `groups` 🔵 |
| `GET /items/{id}/cast` | `cast` 🔵 |
| `GET /items/{id}/staff` | `staff` 🔵 |
| `GET /items/{id}/files` | `files` 🔵 |
| `GET /items/{id}/links` | `links` 🔵 |
| `GET /items/{id}/trailers` | `trailers` 🔵 |

**タグ・カテゴリ・配信リンク・画像を追加取得しない** 🔵

**信頼性**: 🔵 *PRD §8「`GET /api/v1/items/{id}` は既に detail、タグ、カテゴリ、配信リンク、画像、Calibre連携を返すため、追加呼び出しは関連・マイリスト・グループ・キャスト・ファイル・リンク・トレーラーに限られる」より*

### 3. try_join! を使わない 🔵

**信頼性**: 🔵 *設計決定 D-05「1つが失敗しても他を返すため、try_join! は使わない」より*

```rust
let (relations, mylists, groups, cast, staff, files, links, trailers) = futures::join!(
    client.get_relations(id),
    client.get_mylists(id),
    // ...
);
```

`futures::join!` は各結果を独立した `Result` で保持する。`try_join!` は最初の失敗で全体を打ち切るため要件（REQ-021）を満たせない。

### 4. Section への変換 🔵

**信頼性**: 🔵 *REQ-021・EDGE-105・TASK-0009 の `Section<T>` より*

| api の結果 | `Section` |
|---|---|
| `Ok(items)` かつ非空 | `Loaded { items }` |
| `Ok(items)` かつ空 | `Empty`（**未登録**）|
| `Err(...)` | `Failed { error }`（**取得失敗**）|

この区別が REQ-021 の中核。空配列を `Loaded { items: [] }` にしてはならない。

### 5. outcome の決定 🔵

**信頼性**: 🔵 *[dataflow.md](../design/dataflow.md) 機能2 ステップ4 より*

| 条件 | `outcome` |
|---|---|
| `GET /items/{id}` が 404 | `not_found`（他は返さない）🔵 |
| `GET /items/{id}` がその他のエラー | `error` 🟡 |
| 8本すべて成功 | `success` 🔵 |
| 8本のうち1件以上 `Failed` | `partial` 🔵 |

### 6. 関係の向き 🔵

**信頼性**: 🔵 *REQ-072・[interfaces.rs](../design/interfaces.rs) `RelationDirection` より*

`GET /items/{id}/relations` の各行について、対象 Item が `item_id` 側なら `outgoing`、`related_item_id` 側なら `incoming` を付ける。

**api のレスポンス形式を確認する** 🟡: [item-relations.md](../../mediavault-api/item-relations.md) が双方向の関係を返すか、片方向のみかで実装が変わる。

### 7. 関連作品の ItemSummary 化 🟡

**信頼性**: 🟡 *[interfaces.rs](../design/interfaces.rs) `RelationView.related_item: ItemSummary` より*

`GET /items/{id}/relations` が関連先の Item 情報を含まない場合、追加取得が必要になる。含む場合は追加呼び出し不要。

**追加取得が必要な場合の方針** 🟡: 関連が多いと呼び出しが膨らむため、`item_id` と `title` のみ返して詳細は返さない縮退案も検討する。NFR-002（1回で完結）を優先する。

## AIエージェント向け要件

### 未登録と取得失敗の区別 🔵

**信頼性**: 🔵 *REQ-021・US-02「情報が未登録なのか、取得に失敗したのかを区別できる」より*

AI が以下を言い分けられること:

- `empty` → 「この作品にはファイルが登録されていません」
- `failed` → 「ファイル情報の取得に失敗しました。もう一度お試しください」

前者を後者のように伝えると利用者を混乱させるため、スキーマ上で明確に分ける。

### detail の扱い 🔵

**信頼性**: 🔵 *[items.md](../../mediavault-api/items.md)「details は型定義された共通スキーマを持たない」・[interfaces.rs](../design/interfaces.rs) より*

`detail` は media_type ごとに形が異なる自由形式JSON。**加工せずそのまま渡す**。MCP 側で正規化しようとしないこと（形が保証されていないため）。

### レスポンスサイズ 🟡

**信頼性**: 🟡 *PRD §11「1回のツール結果へ全量を詰め込まない」から導かれる注意*

関連作品・キャストが極端に多い Item ではレスポンスが膨らむ。上限を設けるか検討する。ただし REQ-143（一覧系の20/50）は検索ツール向けの規定であり、コンテキスト取得には直接適用されない。実データで確認してから判断する。

## 注意事項

- **`try_join!` を使わないこと**。便利に見えるが REQ-021 を壊す
- **空配列を `Empty` に落とすこと**。`Loaded { items: [] }` は「未登録」の意味を失う
- 8本の並列呼び出しは MediaVault-api に同時負荷をかける。単一ユーザー環境では問題ないが、api 側のコネクションプール設定を確認しておく 🟡
- 関連作品の詳細情報が `GET /items/{id}/relations` に含まれるかを実装前に確認する。含まれない場合、追加取得で呼び出し数がさらに増える 🟡
- 将来 `GET /items/{id}/context` の集約APIを実装する余地は残っている（PRD §8）。性能・一貫性に問題が出たら再検討する
