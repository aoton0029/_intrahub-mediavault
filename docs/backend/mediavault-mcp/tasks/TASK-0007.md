## タスク概要

`/mcp` エンドポイントに静的 Bearer トークン認証を適用する tower ミドルウェアを実装する。比較は `subtle` による定数時間比較とし、タイミング攻撃を防ぐ。

`/healthz` はコンテナ死活監視用として認証対象外にする。MediaVault-api の状態に依存させないことで、api 障害時にコンテナが再起動ループへ陥るのを防ぐ。

## 実装詳細

### 1. 認証ミドルウェア 🔵

**信頼性**: 🔵 *[architecture.md](../design/architecture.md) 認証層・NFR-101 / NFR-102 より*

**実装ファイル**: `backend/mediavault-mcp/src/auth.rs`

```rust
pub async fn bearer_auth(
    State(config): State<Arc<Config>>,
    req: Request,
    next: Next,
) -> Result<Response, StatusCode> {
    let provided = req
        .headers()
        .get(AUTHORIZATION)
        .and_then(|v| v.to_str().ok())
        .and_then(|v| v.strip_prefix("Bearer "));

    match provided {
        Some(token) if constant_time_eq(token, config.auth_token.expose()) => {
            Ok(next.run(req).await)
        }
        _ => Err(StatusCode::UNAUTHORIZED),
    }
}
```

**既存 api との差異** 🔵

**信頼性**: 🔵 *[design-interview.md](../design/design-interview.md) 事前調査より*

| 項目 | 既存 `api_key_auth.rs` | 本タスク |
|---|---|---|
| 比較方式 | `==` による通常比較 | `subtle::ConstantTimeEq` 🔵 NFR-102 |
| 生キー形式の許容 | `Bearer ` なしも許容 | **`Bearer ` 必須** 🟡 |
| 未設定時 | 常に401 | 起動時に失敗（TASK-0006）🔵 REQ-122 |

生キー形式を許容しない理由 🟡: MCP クライアントは標準的に `Bearer` を付ける。許容範囲を狭めることで実装と検証を単純にする。

### 2. 定数時間比較 🔵

**信頼性**: 🔵 *NFR-102・[tech-stack.md](../tech-stack.md) より*

```rust
use subtle::ConstantTimeEq;

fn constant_time_eq(a: &str, b: &str) -> bool {
    a.as_bytes().ct_eq(b.as_bytes()).into()
}
```

**長さの差異について** 🟡

**信頼性**: 🟡 *`subtle` の仕様から導かれる実装上の注意*

`ct_eq` はスライス長が異なると即座に false を返すため、長さは漏れる。トークン長は秘密ではないため実務上問題ないが、より厳密にするならハッシュ値同士を比較する方法もある。本実装では長さ漏洩を許容する。

### 3. ルーター構成 🔵

**信頼性**: 🔵 *NFR-104「/healthz のみ認証対象外」より*

**実装ファイル**: `backend/mediavault-mcp/src/main.rs`

```rust
let protected = Router::new()
    .nest_service("/mcp", mcp_service)          // TASK-0009 で実装
    .layer(middleware::from_fn_with_state(config.clone(), bearer_auth));

let app = Router::new()
    .route("/healthz", get(healthz))            // 認証なし
    .merge(protected)
    .with_state(config);
```

認証ミドルウェアを `/healthz` に**かけない**構成にすることが要点。全体に `layer` を適用してからパスで除外する方式は取らない（除外漏れのリスクがあるため）🟡

### 4. /healthz ハンドラ 🔵

**信頼性**: 🔵 *[architecture.md](../design/architecture.md) 可用性・[mcp-tools.md](../design/mcp-tools.md) より*

**実装ファイル**: `backend/mediavault-mcp/src/main.rs`

MCPプロセス自身の生存のみを返す。MediaVault-api へは**アクセスしない**。

```json
{ "status": "ok", "version": "0.1.0" }
```

**MCPツール `health` との違い** 🔵

**信頼性**: 🔵 *[mcp-tools.md](../design/mcp-tools.md)「/healthz と MCPツール health を分離」より*

| | `/healthz` | MCPツール `health` |
|---|---|---|
| 認証 | 不要 | 必須 |
| api への到達確認 | しない | する |
| 用途 | コンテナ死活監視 | 障害切り分け（TASK-0010）|

### 5. ログ出力 🔵

**信頼性**: 🔵 *REQ-145・[architecture.md](../design/architecture.md) セキュリティ より*

401 発生時は `tracing::warn!` でパスと発生時刻のみを記録する。ヘッダー値・トークン・リクエストボディは記録しない。

## 注意事項

- **`rmcp` の `StreamableHttpService` と axum ミドルウェアの組み合わせ方は TASK-0005 で確認済みの前提**。`nest_service` で包めない場合は `Router::layer` の適用位置を調整する 🟡
- **MCP のセッション管理と認証の関係**: Streamable HTTP はセッションIDを使う場合がある。初回リクエストで認証すればセッション継続中は再検証不要か、毎リクエスト検証が必要かを `rmcp` の実装で確認する。安全側に倒し、**毎リクエスト検証**を既定とする 🟡
- MediaVault-api の公開APIは無認証であるため、この認証が AIエージェント経路における唯一の関門になる（[note.md](../spec/note.md) 注意事項）🔵
- リバースプロキシ側では認証を終端しない（内部経路がプロキシをバイパスするため）🔵 *PRD §10 仮決定より*
