### 1. ItemSummary への縮約 🔵

**信頼性**: 🔵 *設計決定 D-04（ヒアリング2026-08-07 Q4）・[interfaces.rs](../design/interfaces.rs) より*

**実装ファイル**: `backend/mediavault-mcp/src/result/mod.rs` または `src/api/models.rs`

| `ItemSummary` フィールド | 由来 | 備考 |
|---|---|---|
| `item_id` | `Item.id` | 🔵 |
| `title` | `Item.title` | 🔵 |
| `original_title` | `Item.original_title` | 同名作品の判別用（REQ-012）🔵 |
| `media_type` | `Item.media_type` | 🔵 |
| `release_year` | `Item.release_date` の年 | フル日付から縮約 🟡 |
| `status` | `Item.status` | 🔵 |
| `rating` | `Item.rating` | 🔵 |
| `is_favorite` | `Item.is_favorite` | 🔵 |
| `tags` | `ItemWithRefs.tags` の `name` のみ | ID を落とす 🟡 |

**含めないもの** 🔵

**信頼性**: 🔵 *設計決定 D-04「description や details は含めない」より*

`description` / `details` / `cover_image_url` / `homepage_url` / `external_id` / `source` / `created_at` / `updated_at` / `categories`。

**`ItemWithRefs` を持たない場面** 🟡

**信頼性**: 🟡 *`POST /items` などが `Item`（tags なし）を返すことから導かれる*

`create_item` / `import_external_item` は `Item` のみを受け取る。`tags` が取得できない場合は空配列にする変換も用意する。

### 2. 名前解決サービス 🔵

**信頼性**: 🔵 *REQ-060・PRD §8「タグ・カテゴリはID指定のため、MCPが名前から解決する」より*

**実装ファイル**: `backend/mediavault-mcp/src/services/resolve.rs`

```rust
pub enum Resolution {
    Found(NamedRef),
    NotFound { requested: String, available: Vec<String> },
}

pub struct MasterResolver { /* 呼び出し内メモ化 */ }

impl MasterResolver {
    pub async fn resolve_tag(&mut self, name: &str) -> Result<Resolution, ApiClientError>;
    pub async fn resolve_category(&mut self, name: &str) -> Result<Resolution, ApiClientError>;
    pub async fn resolve_mylist(&mut self, name: &str) -> Result<Resolution, ApiClientError>;
}
```

対応する api: `GET /api/v1/tags` / `GET /api/v1/categories` / `GET /api/v1/mylists` 🔵

### 3. 名前の照合ルール 🟡

**信頼性**: 🟡 *[dataflow.md](../design/dataflow.md) 機能4「前後空白除去 + 完全一致（大文字小文字は区別する）」より*

- 前後の空白を除去してから比較する
- **完全一致**。部分一致は採用しない（「積読」で「積読候補」に付与されると事故になる）
- 大文字小文字は区別する（日本語のタグが主であり、区別しないことの利得が小さい）

これらは要件に明記がないため、実装時に見直してもよい。ただし部分一致への変更は誤付与のリスクがあるため避ける。

### 4. キャッシュしない方針 🔵

**信頼性**: 🔵 *[architecture.md](../design/architecture.md) 状態管理「名前→ID解決はキャッシュしない」より*

- **呼び出しをまたぐキャッシュを持たない**。Web UI など別経路で作られたタグを取りこぼすと、REQ-111 の「候補なし」が誤答になる
- **1回の呼び出し内ではメモ化する**。`organize_item` で3つのタグを解決するとき、`GET /tags` は1回で済ませる

`MasterResolver` をツール呼び出しごとに生成し、呼び出し終了で破棄することでこれを実現する 🟡

### 5. 候補名の提示 🟡

**信頼性**: 🟡 *[interfaces.rs](../design/interfaces.rs) `OperationResult::NotResolved` の `available_names`「参考として提示する既存の候補名（上位数件）」より*

解決できないとき、既存のマスタ名を返して AI が次の手を打てるようにする。全件返すとレスポンスが膨らむため、上位10件程度に制限する。

**類似名の優先** 🟡: 完全一致しない場合でも、部分一致・前方一致するものを優先して候補に含めると AI が誤字に気付きやすい。実装時に判断してよい。

## 注意事項

- **キャッシュを「性能改善のため」と後から入れないこと**。設計上の明示的な判断であり、入れると REQ-111 の意味が壊れる（[architecture.md](../design/architecture.md) 状態管理）
- 名前の照合を部分一致にしないこと。誤付与は REQ-113（冪等性）では防げない
- `ItemSummary` に「あとで必要になりそうだから」とフィールドを足さないこと。設計決定 D-04 はレスポンスサイズ抑制が目的
- `GET /mylists` のレスポンス形式は [mylists.md](../../mediavault-api/mylists.md) を確認する。タグ・カテゴリと同形とは限らない 🟡
