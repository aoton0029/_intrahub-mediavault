## 実装詳細

### 1. 誤書き込み0件の機械的検証 🔵

**信頼性**: 🔵 *NFR-301・受け入れ基準 TC-NFR-301-01「書き込み系ツールの入力スキーマを列挙し、対象指定引数が UUID 型のみであることを検証」より*

**実装ファイル**: `backend/mediavault-mcp/tests/safety.rs`

`tools/list` から書き込み系ツール（`readOnlyHint: false`）を抽出し、各ツールの `inputSchema` を検査する。

```
検証内容:
- 対象を指す引数（item_id / related_item_id）が string + format: uuid であること
- title / query / name のような、Item を特定しうる自由文字列引数が存在しないこと
```

**この検証が NFR-301 の実装**。設計決定 D-02（書き込みは UUID のみ）が守られていることを、個別ツールのテストではなく横断的に保証する。

**許容する文字列引数** 🟡: `organize_item` の `tags` / `categories` / `mylists`、`create_item` の `title`、`add_access_link` の `label` / `platform` は Item を特定するものではないため許容する。除外リストを明示的に持ち、新しい文字列引数が増えたらテストが落ちるようにする。

### 2. 破壊的ツールの非公開検証 🔵

**信頼性**: 🔵 *REQ-141・受け入れ基準 TC-REQ-141-01 より*

`tools/list` の結果に、以下のパターンに該当するツール名が存在しないことを検証する。

```
delete_* / remove_* / detach_* / unlink_* / *_delete
update_api_key / set_api_key
move_file / rename_file
```

**さらに `destructiveHint: true` のツールが1つもないこと**を検証する 🟡。

### 3. ApiClient に DELETE がないことの検証 🔵

**信頼性**: 🔵 *[architecture.md](../design/architecture.md) アーキテクチャ制約・TASK-0008 より*

`ApiClient` に `delete` メソッドが存在しないことを、コンパイル時または全ツール実行時の wiremock 検証で担保する。

**実装方針** 🟡: すべての統合テストで共通のモックを使い、テスト終了時に「DELETE リクエストを1件も受け取っていない」ことを確認するヘルパを用意する。

### 4. 秘密情報の非露出検証 🔵

**信頼性**: 🔵 *REQ-145・受け入れ基準 TC-NFR-103-01 / TC-NFR-103-02 より*

**全11ツール**を実行し、結果のJSONに以下が含まれないことを検証する。

- `MCP_AUTH_TOKEN` の値
- `INTERNAL_API_KEY` の値

テストでは識別しやすい特徴的な値（例: `"SECRET-TOKEN-DO-NOT-LEAK"`）を設定し、全レスポンスを文字列検索する 🟡。

**ログについても同様に検証する** 🔵: `tracing` の出力を捕捉し、成功時・失敗時ともにトークンが含まれないことを確認する。

### 5. DB非依存の検証 🔵

**信頼性**: 🔵 *NFR-303・受け入れ基準 TC-NFR-303-01 より*

```bash
cargo tree -p mediavault-mcp | grep -q sqlx && exit 1 || exit 0
```

CI のジョブとして実行する（TASK-0026 で組み込む）🟡。

**あわせて検証するもの** 🟡: `tokio-postgres` / `diesel` など他の DB クライアント、embedding 生成系ライブラリ（REQ-144）も含まれないこと。

### 6. 書き込み結果の検証可能性 🔵

**信頼性**: 🔵 *NFR-203・PRD §12「書き込み結果の100%で対象Item IDと変更内容を確認できる」より*

全書き込みツールを成功パスで実行し、結果に以下が含まれることを検証する。

| ツール | 必須フィールド |
|---|---|

### 7. 認証の横断検証 🔵

## AIエージェント向け要件

### 一貫した安全性 🔵

**信頼性**: 🔵 *PRD §6 原則3・§10 より*

11ツールのうち1つでも例外があると、AI はその抜け道を使いうる。**横断検証は「例外がないこと」を保証する**ことに意味がある。

新しいツールが追加されたとき、このテストが自動的に検査対象へ含めるよう、`tools/list` から動的に取得する実装にする 🟡。ツール名のハードコードリストを持つと、追加時に検査漏れが起きる。

## 注意事項

- **ツール名のハードコードを避ける**。`tools/list` から動的に取得し、将来ツールが増えても自動的に検査対象になるようにする
- **このテストが落ちたら実装を直す。テストを緩めない**。安全性要件は PRD §12 の成功指標であり、達成できないなら設計へ差し戻す
- 秘密情報の検索は部分文字列マッチで行う。トークンをBase64などで変形して出力していないかまでは検出できない点は限界として認識する 🟡
- REQ-144（ナレッジ生成しない）の検証は自動化が難しい。依存チェック + コードレビューの併用とし、限界を明示する 🟡
