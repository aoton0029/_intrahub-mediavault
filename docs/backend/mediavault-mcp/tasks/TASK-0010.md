## タスク概要

最初の MCP ツールとして `health` を実装する。MediaVault-api への到達性と応答時間、MCP 自身のバージョンを返す。

機能的に最も単純なツールであるため、**TASK-0009 で作った土台が実際に動くことを検証する役割**を兼ねる。ここで確立するツール実装のパターン（Tool層 → Service層 → ApiClient層、テストの書き方）を Phase 2・3 が踏襲する。

### 2. Service層 🔵

**信頼性**: 🔵 *REQ-100・[architecture.md](../design/architecture.md) レイヤ構成より*

**実装ファイル**: `backend/mediavault-mcp/src/services/health.rs`

**確認範囲を限定する** 🔵

**信頼性**: 🔵 *ヒアリング（requirements フェーズ Q8）「api到達性 + MCP自身のバージョン」より*

以下は**確認しない**。範囲を広げないこと。

- 内部APIキーの有効性（`/api/v1/internal/*` を叩かない）
- 外部APIキーの設定状況（`GET /settings/api-keys` を叩かない）

外部APIキー未設定は `search_external_catalog` 実行時の 422 で検知する方針に一本化している（REQ-117）。

### 3. api 停止時もツールは成功させる 🔵

**信頼性**: 🔵 *EDGE-001・受け入れ基準 TC-100-E01「api が停止していてもツール自体は Success を返す」より*

```json
{
  "outcome": "success",
  "mcp_version": "0.1.0",
  "api": {
    "reachable": false,
    "latency_ms": null,
    "error": { "code": "MCP_API_UNREACHABLE", "message": "...", "retriable": true }
  }
}
```

診断ツールとして機能させるため、`ApiClientError::Connection` を**ツール全体のエラーに昇格させない**。他のツールとは扱いが異なる点に注意する。

## AIエージェント向け要件

### 障害切り分けに使える情報 🔵

**信頼性**: 🔵 *[mcp-tools.md](../design/mcp-tools.md) のツール説明文より*

- `reachable` が false のとき、AI が「MediaVault が動いていない」と利用者へ説明できる情報が揃っていること
- `retriable: true` により、AI が「しばらく待って再試行する」判断を下せること
- **api の内部エラー（500）と接続不能を区別できること**。前者は「MediaVault は動いているが不調」、後者は「MediaVault が起動していない」であり、利用者への案内が変わる 🟡

## 注意事項

- **`health` は例外的に、接続失敗をツールのエラーにしない**。他のツール（Phase 2・3）は接続失敗を `outcome: error` にする。この違いを実装時に取り違えないこと
- 本タスクで確立するパターン（Tool層の薄さ、Service層への委譲、wiremock テストの書き方）が Phase 2・3 のテンプレートになる。**急いで雑に作らない**
- タイムアウトは通常のリクエストタイムアウト（15秒）をそのまま使う。診断用途なので短くしたくなるが、「遅い」ことも診断情報として有用 🟡
- 依存サービス（worker / KnowledgeHub）の状態確認は範囲外。PRD §7.1 の「依存サービス状態」はヒアリングで api 到達性に限定された 🔵
