## タスク概要

外部データベースに存在しない作品（同人誌・個人資料・ローカルファイル）を手動登録する。Item 作成に加え、ファイルパス・URL・タグ・マイリストを同じ呼び出しで関連付ける（REQ-041）。

**部分失敗の表現が要件の中核**（REQ-114 / EDGE-004）。Item 作成後の関連付けが失敗しても、作成済み Item ID を必ず返す。

## 実装詳細

### 1. ツール定義 🔵

**信頼性**: 🔵 *[mcp-tools.md](../design/mcp-tools.md) 5. のパラメータ表・[interfaces.rs](../design/interfaces.rs) `CreateItemParams` より*

**実装ファイル**: `backend/mediavault-mcp/src/tools/create_item.rs`

- annotation: `readOnlyHint: false`、`destructiveHint: false` 🔵
- 説明文（AI向け）:
  > 外部データベースに存在しない作品（同人誌・個人資料・ローカルファイルなど）を手動で登録する。外部で見つかる作品は `search_external_catalog` → `import_external_item` を使うこと。

### 2. 実行順序 🔵

**信頼性**: 🔵 *[dataflow.md](../design/dataflow.md) 機能5・EDGE-004 より*

```
1. POST /api/v1/items                    ← 必須。失敗したら全体を error で終了
2. 以降を順に実行（失敗しても続行）:
   - ファイルパス   → POST /items/{id}/files
   - URL           → POST /items/{id}/links
   - タグ名        → 名前解決 → POST /items/{id}/tags/{tag_id}
   - マイリスト名  → 名前解決 → POST /mylists/{id}/items
```

Item 作成が失敗した場合、後続は実行せず `outcome: error`、`item: null` で返す 🔵

### 3. 部分失敗の記録 🔵

**信頼性**: 🔵 *REQ-114・EDGE-004・TASK-0009 の `OperationResult` より*

各関連付けの結果を `OperationResult` で記録する。

| 状況 | `OperationResult` |
|---|---|
| 付与成功 | `Applied { created_new }` |
| 名前が解決できず `create_if_missing` 未指定 | `NotResolved { available_names }` |
| 付与失敗 | `Failed { error }` |
| 先行失敗により未実行 | `Skipped` 🟡 |

**全体の `outcome`** 🔵: TASK-0009 の集約ヘルパで決定する。Item 作成に成功していれば最低でも `partial`（`error` にはしない）🟡

### 4. ロールバックしない 🔵

**信頼性**: 🔵 *[dataflow.md](../design/dataflow.md)「データ整合性の保証」・REQ-141 より*

関連付けが失敗しても、作成済み Item を削除しない。理由:

- 補償トランザクションには削除系 API の呼び出しが必要で、REQ-141「削除系を公開しない」と矛盾する
- 補償自体が失敗しうる
- REQ-114 は「成功したように見せない」であって「なかったことにする」ではない

**作成済み Item ID を必ず返す**ことで、利用者・AI が状況を把握して手動で補正できる（EDGE-004）。

### 5. ファイルパスの扱い 🟡

**信頼性**: 🟡 *[item-files.md](../../mediavault-api/item-files.md)・[tech-stack.md](../../tech-stack.md) のファイルストレージ設計から導かれる*

`file_paths` は**実データ領域の絶対パス**（`/srv/anime` など）を想定する。アップロード（`POST /items/{id}/files/upload`）は行わない。

- MCP はファイルの実在を確認しない（ファイルシステムへアクセスしない）
- api 側のバリデーションに委ねる
- `POST /items/{id}/files` のリクエスト形式を [item-files.md](../../mediavault-api/item-files.md) で確認する 🟡

### 6. URL のバリデーション 🔵

**信頼性**: 🔵 *REQ-116（`add_access_link` と同じ規約）より*

`url` クレートでパースし、スキームが `http` / `https` であることを確認する。不正なURLは登録せず `Failed` として記録する 🟡

### 7. create_if_missing 🔵

**信頼性**: 🔵 *REQ-111・[interfaces.rs](../design/interfaces.rs)「organize_item と同一の規約を適用」より*

既定 false。`organize_item`（TASK-0020）と同じ意味・同じ既定値にする。ツール間で規約がぶれると AI が混乱する。

## AIエージェント向け要件

### 部分失敗の伝わりやすさ 🔵

**信頼性**: 🔵 *REQ-114・US-04「成功した操作と失敗した操作が分かる」より*

AI が利用者へ以下のように伝えられること:

> 「作品を登録しました（ID: xxx）。タグ『同人』の付与に失敗したので、あとで `organize_item` で付け直せます。」

そのため、`item_id` と各操作の結果が同一レスポンスに揃っている必要がある。

### 手動登録と外部登録の使い分け 🔵

**信頼性**: 🔵 *NFR-202・US-04 / US-03 より*

説明文で「外部で見つかる作品は `import_external_item` を使う」と案内し、AI が手動登録を安易に選ばないようにする。手動登録はメタデータが乏しくなるため。

### 再実行の安全性 🟡

**信頼性**: 🟡 *PRD §6 原則6 から導かれるが、`create_item` の冪等性は要件に明記がない*

**このツールは冪等ではない**。同じ引数で2回呼ぶと Item が2件作られる。api 側に手動作成 Item の重複判定がないため。

AI が失敗時に安易な再実行をしないよう、説明文または結果で「既に作成済みの可能性」を判断できる情報（`item_id`）を返すことが重要。

## 注意事項

- **ロールバックを実装しないこと**。「失敗したら綺麗にしたい」という発想は自然だが、REQ-141 と衝突し、補償自体が失敗しうる
- **`create_item` は冪等ではない**。他のツール（`organize_item` / `relate_items` / `add_access_link`）が冪等であるのと対照的。接続エラー時に AI が再実行すると重複が生まれる。この制約を説明文に含めるか検討する 🟡
- 名前解決とタグ付与のロジックは `organize_item`（TASK-0020）と重複する。**TASK-0020 で共通化する前提で実装する**か、本タスクで先に共通サービスへ切り出す。後者が望ましい 🟡
- `POST /items/{id}/files` のリクエスト形式（パスの相対／絶対、必須フィールド）を [item-files.md](../../mediavault-api/item-files.md) で確認する 🟡
