## タスク概要

2つの Item を関係種別付きで関連付ける。原作と映像化、続編、DLC などをメディアをまたいで辿れるようにする（US-07）。

**要点は関係の向きの明示**（REQ-072）。`item_id` が起点、`related_item_id` が終点であり、種別ごとに意味が異なる。AI と利用者が向きを取り違えると、原作と映像化が逆に登録される。

## 実装詳細

### 1. ツール定義 🔵

**信頼性**: 🔵 *[mcp-tools.md](../design/mcp-tools.md) 8.・[interfaces.rs](../design/interfaces.rs) `RelateItemsParams` より*

**実装ファイル**: `backend/mediavault-mcp/src/tools/relate_items.rs`

| 引数 | 型 | 説明 |
|---|---|---|
| `item_id` | `Uuid`（必須）| 関係の**起点** 🔵 |
| `related_item_id` | `Uuid`（必須）| 関係の**終点** 🔵 |
| `relation_type` | `RelationType`（必須）| 固定6種 🔵 REQ-071 |

- annotation: `readOnlyHint: false`、`destructiveHint: false` 🔵
- 説明文（AI向け）:
  > 2つの作品を関係づける。両方の `item_id` を `search_library` で先に特定しておくこと。関係には向きがあり、`item_id` が起点、`related_item_id` が終点になる。

### 2. 関係種別と向きの定義 🔵

**信頼性**: 🔵 *REQ-072・[mcp-tools.md](../design/mcp-tools.md) の関係種別表・PRD §15.1 より*

| 値 | `item_id`（起点） | `related_item_id`（終点） |
|---|---|---|
| `adaptation` | 原作 | 映像化・翻案作品 |
| `sequel` | 前作 | 続編 |
| `prequel` | 後の作品 | 前日譚 |
| `spinoff` | 本編 | スピンオフ |
| `dlc` | 本編 | DLC・追加コンテンツ |
| `reference` | 引用元 | 引用先 |

**この表をツールの説明文とパラメータ説明の両方に埋め込む** 🟡。AI が向きを判断する唯一の手がかりであり、スキーマの外に置かない。

### 3. 自己参照の拒否 🟡

**信頼性**: 🟡 *EDGE-005・[design-interview.md](../design/design-interview.md)「本設計で決定（拒否）」より*

`item_id == related_item_id` の場合、api を呼ばず `MCP_INVALID_ARGUMENT` を返す。

自己参照は意味を持たず、api 側に制約があるかも未確認であるため MCP 側で弾く。

### 4. api 呼び出し 🔵

**信頼性**: 🔵 *[item-relations.md](../../mediavault-api/item-relations.md) より*

```
POST /api/v1/item-relations
{ "item_id": "...", "related_item_id": "...", "relation_type": "adaptation" }
```

### 5. 409 の冪等化 🔵

**信頼性**: 🔵 *REQ-113・[dataflow.md](../design/dataflow.md)「冪等化する409の一覧」・`init_schema.up.sql:102` の `uq_item_relations` より*

409 `DUPLICATE_RELATION` を受けたら `outcome: success` + `already_related: true` で返す。

一意制約は `(item_id, related_item_id, relation_type)` の3つ組。同じ2作品でも種別が違えば別の関係として登録できる 🔵

**既存関係の relation_id を取得するか** 🟡: 409 のレスポンスに ID が含まれない場合、`GET /items/{id}/relations` で探すか、`relation_id: null` で返すかを選ぶ。後者で十分（AI が続けて使う場面がない）。

### 6. 両 Item の情報取得 🔵

**信頼性**: 🔵 *[interfaces.rs](../design/interfaces.rs) `RelateItemsResult.item` / `related_item` より*

`GET /items/{item_id}` と `GET /items/{related_item_id}` を**並列**で取得し、`ItemSummary` にして返す 🟡。

**404 の場合** 🔵 *REQ-110 より*: いずれかが存在しなければ関係を登録せず `not_found` で終了する。

**取得の順序** 🟡: 登録前に両 Item を取得する（存在確認を兼ねる）。登録後に取得すると、存在しない Item への登録を api のエラーで知ることになり、どちらが存在しないか分からない。

### 7. description の生成 🔵

**信頼性**: 🔵 *REQ-072・[interfaces.rs](../design/interfaces.rs)「向きを自然文で示す」より*

```
「小説A」（原作）→「映画A」（映像化）
```

種別ごとの起点・終点のラベル（実装項目2の表）を使って組み立てる。AI が利用者へ「どう登録されたか」を説明する材料になる。

## AIエージェント向け要件

### 向きの明示 🔵

**信頼性**: 🔵 *REQ-072・US-07「関係の向きと種類が明示される」より*

**このツールで最も事故が起きやすいのは向きの取り違え**。原作と映像化を逆に登録すると、利用者が気付きにくいうえ MVP では解除手段がない（REQ-141）。

対策:
- パラメータ説明に起点・終点の意味を種別ごとに書く
- 結果の `description` で「どう登録されたか」を自然文で返す
- AI が利用者へ確認できる材料（両作品のタイトル）を返す

### 固定一覧であることの伝達 🔵

**信頼性**: 🔵 *REQ-071・PRD §15.1「利用者定義は将来候補」より*

利用者が「オマージュ元として登録して」と言った場合、AI が「`reference` として登録します」と既存種別へマッピングできること。エラー時に利用可能な値を返す。

### 解除できないことへの配慮 🟡

**信頼性**: 🟡 *REQ-141（関連解除を公開しない）から導かれる注意*

誤った関係を登録しても MCP からは解除できない。Web UI での手動削除が必要になる。説明文でこれを示唆するか検討する。

## 注意事項

- **TASK-0001（ENUM 拡張）が未完了だと4種別が使えない**。`reference` / `dlc` のみで先行実装すると、後で6種別へ広げる際にテストの作り直しが発生する。TASK-0001 の完了を待つこと
- **向きの説明をスキーマの外に置かないこと**。README に書いても AI は読まない。ツールの説明文とパラメータ説明に埋め込む
- 誤登録は MVP では取り消せない。`relate_items` は他の書き込みツールより慎重な設計が要る 🟡
- 利用者定義の関係種別は将来候補（PRD §7.3）。「その他」のような逃げ道を作らないこと。固定一覧の意味が失われる
