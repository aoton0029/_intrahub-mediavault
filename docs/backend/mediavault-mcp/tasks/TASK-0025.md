## タスク概要

11ツールの**説明文・パラメータ説明・annotation** を実際の MCP クライアント（Claude Code）で確認しながら調整する。

MCPサーバーにとって、ツールの説明文は UI にあたる。実装が正しくても説明文が不十分だと、AI がツールを誤用したり、使うべき場面で使わなかったりする。

**本タスクは実際に AI に使わせて確認する工程**であり、机上の実装だけでは完了しない。

## 実装詳細

### 1. ツール説明文の実装 🔵

**信頼性**: 🔵 *[mcp-tools.md](../design/mcp-tools.md) の各ツールの「ツール説明（AI向け）」より*

設計文書に記載済みの説明文を実装へ反映する。11ツール分。

**説明文に含めるべき要素** 🟡:

| 要素 | 例 |
|---|---|
| 何をするか | 「MediaVault に既に登録済みの作品を検索する」 |
| いつ使うか | 「所蔵確認に使う」 |
| 使わない場面 | 「未登録の作品を外部から探す場合は `search_external_catalog` を使う」 |
| 前提条件 | 「`item_id` は `search_library` で先に一意に特定しておくこと」 |

### 2. ローカル検索と外部検索の区別 🔵

**信頼性**: 🔵 *REQ-032 / NFR-202・PRD §6 原則2・受け入れ基準 TC-NFR-202-01 より*

**PRD の原則2「名称・説明・レスポンスのすべてで区別する」の最終確認**。

| 層 | 実装 | 担当タスク |
|---|---|---|
| 名称 | `search_library` / `search_external_catalog` | TASK-0013 / TASK-0015 |
| 説明 | 互いを参照し「所蔵確認ではない」を明示 | **本タスク** |
| レスポンス | `source` フィールド、`item_id` の有無 | TASK-0013 / TASK-0015 |

説明文が相互参照になっていることをテストで検証する 🟡（一方の説明文に他方のツール名が含まれること）。

### 3. relate_items の向きの説明 🔵

**信頼性**: 🔵 *REQ-072・[mcp-tools.md](../design/mcp-tools.md) 8. の関係種別表より*

6種別それぞれの起点・終点の意味を**パラメータ説明に埋め込む**。ツール説明文だけでなく、`relation_type` の enum 説明にも含める。

**最も誤用リスクが高い箇所**。原作と映像化を逆に登録すると、MVP では解除できない（REQ-141）。

### 4. annotation の設定 🔵

**信頼性**: 🔵 *REQ-004・受け入れ基準 TC-REQ-004-01 より*

| 区分 | ツール | annotation |
|---|---|---|
| 読み取り5件 | `search_library`, `get_item_context`, `search_external_catalog`, `collection_overview`, `health` | `readOnlyHint: true` |
| 書き込み6件 | `import_external_item`, `create_item`, `update_consumption`, `organize_item`, `relate_items`, `add_access_link` | `readOnlyHint: false`, `destructiveHint: false` |

`idempotentHint` が MCP 仕様にあれば、冪等なツール（`organize_item` / `relate_items` / `add_access_link`）に設定する 🟡。`create_item` は冪等でないため設定しない。

### 5. パラメータ説明の充実 🟡

**信頼性**: 🟡 *NFR-201 の趣旨をパラメータ単位へ適用した判断*

`schemars` の `#[schemars(description = "...")]` で各引数に説明を付ける。特に以下:

| 引数 | 説明すべきこと |
|---|---|
| `consumed_date` | `YYYY-MM-DD` 形式のみ。自然言語不可 |
| `create_if_missing` | 既定 false。true のときのみ新規作成 |
| `limit` | 1..=50。超過はエラー（丸めない） |
| `platform` | 対応5種の列挙。それ以外は通常リンクへ |
| `item_id` / `related_item_id` | 関係の起点・終点 |

### 6. 実クライアントでのシナリオ確認 🔵

**信頼性**: 🔵 *[user-stories.md](../spec/user-stories.md) の9ストーリー・PRD §7.1 MVP完了条件「US-01からUS-09までの主要フローをMCPクライアントから実行できる」より*

Claude Code から実際に以下を試す。

| # | シナリオ | 確認点 |
|---|---|---|
| 1 | 「〇〇って持ってる？」 | `search_library` を選ぶか |
| 2 | 「〇〇について詳しく」 | `get_item_context` を選ぶか |
| 3 | 「〇〇を追加して」（未所蔵）| 所蔵確認 → 外部検索 → 登録の順に進むか |
| 4 | 「この同人誌を登録して」 | `create_item` を選ぶか（外部検索へ行かないか）|
| 5 | 「昨日見終わった」 | 日付を変換して `update_consumption` を呼ぶか |
| 6 | 「積読タグ付けて」 | `organize_item`。存在しないとき勝手に作らないか |
| 7 | 「原作と映画版を紐づけて」 | 向きを正しく判断するか |
| 8 | 「Netflix のリンク追加して」/「Jellyfin の…」| 振り分けとフォールバックが伝わるか |
| 9 | 「次に読むもの選んで」 | `collection_overview` → `search_library` と進むか |

**確認結果を記録し、説明文を調整する**。これが本タスクの主作業。

### 7. 呼び出し回数の実測 🔵

**信頼性**: 🔵 *PRD §12・NFR-001 ~ NFR-004・受け入れ基準 TC-NFR-001-01 ~ TC-NFR-004-01 より*

| 指標 | 目標 | シナリオ |
|---|---|---|
| 所蔵確認 | 1回 | #1 |
| 作品コンテキスト | 1回 | #2 |
| 外部検索→登録 | 候補選択を除き2回 | #3 |
| タグ付与 | 1回 | #6 |

超過する場合、説明文の不足か設計の問題かを切り分ける。

## AIエージェント向け要件

> 本タスク全体が AI エージェント向け要件そのものである。

### 説明文は MCP サーバーの UI 🔵

**信頼性**: 🔵 *PRD §6 原則1「目的単位のツールにする」・NFR-202 より*

- 実装が正しくても説明文が不十分なら、AI は正しく使えない
- 説明文の調整は「仕上げの雑務」ではなく、**MVP の完了条件（PRD §7.1）に直結する作業**

### 使わない場面の明示 🟡

**信頼性**: 🟡 *NFR-202 の実践方法として妥当な推測*

「何ができるか」だけでなく「これは違う」を書くほうが誤用を減らせる。特に紛らわしい組み合わせ:

- `search_library` ⇔ `search_external_catalog`
- `create_item` ⇔ `import_external_item`
- `add_access_link` の3つの `kind`

## 注意事項

- **実クライアント確認を省略しないこと**。自動テストは説明文の「存在」は確認できるが「有効性」は確認できない
- 説明文を長くしすぎないこと。すべてのツール説明はコンテキストを消費する。要点を簡潔に 🟡
- 誤用が観察されたとき、まず説明文で解決を試みる。それでも直らない場合は設計（ツールの分け方・引数の形）の問題である可能性を検討する 🟡
- MCP クライアントによってツール選択の挙動は異なる。Claude Code で確認するが、他クライアントでも通用する説明文を心がける 🟡
