## タスク概要

タグ・カテゴリ・マイリストを**名前で**指定して Item へ付与する。ID を意識しない整理体験（US-06）を実現する中核ツール。

**設計上の要点は3つ**:
- 名前→ID解決（REQ-060）
- 冪等性を「事前取得 + 差分適用」で担保（設計決定 D-03）
- `create_if_missing` 既定 false（REQ-111 / PRD §15.1）

## 依存タスク

- **前提タスク**: [TASK-0012](TASK-0012.md)（名前解決）, [TASK-0018](TASK-0018.md)（付与ロジックの共通化）
- **後続タスク**: なし

## 完了条件

- [ ] タグ・カテゴリ・マイリストを名前で付与できる
- [ ] 1回のツール呼び出しで3種すべてを処理できる（NFR-004）
- [ ] 既に付与済みなら重複を作らず `AlreadyApplied` を返す
- [ ] `create_if_missing` 未指定時は新規作成せず `NotResolved` を返す
- [ ] 新規作成分と既存分が `created_new` で区別できる
- [ ] 一部失敗時に成功・失敗・未処理が区別できる
- [ ] 対象は `item_id`（UUID）のみ

## 実装詳細

### 1. ツール定義 🔵

**信頼性**: 🔵 *[mcp-tools.md](../design/mcp-tools.md) 7.・[interfaces.rs](../design/interfaces.rs) `OrganizeItemParams` より*

**実装ファイル**: `backend/mediavault-mcp/src/tools/organize_item.rs`

| 引数 | 型 | 既定 |
|---|---|---|
| `item_id` | `Uuid`（必須）| — 🔵 REQ-142 |
| `tags` | `Vec<String>` | `[]` 🔵 |
| `categories` | `Vec<String>` | `[]` 🔵 |
| `mylists` | `Vec<String>` | `[]` 🔵 |
| `create_if_missing` | `bool` | **false** 🔵 REQ-111 |

- annotation: `readOnlyHint: false`、`destructiveHint: false` 🔵
- 説明文（AI向け）:
  > タグ・カテゴリ・マイリストを**名前で**指定して作品に付与する。存在しない名前は既定では作成されず「候補なし」として返る。新規作成したい場合のみ `create_if_missing: true` を指定すること。

### 2. 事前取得（設計決定 D-03）🔵

**信頼性**: 🔵 *ヒアリング2026-08-07 Q2・[dataflow.md](../design/dataflow.md) 機能4 より*

**実装ファイル**: `backend/mediavault-mcp/src/services/organize.rs`

```
並列で取得:
  GET /api/v1/items/{id}           → 既存タグ・カテゴリ（ItemDetail に含まれる）
  GET /api/v1/items/{id}/mylists   → 既存マイリスト
  GET /api/v1/tags                 → タグマスタ（指定がある場合のみ）
  GET /api/v1/categories           → カテゴリマスタ（同上）
  GET /api/v1/mylists              → マイリストマスタ（同上）
```

**この方式を採る理由** 🔵: 「既に付与済み」を確実に判別でき、REQ-061 の `created_new` 区別と REQ-113 の冪等性を同時に満たせる。409 を握る方式は `POST /items/{id}/tags/{tag_id}` が 409 を返す保証がドキュメント上ない。

**マスタ取得は指定がある種別のみ** 🟡: `tags` が空なら `GET /tags` を呼ばない。無駄な呼び出しを避ける。

### 3. 4分岐の判定 🔵

**信頼性**: 🔵 *[dataflow.md](../design/dataflow.md) 機能4 のフローチャートより*

各指定名について:

| 条件 | 動作 | `OperationResult` |
|---|---|---|
| 既に付与済み | 何もしない | `AlreadyApplied` 🔵 REQ-113 |
| マスタに存在・未付与 | 付与 POST | `Applied { created_new: false }` 🔵 |
| マスタに不在・`create_if_missing: false` | 何もしない | `NotResolved { available_names }` 🔵 REQ-111 |
| マスタに不在・`create_if_missing: true` | 作成 → 付与 | `Applied { created_new: true }` 🔵 REQ-061 |

### 4. 付与の実行 🔵

**信頼性**: 🔵 *[tags.md](../../mediavault-api/tags.md) / [categories.md](../../mediavault-api/categories.md) / [mylists.md](../../mediavault-api/mylists.md) より*

| 種別 | 作成 | 付与 |
|---|---|---|
| タグ | `POST /api/v1/tags` | `POST /api/v1/items/{id}/tags/{tag_id}` 🔵 |
| カテゴリ | `POST /api/v1/categories` | `POST /api/v1/items/{id}/categories/{category_id}` 🔵 |
| マイリスト | `POST /api/v1/mylists` | `POST /api/v1/mylists/{id}/items`（body: `item_id`）🔵 |

マイリストのみ付与の向きが逆（マイリスト側のエンドポイント）である点に注意 🔵

**逐次実行する** 🟡: *[dataflow.md](../design/dataflow.md) 機能4 ステップ3「並列にすると部分失敗時の『未処理』の意味が曖昧になる」より*

付与 POST は指定順に逐次実行する。失敗しても後続を続行し、各結果を記録する。

### 5. 作成競合の扱い 🟡

**信頼性**: 🟡 *[dataflow.md](../design/dataflow.md)「冪等化する409の一覧」より*

`create_if_missing: true` で `POST /tags` が 409 `DUPLICATE_TAG_NAME` を返した場合（別経路で同時に作られた）、マスタを再取得して ID を得てから付与へ進む。エラーにしない。

### 6. ロールバックしない 🔵

**信頼性**: 🔵 *[dataflow.md](../design/dataflow.md)「データ整合性の保証」・REQ-141 より*

途中で失敗しても、作成済みのタグや付与済みの関連を取り消さない。TASK-0018 と同じ方針。

### 7. outcome の集約 🔵

**信頼性**: 🔵 *TASK-0009 の集約ヘルパ・REQ-114 より*

| 状況 | `outcome` |
|---|---|
| すべて `Applied` / `AlreadyApplied` | `success` |
| 一部が `Failed` / `NotResolved`、成功も1件以上 | `partial` |
| すべて `Failed` / `NotResolved` | `error` |
| 指定が空（3種すべて空配列）| `success`（何もしていない）🟡 |

## AIエージェント向け要件

### 3状態の言い分け 🔵

**信頼性**: 🔵 *REQ-061 / REQ-111 / REQ-113・US-06 より*

AI が以下を区別して伝えられること:

| `OperationResult` | 利用者への伝え方 |
|---|---|
| `Applied { created_new: false }` | 「『積読』タグを付けました」 |
| `Applied { created_new: true }` | 「『積読』タグを**新規作成して**付けました」 |
| `AlreadyApplied` | 「既に『積読』タグが付いています」 |
| `NotResolved` | 「『積読』というタグはありません。作成しますか？」 |
| `Failed` | 「タグの付与に失敗しました」 |

### 新規作成の明示 🔵

**信頼性**: 🔵 *REQ-061・PRD §15.1「作成した対象と既存の対象を結果上で区別する」より*

タグの乱立は利用者にとって管理コストになる。`created_new: true` を AI が必ず伝えられるようにする。

### 候補提示による誤字の吸収 🟡

**信頼性**: 🟡 *[interfaces.rs](../design/interfaces.rs) `NotResolved.available_names` より*

`available_names` により、AI が「『積読』ではなく『積ん読』でしょうか？」と確認できる。誤字で新規タグが作られることを防ぐ。

## 注意事項

- **`create_if_missing` の既定を true にしないこと**。PRD §15.1 で確定した決定であり、タグの乱立を防ぐための判断
- **事前取得を「呼び出しが多いから」と省略しないこと**。設計決定 D-03 であり、省略すると `AlreadyApplied` の判別ができなくなる
- `create_item`（TASK-0018）と付与ロジックが重複する。**共通の Service へ切り出す**こと。片方だけ挙動が変わると AI が混乱する 🟡
- マイリストの付与だけエンドポイントの向きが逆（`POST /mylists/{id}/items`）。実装時に取り違えやすい 🔵
- 名前の照合は完全一致（TASK-0012）。部分一致にすると「積読」で「積読候補」に付与される事故が起きる
