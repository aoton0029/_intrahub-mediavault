## 実装詳細

### 1. エラー透過の全ツール検証 🔵

**信頼性**: 🔵 *REQ-146・受け入れ基準 TC-REQ-146-01 より*

**実装ファイル**: `backend/mediavault-mcp/tests/error_consistency.rs`

各ツールについて、api が特徴的な `code` / `message` を返したとき、それがツール結果に**原文のまま**現れることを検証する。

```json
モックの応答: {"success":false,"error":{"code":"TAG_NOT_FOUND","message":"タグが見つかりません"}}
期待: ツール結果の error.code == "TAG_NOT_FOUND" && error.message == "タグが見つかりません"
```

MCP が独自のメッセージへ置き換えたり、要約したりしないこと。

### 2. エラー分類の一貫性 🔵

**信頼性**: 🔵 *REQ-120・EDGE-001 / EDGE-002・[dataflow.md](../design/dataflow.md) より*

全ツール × 3種のエラーで、`code` と `retriable` が一貫することを検証する。

| 状況 | 全ツール共通の期待 |
|---|---|
| api 停止 | `MCP_API_UNREACHABLE`、`retriable: true` 🔵 |
| api が 500 | api の code、`retriable: true` 🔵 |
| api が 400 | api の code、`retriable: false` 🔵 |
| api が 404 | `outcome: not_found`、api の code 🔵 |

**例外**: `health` は接続失敗でも `outcome: success` を返す（TASK-0010）。これを「例外として正しい」ことを明示的にテストする 🔵

### 3. 冪等化する409の検証 🔵

**信頼性**: 🔵 *[dataflow.md](../design/dataflow.md)「冪等化する409の一覧」・REQ-112 / REQ-113 より*

| エラーコード | ツール | 期待 |
|---|---|---|
| `ITEM_ALREADY_IMPORTED` | `import_external_item` | `success` + `already_existed: true` 🔵 |
| `DUPLICATE_RELATION` | `relate_items` | `success` + `already_related: true` 🔵 |
| `DUPLICATE_STREAMING_LINK` | `add_access_link` | `success` + `already_registered: true` 🟡 |
| `DUPLICATE_TAG_NAME` | `organize_item` | 再取得して付与へ進む 🟡 |

**冪等化しない409** 🟡: 上記以外の 409 は通常のエラーとして返ることを確認する。すべての409を成功にすると、本来の重複エラーを見逃す。

### 5. api 全停止時の全ツール動作 🔵

**信頼性**: 🔵 *REQ-120 / REQ-121 より*

## AIエージェント向け要件

### エラー対処法の再利用性 🔵

**信頼性**: 🔵 *NFR-201・PRD §11 より*

AI が1つのツールで学んだエラー対処法を、他のツールでもそのまま使えること。

- 「`retriable: true` なら少し待って再試行」が全ツールで正しい
- 「`outcome: not_found` なら対象を再検索」が全ツールで正しい
- 「`code` を利用者へそのまま伝えれば意味が通る」が全ツールで正しい

**一貫性が崩れると、AI はツールごとに異なる推測をする**。それが誤った操作につながる。

### 再試行の安全性 🔵

**信頼性**: 🔵 *PRD §6 原則6・REQ-113 より*

`retriable: true` を見た AI が再試行したとき、冪等なツール（`organize_item` / `relate_items` / `add_access_link`）では重複が生まれないこと。

**`create_item` は冪等でない**ため、`retriable` の扱いに注意が必要（TASK-0018 の注意事項）🟡。

## 注意事項

- **一貫性の欠如を見つけたら、テストではなく実装を直す**。「このツールだけ特別」を許すと AI の推測が壊れる
- `health` の例外だけは意図的なもの。テストで「例外として正しい」ことを明示し、将来のリファクタで揃えられないようにする
- 個別タスクで既にテスト済みの Edgeケースを重複実装しない。本タスクは**横断的な一貫性**の検証に集中する 🟡
- `create_item` が冪等でないことは設計上の制約（api 側に手動作成の重複判定がない）。テストで確認するだけで、無理に冪等化しない 🟡
