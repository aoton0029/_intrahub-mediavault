# mediavault-mcp ヒアリング記録

**作成日**: 2026-08-07
**ヒアリング実施**: step4 既存情報ベースの差分ヒアリング

## ヒアリング目的

[PRD](../PRD.md) は §15 で主要な決定を済ませているため、本ヒアリングでは **PRD §8「MediaVault-apiへの要求候補」と既存実装の実態との差分**、および PRD §15.2 の残課題に絞って質問した。

### 事前調査（既存実装の確認）

`backend/mediavault-api/src/routes/mod.rs`、`migrations/20260623000001_init_schema.up.sql`、`docs/backend/mediavault-api/*.md` を確認し、以下を特定した。

| 確認事項 | 実態 |
|---|---|
| `relation_type` | PostgreSQL ENUM `('reference','dlc')`。拡張にはマイグレーションが必要 |
| `GET /items` の `title` | 本題の部分一致のみ。`original_title`・`details.alternative_titles` は対象外 |
| 総件数 | `GET /items` は `total` を返さない（COUNT回避のため意図的） |
| 集約API | `/items/{id}/context`、`/collection/overview`、`/items/{id}/text` はいずれも未実装 |
| jobs API | 汎用 jobs は未実装。存在するのは `/import/booklog/jobs/*` のみ |
| `streaming_links.platform` | `netflix` / `amazon_prime` / `disney_plus` / `dmm_tv` / `apple_tv` の5種固定 |
| `item_status` | `not_started` / `in_progress` / `completed` の3値 |
| 公開API の認証 | `/api/v1/*` は無認証 |

> **後日注記（2026-08-15）**: 上表はヒアリング時点（2026-08-07）の調査記録である。全文取得と抽出操作の未実装状態は `docs/extractor/` の設計・実装により解消済み。

## 質問と回答

### 事前フェーズ: 作業規模・出力先・調査範囲

**質問日時**: 2026-08-07
**カテゴリ**: スコープ設定

- **作業規模** → **フル機能開発**（詳細なEARS要件、ユーザーストーリー、受け入れ基準、非機能要件・エッジケース含む）
- **出力先** → **`docs/backend/mediavault-mcp/spec/`**（PRD・tech-stack と同じ場所にまとめる。kairo既定の `docs/spec/` は不採用）
- **既存コードベースの詳細分析** → **必要**

**信頼性への影響**: コードベース分析により、PRD §8 の要求候補が「未実装」なのか「実装済みだが制約あり」なのかを一次情報で確認でき、REQ-011 / REQ-013 / REQ-071 / REQ-090 の前提を 🟡 から 🔵 へ引き上げられた。

### Q1: `relate_items` の関係種別拡張をMVPスコープでどう扱うか

**質問日時**: 2026-08-07
**カテゴリ**: 既存設計確認 / 影響範囲
**背景**: PRD §15.1 で「関係種別を6値へ拡張するよう api へ要求する」と確定しているが、実態は PostgreSQL ENUM の2値であり、MCP 単独では実現できない。MCP の MVP 完了条件に影響する。

**回答**: **api側を先に拡張**（MCP実装前の前提タスクとして ENUM 拡張マイグレーションを行い、MCP は MVP から6種別を提供する）

**信頼性への影響**:
- REQ-071（関係種別6種）が 🟡 → 🔵
- [prep.md](prep.md) PREP-01 を「必須」として追加

---

### Q2: `search_library` の別名・原題検索をMVPでどうするか

**質問日時**: 2026-08-07
**カテゴリ**: 未定義部分の詳細化
**背景**: PRD §8 に「別名・原題を含む検索」が要求候補として挙がっているが、MVPで必須かどうかが未確定だった。MCP側で表記揺れ候補を生成する代替案もありうる。

**回答**: **api側を拡張**（`GET /items` の検索対象を `original_title` と `details.alternative_titles` へ広げる）

**信頼性への影響**:
- REQ-011（別名・原題検索）が新規要件として 🔵 で追加
- PREP-02 を「必須」として追加

---

### Q3: `collection_overview` のMVP提供範囲

**質問日時**: 2026-08-07
**カテゴリ**: 追加要件 / スコープ調整
**背景**: PRD §15.1 では「media_type別件数と最近追加・更新されたItemに限定し、status別内訳は集計API実装後」と**仮決定**の状態だった。`GET /items` が総件数を返さない以上、status別内訳には新APIが必須。

**回答**: **集計APIも今回実装**（`GET /api/v1/collection/overview` を新設し、status別・お気に入り別件数もMVPで提供する）

**信頼性への影響**:
- PRD §15.1 の「仮決定」が確定へ。REQ-090 が 🟡 → 🔵
- REQ-013（該当件数）の実現手段も明確化
- PREP-03 / PREP-04 を「必須」として追加

---

### Q4: 非対応プラットフォームの配信URLの扱い

**質問日時**: 2026-08-07
**カテゴリ**: 未定義部分の詳細化
**背景**: PRD §5 US-08 は「配信サービス、公式サイト、Jellyfin、Calibre-Web、トレーラー」を挙げるが、`streaming_links.platform` は5種固定であり、Jellyfin や U-NEXT は表現できない。

**回答**: **通常リンクへフォールバック**（対象外サービスは `item_links` へラベル付きで登録し、どちらに登録したかを結果で返す）

**信頼性への影響**:
- REQ-081 が新規要件として 🔵 で追加
- api 側の ENUM 拡張が不要となり、前提タスクが1件減った

---

### Q5: `get_item_context` の実装方式（PRD §15.2 の残課題）

**質問日時**: 2026-08-07
**カテゴリ**: 既存設計確認
**背景**: PRD §15.2 に「集約APIにするか MCP による複数API合成にするか」が残課題として残っていた。

**回答**: **MCP側で複数API合成**（`GET /items/{id}` に加え、関連・マイリスト・グループ・キャスト・ファイル・リンク・トレーラーを取得して合成する。api改修は不要）

**信頼性への影響**:
- PRD §15.2 の残課題が解消。REQ-022 が 🔵
- NFR-005（並列取得）を NFR-002 の達成手段として追加（🟡）

---

### Q6: 書き込みツールの対象Item指定方法（PRD §6 原則3の具体化）

**質問日時**: 2026-08-07
**カテゴリ**: 未定義部分の詳細化 / 安全性
**背景**: PRD §6 原則3「曖昧な対象へ書き込まない」は方針としては確定していたが、ツール引数レベルの実現方法が未定義だった。

**回答**: **`item_id` 必須**（書き込み系ツールは UUID のみ受け付ける。タイトル解決は `search_library` の責務に分離する）

**信頼性への影響**:
- REQ-142 が 🔵 で追加。制約要件として明文化
- NFR-301（誤書き込み0件）の検証方法が「入力スキーマの列挙で機械的に確認できる」形になり、テスト設計が確定

---

### Q7: 一覧系ツールの返却件数

**質問日時**: 2026-08-07
**カテゴリ**: 非機能要件 / パフォーマンス
**背景**: PRD §11 は「件数上限とページネーションを持つ」とだけ述べており、具体値が未定義だった。`GET /items` は既定20・最大100。

**回答**: **既定20 / 上限50**（AIのコンテキストを圧迫しないよう api より厳しくし、カーソルを返して継続取得可能にする）

**信頼性への影響**:
- REQ-143 が 🔵 で追加、REQ-130（カーソル）も確定
- EDGE-101（51以上の指定）が新規の境界値ケースとして発生（丸めか拒否かは設計で確定：🟡 のまま）

---

### Q8: MCPツール `health` の確認内容

**質問日時**: 2026-08-07
**カテゴリ**: 未定義部分の詳細化
**背景**: PRD §7.1 は「MediaVault-apiへの接続と依存サービス状態を確認」とのみ記載。依存サービスの範囲が未定義だった。

**回答**: **MediaVault-api 到達性 + MCP自身のバージョン**（内部APIキーの有効性確認、外部APIキーの設定状況は含めない）

**信頼性への影響**:
- REQ-100 が 🔵 で確定。スコープが縮小し、実装が単純化
- 外部APIキー未設定は `search_external_catalog` 実行時の 422 で検知する方針（REQ-117）に一本化

## ヒアリング結果サマリー

### 確認できた事項

- PRD §15.1 の「仮決定」であった `collection_overview` の提供範囲が確定した（Q3）
- PRD §15.2 の残課題「`get_item_context` の実装方式」が解消した（Q5）
- PRD §6 原則3が、ツール引数レベルの具体的制約（`item_id` 必須）へ落ちた（Q6）
- PRD §11 の抽象的な件数制限が具体値（20/50）になった（Q7）
- MCP のみでは実現できず、mediavault-api の先行改修が必要な要件が4件あることが確定した（Q1, Q2, Q3）

### 追加/変更要件

| 種別 | 内容 |
|---|---|
| 追加 | REQ-011（別名・原題検索）、REQ-081（配信リンクのフォールバック）、REQ-142（`item_id` 必須）、REQ-143（20/50）、NFR-005（並列取得） |
| 変更 | REQ-090（`collection_overview` が status別・お気に入り別も返す。PRDでは第2段階以降だった） |
| 縮小 | REQ-100（`health` の確認範囲を api 到達性とバージョンに限定） |

### 残課題

| 残課題 | ステータス | メモ |
|---|---|---|
| `limit` に上限超過値が渡されたときに丸めるか拒否するか | 設計で決定 | EDGE-101。丸めは寛容だが利用者に上限が伝わりにくい |
| `rating` の許容範囲 | 設計で決定 | MediaVault-api 側の仕様が文書化されていない。EDGE-104 |
| `relate_items` で自己参照を拒否するか | 設計で決定 | EDGE-005。API側に制約があるか未確認 |
| `rmcp` の採用バージョン | 仮決定 | 3.1系（[tech-stack.md](../tech-stack.md)）。実装着手時に最新安定版を再確認 |
| 第2段階（全文取得・jobs・stdio）の要件詳細 | 保留 | REQ-900 ~ REQ-902 として枠のみ確保。api側の実装が前提 |
