# mediavault-mcp 要件定義書

## 概要

MediaVault-mcp は、AIエージェント（Claude Code などのMCPクライアント、KnowledgeHub常駐エージェント）から MediaVault のコレクションを検索・理解・登録・整理・更新するための MCP サーバーである。

REST API をそのままツール化せず、利用者の目的単位のツールへまとめる。データは所有せず、読み書きはすべて MediaVault-api を経由する。本要件定義は **MVP（PRD §7.1）** を対象とし、第2段階（全文取得・非同期ジョブ・stdio）は将来枠として要件IDのみ確保する。

### 通常要件

#### サーバー基盤

- REQ-001: システムは Streamable HTTP トランスポートで MCP サーバーを提供しなければならない 🔵 *PRD §14・§15.1「stdio／Streamable HTTPの提供順序」より*
- REQ-002: システムは MCP ツールの一覧と入出力スキーマを Rust 構造体から生成して公開しなければならない 🔵 *PRD §14より*
- REQ-003: システムは MediaVault-api への HTTP 呼び出しのみでデータを読み書きしなければならない 🔵 *PRD §6 原則8・§13より*
- REQ-004: システムは MCP ツールを読み取り系と追記・更新系に区別し、MCPのツールメタデータ上で識別できるようにしなければならない 🔵 *PRD §10より*

#### search_library（US-01, US-09）

- REQ-010: システムは MediaVault 内の Item をタイトル、メディア種別、状態、タグ名、カテゴリ名、お気に入りで絞り込んで検索できなければならない 🔵 *PRD §7.1・`GET /api/v1/items` の実装済みフィルタより*
- REQ-011: システムは検索において、本題（`title`）に加え原題（`original_title`）および別名（`details.alternative_titles`）を対象としなければならない 🔵 *ヒアリング2026-08-07「api側を拡張」より*
- REQ-012: システムは検索結果の各候補に、同名作品を区別できる情報（ID、メディア種別、公開年、状態、タグ）を含めなければならない 🔵 *PRD §5 US-01より*
- REQ-013: システムは検索結果に、選定条件に対する該当件数を含めなければならない 🔵 *PRD §5 US-09・§8「検索結果の該当件数」より*
- REQ-014: システムは検索結果が0件の場合、外部カタログの検索結果と区別できる形で0件であることを返さなければならない 🔵 *PRD §5 US-01・§6 原則2より*

#### get_item_context（US-02）

- REQ-020: システムは Item ID を受け取り、Item本体、詳細、タグ、カテゴリ、マイリスト、ファイル、リンク、配信リンク、トレーラー、関連作品、スタッフ、キャスト、グループをまとめて返さなければならない 🔵 *PRD §7.1・§8より*
- REQ-021: システムは各情報について、未登録である場合と取得に失敗した場合を区別して返さなければならない 🔵 *PRD §5 US-02より*
- REQ-022: システムは複数の MediaVault-api エンドポイントを呼び出して作品コンテキストを合成しなければならない 🔵 *ヒアリング2026-08-07「MCP側で複数API合成」・PRD §15.2より*

#### search_external_catalog / import_external_item（US-03）

- REQ-030: システムは メディア種別と検索語を受け取り、外部カタログの候補一覧を返さなければならない 🔵 *PRD §7.1・`GET /api/v1/items/search` より*
- REQ-031: システムは 外部カタログの各候補に、タイトル、公開年、メディア種別、プロバイダー、プロバイダー固有IDを含めなければならない 🔵 *PRD §5 US-03・`SearchResultItem` より*
- REQ-032: システムは 外部カタログ検索のツール名と結果を、MediaVault内検索と明確に区別できるものにしなければならない 🔵 *PRD §6 原則2より*
- REQ-033: システムは プロバイダー固有IDとプロバイダー名を受け取り、対応する Item を MediaVault へ登録しなければならない 🔵 *PRD §7.1・`POST /api/v1/items/import` より*

#### create_item（US-04）

- REQ-040: システムは タイトルとメディア種別を必須として、Item を手動登録できなければならない 🔵 *PRD §5 US-04・`POST /api/v1/items` より*
- REQ-041: システムは 手動登録と同じ呼び出しの中で、任意でファイルパス、URL、タグ名、マイリスト名を関連付けられなければならない 🔵 *PRD §5 US-04より*

#### update_consumption（US-05）

- REQ-050: システムは `status`、`consumed_date`、`rating`、`is_favorite` を1回の呼び出しで更新できなければならない 🔵 *PRD §15.1「`update_consumption` の対象項目」より*
- REQ-051: システムは 更新の結果として、対象ItemのIDと表示名、および更新前後の値を返さなければならない 🔵 *PRD §5 US-05・§6 原則5より*
- REQ-052: システムは 確定済みの日付（`YYYY-MM-DD`）のみを受け取り、自然言語の日付表現を解釈してはならない 🔵 *PRD §5 US-05より*

#### organize_item（US-06）

- REQ-060: システムは タグ、カテゴリ、マイリストを名前で受け取り、MediaVault-api から ID を解決して Item へ付与しなければならない 🔵 *PRD §7.1・§8「タグ・カテゴリはID指定のためMCPが名前から解決する」より*
- REQ-061: システムは 付与結果において、新規作成した対象と既存の対象を区別して返さなければならない 🔵 *PRD §15.1「タグ・カテゴリ・マイリストの自動作成」より*

#### relate_items（US-07）

- REQ-070: システムは 2つの Item ID と関係種別を受け取り、関係を登録しなければならない 🔵 *PRD §7.1より*
- REQ-071: システムは 関係種別として `adaptation` / `sequel` / `prequel` / `spinoff` / `dlc` / `reference` の固定一覧のみを受け付けなければならない 🔵 *PRD §15.1「関係種別」・ヒアリング2026-08-07「api側を先に拡張」より*
- REQ-072: システムは 関係の向き（`item_id` → `related_item_id`）が種別ごとに何を意味するかをツール説明で明示しなければならない 🔵 *PRD §5 US-07・§8より*

#### add_access_link（US-08）

- REQ-080: システムは URL と用途（通常リンク／配信リンク／トレーラー）を受け取り、対応する MediaVault-api へ登録しなければならない 🔵 *PRD §7.1より*
- REQ-081: システムは 配信リンクとして指定されたプラットフォームが MediaVault-api の対応一覧（`netflix` / `amazon_prime` / `disney_plus` / `dmm_tv` / `apple_tv`）にない場合、通常リンクとして登録し、そのフォールバックが起きたことを結果に含めなければならない 🔵 *ヒアリング2026-08-07「通常リンクへフォールバック」より*

#### collection_overview（US-09）

- REQ-090: システムは メディア種別別の件数、状態別の件数、お気に入り件数、最近追加・更新された Item を返さなければならない 🔵 *ヒアリング2026-08-07「集計APIも今回実装」より*

#### health

- REQ-100: システムは MediaVault-api への到達可否と応答時間、および MediaVault-mcp 自身のバージョンを返さなければならない 🔵 *ヒアリング2026-08-07より*

### 条件付き要件

- REQ-110: 書き込みツールに未知の Item ID が渡された場合、システムは書き込みを行わず、Item が存在しないことを示すエラーを返さなければならない 🔵 *PRD §10「存在しないItemを正常終了として扱わない」より*
- REQ-111: タグ・カテゴリ・マイリストの名前が既存に一致しない場合、システムは `create_if_missing` が明示的に指定されたときのみ新規作成し、指定がなければ作成せず「候補なし」として返さなければならない 🔵 *PRD §15.1「タグ・カテゴリ・マイリストの自動作成」より*
- REQ-112: 既にインポート済みの外部作品を `import_external_item` で登録しようとした場合、システムは重複を作らず既存の Item を返さなければならない 🔵 *PRD §5 US-03・`POST /items/import` の 409 `ITEM_ALREADY_IMPORTED` より*
- REQ-113: 既に付与済みのタグ・カテゴリ・マイリスト、または既に登録済みの関係を再度指定された場合、システムは重複を作らず「既に付与済み」であることを返さなければならない 🔵 *PRD §6 原則6より*
- REQ-114: 複数段階の書き込みのうち一部が失敗した場合、システムは成功した操作と失敗した操作を区別して返し、全体を成功として扱ってはならない 🔵 *PRD §5 US-04・§10より*
- REQ-115: `Authorization` ヘッダーが欠落または不正な場合、システムは MCP ツールを実行せず 401 を返さなければならない 🔵 *PRD §15.1「外部・内部経路の認証」より*
- REQ-116: 不正な形式の URL が指定された場合、システムは登録を行わずバリデーションエラーを返さなければならない 🔵 *PRD §10より*
- REQ-117: `search_external_catalog` の対象プロバイダーのAPIキーが未設定の場合、システムは 422 `API_KEY_NOT_CONFIGURED` を利用者が識別できる形で返さなければならない 🔵 *`GET /items/search` の実装済みエラーより*

### 状態要件

- REQ-120: MediaVault-api が停止している場合、システムは接続エラーであることを示し、MediaVault-api の業務エラーと区別して返さなければならない 🔵 *PRD §11より*
- REQ-121: worker や KnowledgeHub が停止している場合であっても、システムは MVP のメタデータ検索・登録・整理ツールを提供し続けなければならない 🔵 *PRD §11より*
- REQ-122: `MCP_AUTH_TOKEN` が未設定または空文字の場合、システムは起動に失敗しなければならない 🟡 *tech-stack.md の設計判断。PRD §15.1「無認証の接続からツールを実行できない」を起動時に担保するための妥当な具体化*

### オプション要件

- REQ-130: システムは 一覧系ツールの結果に継続取得用のカーソルを含めてもよい 🔵 *PRD §11・`GET /items` の keyset ページネーションより*
- REQ-131: システムは MCP Resources / Prompts を提供しなくてよい 🔵 *PRD §14「初期スコープはToolsを中心とし、ResourcesとPromptsは将来候補」より*

### 制約要件

- REQ-140: システムは PostgreSQL へ直接アクセスしてはならない 🔵 *PRD §6 原則8・§13より*
- REQ-141: システムは MVP において Item 削除、物理ファイル削除、関連解除、APIキー更新のツールを公開してはならない 🔵 *PRD §10・§13・§15.1より*
- REQ-142: システムは 書き込みツールの対象 Item を UUID（`item_id`）でのみ受け取り、タイトル文字列を書き込み対象の指定手段として受け付けてはならない 🔵 *ヒアリング2026-08-07「item_id 必須」・PRD §6 原則3より*
- REQ-143: システムは 一覧系ツールの返却件数を既定20件・上限50件に制限しなければならない 🔵 *ヒアリング2026-08-07より*
- REQ-144: システムは 要約、Wiki、推薦、embedding を生成しても保存してもならない 🔵 *PRD §6 原則7・§13より*
- REQ-145: システムは API キー、認証トークンをツール引数、ツール結果、ログのいずれにも出力してはならない 🔵 *PRD §10より*
- REQ-146: システムは MediaVault-api が返したエラーコードとメッセージを失わずに利用者へ返さなければならない 🔵 *PRD §7.1 MVP完了条件より*

### 将来要件（第2段階・本要件定義のスコープ外）

- REQ-900: システムは 抽出済み全文をページまたはチャンク単位で取得できるようにする（`get_item_text`, US-10）🔵 *PRD §7.2より*
- REQ-901: システムは ファイルのテキスト抽出を冪等に依頼・監視・キャンセルできるようにする（`request_extraction` / `get_extraction_status` / `cancel_extraction`, US-11）🔵 *PRD §7.2より*
- REQ-902: システムは stdio トランスポートを、Streamable HTTP とツールの意味・入出力を同一にしたうえで追加する 🔵 *PRD §11・§15.1より*
- REQ-903: システムは 作品に記録済みの引用を、出典位置（`locator_type` と対応する位置フィールド）を保ったまま一覧できるようにする（`list_citations`, US-12）🟡 *PRD §7.2・設計決定 D-11（ヒアリング2026-08-13）より*
- REQ-904: システムは 引用を追記できるようにする（`add_citation`, US-12）。**`locator_type` と位置フィールドが整合しない場合は MediaVault-api を呼ばずに拒否する** 🟡 *設計決定 D-11 より。api 側は整合を必須バリデーションしないため（[citations.md](../../mediavault-api/citations.md)）、MCP 側で担保しないと出典不明の引用が蓄積する*
- REQ-905: システムは 引用の更新・削除ツールを提供してはならない 🟡 *設計決定 D-11 より。`quote_text` は利用者が書いた本文であり、上書きは実質的に破壊的であるため*

## 非機能要件

### パフォーマンス

- NFR-001: 所蔵確認は原則1回の MCP ツール呼び出しで候補を取得できなければならない 🔵 *PRD §12より*
- NFR-002: 作品コンテキストは原則1回の MCP ツール呼び出しで取得できなければならない 🔵 *PRD §12より*
- NFR-003: 外部検索から登録までは、候補選択を除き2回以内の MCP ツール呼び出しで完了できなければならない 🔵 *PRD §12より*
- NFR-004: タグ／カテゴリ／マイリストの名前指定による付与は1回の MCP ツール呼び出しで完了できなければならない 🔵 *PRD §12より*
- NFR-005: `get_item_context` を構成する複数の MediaVault-api 呼び出しは並列に実行しなければならない 🟡 *NFR-002 を MCP合成方式（REQ-022）で満たすための妥当な実装要件*
- NFR-006: MediaVault-api への呼び出しにはタイムアウトを設定し、MCP接続を無期限に占有してはならない 🟡 *PRD §11「MCP接続を長時間占有せず」から妥当な推測*

### セキュリティ

- NFR-101: Streamable HTTP エンドポイントは静的 Bearer トークンによる認証を必須とし、MCPプロセス自身が検証しなければならない 🔵 *PRD §10・§15.1・ヒアリング2026-08-07より*
- NFR-102: トークン比較は定数時間で行わなければならない 🟡 *tech-stack.md の設計判断。タイミング攻撃回避のための妥当な具体化*
- NFR-103: 内部書き込みAPIの呼び出しには `INTERNAL_API_KEY` を用い、MCPクライアントへ露出してはならない 🔵 *PRD §10より*
- NFR-104: プロセス死活監視用のエンドポイントのみ認証対象外とし、MCPツールはすべて認証必須としなければならない 🟡 *tech-stack.md の設計判断。運用上の必要から妥当な具体化*

### ユーザビリティ

- NFR-201: MCP ツールの入出力は構造化し、AI が ID、候補、ページネーション、部分失敗を判定できる形にしなければならない 🔵 *PRD §11より*
- NFR-202: ツール名と説明文は、MediaVault内検索と外部カタログ検索の違いが説明文を読まずとも区別できるものにしなければならない 🔵 *PRD §6 原則2より*
- NFR-203: 書き込み結果の100%で、対象 Item ID と変更内容を確認できなければならない 🔵 *PRD §12より*

### 保守性・テスト

- NFR-301: 自動テスト上、曖昧な名称から誤った Item へ書き込むケースが0件でなければならない 🔵 *PRD §12より*
- NFR-302: MediaVault-api は `wiremock` によるモックで統合テストしなければならない 🔵 *ヒアリング2026-08-07「単体+APIモック統合」より*
- NFR-303: MCP からの DB 直接アクセスが0件でなければならない（`sqlx` を依存に含めない）🔵 *PRD §12・tech-stack.md より*

## Edgeケース

### エラー処理

- EDGE-001: MediaVault-api が接続不能な場合、`ConnectionError` として返し、認証エラー・業務エラーと混同しない 🔵 *PRD §11より*
- EDGE-002: MediaVault-api が 5xx を返した場合、MCP ツールはエラーとして返し、空の成功結果を返さない 🔵 *PRD §10より*
- EDGE-003: `organize_item` で3件のタグ付与のうち2件目が失敗した場合、1件目の成功と2件目の失敗、3件目の未処理を区別して返す 🔵 *PRD §10より*
- EDGE-004: `create_item` で Item 作成に成功した後のタグ付与が失敗した場合、作成済み Item ID を返したうえで付与失敗を示す 🔵 *PRD §5 US-04より*
- EDGE-005: `relate_items` で同一 Item を関係元・関係先の両方に指定された場合、登録せずバリデーションエラーを返す 🟡 *自己参照は無意味であるという妥当な推測。API側の制約は未確認*
- EDGE-006: 外部プロバイダがタイムアウトした場合、502 `EXTERNAL_API_TIMEOUT` を区別して返す 🔵 *`GET /items/search` の実装済みエラーより*

### 境界値

- EDGE-101: 一覧系ツールで `limit` に51以上が指定された場合、50に丸めるかバリデーションエラーとする（設計で確定）🟡 *REQ-143 から導出される境界。丸めか拒否かは未確定*
- EDGE-102: `search_library` の検索語が空文字または空白のみの場合、全件返却ではなくバリデーションエラーとする 🟡 *PRD §11「コレクション全件を無制限に返さない」から妥当な推測*
- EDGE-103: `create_item` の `title` が空白のみの場合、MediaVault-api と同じく 400 `VALIDATION_ERROR` を返す 🔵 *`POST /items` の実装済み挙動より*
- EDGE-104: `update_consumption` で `rating` に MediaVault-api の許容範囲外の値が渡された場合、API のバリデーションエラーをそのまま返す 🟡 *REQ-146 から導出。rating の許容範囲自体はAPI仕様で明示されていない*
- EDGE-105: `get_item_context` の対象 Item に紐づく情報が一切ない場合、空配列と「未登録」を明示して返し、エラーとしない 🔵 *PRD §5 US-02「未登録なのか取得失敗なのかを区別」より*
- EDGE-106: `status` に MediaVault-api の ENUM（`not_started` / `in_progress` / `completed`）以外が指定された場合、バリデーションエラーとする 🔵 *`item_status` ENUM 定義より*

## 前提となる MediaVault-api 側の改修

以下は本要件の一部を成立させるために mediavault-api 側で必要な改修である。詳細と優先度は [prep.md](prep.md) を参照。

> **2026-08-13 更新**: 全エンドポイントの棚卸しの結果、**4件すべてが実装済み**であることを確認した。MVP の要件は既存APIのみで成立する。確認結果は [design/api-tool-mapping.md](../design/api-tool-mapping.md) §6 を参照。

| 改修 | 関連要件 | 理由 | 状況 |
|---|---|---|---|
| `relation_type` ENUM の拡張 | REQ-071 | 現行は `reference` / `dlc` の2値のみ | ✅ **実装済み**。6値すべて対応し、向きの意味も定義済み（[item-relations.md](../../mediavault-api/item-relations.md)） |
| `GET /items` の別名・原題検索対応 | REQ-011 | 現行は本題の部分一致のみ | ✅ **実装済み**。`title` が title / original_title / `details.alternative_titles` を横断ORで部分一致（[items.md](../../mediavault-api/items.md)） |
| 検索結果の該当件数返却 | REQ-013 | 現行は `total` を返さない | ✅ **実装済み**。`include_total=true` で `pagination.total`（オプトイン方式） |
| `GET /collection/overview` の新設 | REQ-090 | status別・お気に入り別の件数を取得する手段がない | ✅ **実装済み**（[collection.md](../../mediavault-api/collection.md)） |

第2段階の要件 REQ-900 / REQ-901 が依存する Item Text API と抽出リソースは実装済みである。MCP はこれらの公開APIのみを利用する。
