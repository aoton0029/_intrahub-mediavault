## 1. 正常系テストケース（基本的な動作）

### TC-001-02-A: 複数フィールドの部分更新（SET句ビルダー、ユニット）

- **テスト名**: `build_update_item_query`がrating・is_favoriteのみのSET句を生成する
  - **何をテストするか**: `UpdateItemRequest`のうち`rating`・`is_favorite`のみ`Some`の場合に、SET句ビルダー関数が両カラムのみをSET対象として含むSQLを構築するかを確認する
  - **期待される動作**: 生成SQLが`rating = `と`is_favorite = `を含み、`title = `等の他カラムは含まない
- **入力値**: `UpdateItemRequest { rating: Some(4.5), is_favorite: Some(true), ..全フィールドNone }`
  - **入力データの意味**: 要件定義書シナリオ1（TC-001-02）の代表入力。複数フィールド同時更新かつ他フィールド非対象の基本パターンを表す
- **期待される結果**: `sql.contains("rating = ")`かつ`sql.contains("is_favorite = ")`が真、`sql.contains("title = ")`が偽
  - **期待結果の理由**: REQ-0012-01（Someのみ適用）・REQ-0012-03（QueryBuilder踏襲）に直接対応
- **テストの目的**: 動的SET句構築の基本動作を実DB不要で高速に検証する
  - **確認ポイント**: カンマ区切り（2フィールド目に`, `が入る）、`push_bind`によるバインド方式（プレースホルダ`$N`を使用しリテラル値を文字列結合していないこと）
- 🔵 信頼性レベル: 要件定義書REQ-0012-01・REQ-0012-03、note.md「push_item_filtersパターンの踏襲」より

### TC-001-02-B: 部分更新の正常動作（実DB統合）

- **テスト名**: `update_item`がrating・is_favoriteのみを更新し他フィールドを変化させない
  - **何をテストするか**: 実DB上でPATCH相当の更新を行い、対象2フィールドのみ変化し他フィールド（title等）が変化しないことを確認する
  - **期待される動作**: 更新後Itemの`rating==4.5`・`is_favorite==true`、`title`は投入時の値を維持
- **入力値**: 事前に`insert_test_item`で1件投入したitemのID + `UpdateItemRequest { rating: Some(4.5), is_favorite: Some(true), ..None }`
  - **入力データの意味**: 要件定義書シナリオ1・タスクファイルテストケース1の実DB版
- **期待される結果**: 戻り値`Item`の`rating`・`is_favorite`が更新値、`title`が元の値のまま、`updated_at`が更新前より新しい
  - **期待結果の理由**: REQ-0012-01・REQ-0012-02・EDGE-0012-02・DBトリガー(REQ-0012-04)に対応
- **テストの目的**: SET句構築からDB反映・トリガー発火までのEnd-to-End動作を保証する
  - **確認ポイント**: `updated_at`がアプリ側で明示更新していないにもかかわらず変化していること（トリガー発火の間接確認）
- 🔵 信頼性レベル: 要件定義書シナリオ1・REQ-0012-04、タスクファイルテストケース1より

### TC-NEW-01: 単一フィールドのみの更新（status単独、実DB統合）

- **テスト名**: `update_item`がstatusのみを更新する
  - **何をテストするか**: 更新対象フィールドが1個のみの場合でもSET句生成・UPDATE実行が正しく機能するか（カンマ区切りロジックの境界）
  - **期待される動作**: `status`のみ変化し、他フィールドは変化しない
- **入力値**: `UpdateItemRequest { status: Some(ItemStatus::Completed), ..None }`
  - **入力データの意味**: SET句が1項目のみの場合、`push_item_filters`同型の「1件目はカンマなし」ロジックが正しく動くかを確認する代表値
- **期待される結果**: `status==Completed`、他フィールド不変、200相当の戻り値
  - **期待結果の理由**: REQ-0012-03（has_condition方式の踏襲）より、1項目時にカンマが付与されないことを保証する必要がある
- **テストの目的**: SET句が1個のときに先頭カンマや末尾カンマが残らない実装になっているかを確認する
  - **確認ポイント**: SQL文字列に`,`が含まれない（ユニット版で厳密確認、統合版では更新結果の正しさを確認）
- 🟡 信頼性レベル: note.mdの「has_condition方式（カンマ区切り）」記載から妥当な推測（単一フィールドケースは要件定義書に明示なし）

### TC-NEW-02: 単一フィールドのみのSET句生成（SET句ビルダー、ユニット）

- **テスト名**: `build_update_item_query`が単一フィールド指定時に余分なカンマを生成しない
  - **何をテストするか**: TC-NEW-01のSQL構築部分のみを実DB無しで検証する
  - **期待される動作**: 生成SQLが`status = `を含み、カンマの数が0（フィールド間区切りが発生しない）
- **入力値**: `UpdateItemRequest { status: Some(ItemStatus::Completed), ..None }`
  - **入力データの意味**: SET句項目数=1の境界
- **期待される結果**: `sql.contains("SET status = ")`が真、`sql.matches(',').count() == 0`（WHERE句のidバインドより前の部分に限定するか、SET句部分文字列を切り出して確認）
  - **期待結果の理由**: 1項目のみの場合に不要なカンマが残るとSQL構文エラーになるため
- **テストの目的**: カンマ結合ロジックの境界（0→1→2項目)を保証する
  - **確認ポイント**: SET句生成ロジックの先頭フラグ処理
- 🟡 信頼性レベル: note.mdのhas_condition方式記載からの妥当な推測

### TC-001-EDGE01-A: 全フィールドNoneでの無更新・SQL未実行（ユニット、分岐ロジック）

- **テスト名**: 全フィールドNoneの`UpdateItemRequest`に対してSET句ビルダーがNoneを返す（またはSET対象0件を示す）
  - **何をテストするか**: SET句生成関数が「更新対象なし」を呼び出し元（リポジトリ関数）に伝え、UPDATE文を組み立てない分岐に入れる契約になっているかを確認する
  - **期待される動作**: ビルダー関数が`Option<QueryBuilder>`等で「構築不要」を表現する場合は`None`、または空のSET句を示す値を返す
- **入力値**: `UpdateItemRequest`の全フィールドが`None`
  - **入力データの意味**: 要件定義書EDGE-0012-01の具体例（リクエストボディ`{}`相当）
- **期待される結果**: SET対象フィールド数が0であることを示す戻り値（実装の関数シグネチャに応じて`is_none()`または`fields_count()==0`で確認）
  - **期待結果の理由**: REQ-0012-101（UPDATE文を実行してはならない）に対応するための前段ロジック
- **テストの目的**: 「UPDATE実行 or 現状取得のみ」の分岐をリポジトリ層に正しく伝播できるかを確認する
  - **確認ポイント**: 関数の戻り値型が「SET対象なし」を表現できる設計になっていること
- 🔵 信頼性レベル: 要件定義書REQ-0012-101・EDGE-0012-01、note.md L36「SET句が0件のときはUPDATE文を実行せず取得のみ」より

### TC-001-EDGE01-B: 全フィールドNoneでの無更新・現状返却（実DB統合）

- **テスト名**: `update_item`が全フィールドNoneのとき現在の状態をそのまま返す
  - **何をテストするか**: 空オブジェクト相当の更新リクエストに対し、UPDATE文を実行せず（または実行されても実質的な変化がなく）、現在のitem状態がそのまま返るかを確認する
  - **期待される動作**: 戻り値が更新前の投入値と完全一致し、`updated_at`も変化しない
- **入力値**: 事前投入済みitem + `UpdateItemRequest`全フィールド`None`
  - **入力データの意味**: 要件定義書シナリオ2・EDGE-0012-01（リクエストボディ`{}`）に対応
- **期待される結果**: 戻り値の全フィールドが投入時の値と一致、`updated_at`が更新前と同一（トリガーが発火していないこと＝UPDATE文未実行の確認）
  - **期待結果の理由**: REQ-0012-101の「UPDATE文を実行しない」という厳密な要件を、`updated_at`不変という観測可能な形で検証する
- **テストの目的**: 無更新パスがDBへの実質的な副作用（トリガー発火含む）を一切起こさないことを保証する
  - **確認ポイント**: `updated_at`の値が変化しないこと（最も強い検証）
- 🔵 信頼性レベル: 要件定義書シナリオ2・REQ-0012-101・REQ-0012-202、タスクファイル「全フィールドがNoneの場合は何もUPDATEせず現在の状態を返す」より

### TC-NEW-03: 更新不可フィールドはデシリアライズで無視される（ユニット）

- **テスト名**: `UpdateItemRequest`に`media_type`・`source`・`external_id`相当のJSONキーを含めてもエラーにならず無視される
  - **何をテストするか**: リクエストJSONに本来存在しないフィールド（`media_type`等）が含まれた場合、serdeのデフォルト動作（未知フィールド無視）によってデシリアライズが成功し、`UpdateItemRequest`構造体にそれらの値が反映されないことを確認する
  - **期待される動作**: デシリアライズが成功し、`UpdateItemRequest`に`media_type`等のフィールド自体が存在しないため、SET句生成対象にもならない
- **入力値**: `{ "title": "新タイトル", "media_type": "movie", "source": "manual", "external_id": "999" }`
  - **入力データの意味**: 要件定義書シナリオ5・REQ-0012-05の直接的な検証データ。クライアントが誤って（または悪意を持って）更新不可フィールドを送信するケースを表す
- **期待される結果**: `serde_json::from_value::<UpdateItemRequest>(...)`が`Ok`を返し、`title`のみ`Some("新タイトル")`、その他のフィールドは構造体に存在しないため検証不能（＝コンパイル時に保証される）
  - **期待結果の理由**: REQ-0012-05「DTOに該当フィールドが存在しないことで保証する」という設計方針が実際に機能していることの確認
- **テストの目的**: 更新不可フィールド拒否の保証メカニズム（型レベルの保証）が破られていないことを回帰確認する
  - **確認ポイント**: 既存のTASK-0008テスト`update_item_request_deserializes_partial_fields`との重複を避けつつ、不可フィールド混入時の挙動に特化する
- 🔵 信頼性レベル: 要件定義書シナリオ5・REQ-0012-05より

## 2. 異常系テストケース（エラーハンドリング）

### TC-001-E02-A: 存在しないUUIDでITEM_NOT_FOUND（実DB統合）

- **テスト名**: `update_item`が存在しないitem IDに対して`Ok(None)`（または同等のNotFound表現）を返す
  - **エラーケースの概要**: 有効なUUID形式だが、DB上に該当レコードが存在しない場合の処理
  - **エラー処理の重要性**: 存在しないリソースへの更新試行をクライアントに正しく伝え、誤って「成功した」と誤認させないため
- **入力値**: `Uuid::new_v4()`で生成した未登録のUUID + 任意の`UpdateItemRequest`（例: `{ rating: Some(3.0) }`）
  - **不正な理由**: DBの`items`テーブルに対応する行が存在しない
  - **実際の発生シナリオ**: クライアントが古いキャッシュのIDを使って更新を試みた場合、または他ユーザーが既に削除した後にPATCHを送った場合
- **期待される結果**: リポジトリ関数が`Ok(None)`を返す（note.md L34の「RETURNING句をfetch_optionalで受け、空ならNotFound」方針）
  - **エラーメッセージの内容**: リポジトリ層ではNoneのみを返し、ApiErrorへの変換はハンドラ層の責務（責務分離の確認）
  - **システムの安全性**: 存在しない行へのUPDATEは0行に影響するのみで、他データへの副作用がないことを保証する
- **テストの目的**: 「UPDATE実行→影響0件→NotFound」のリポジトリ層ロジックを保証する
  - **品質保証の観点**: REQ-0012-202（影響行数0件もNotFoundとして扱う）の実装漏れを防ぐ
- 🔵 信頼性レベル: 要件定義書REQ-0012-201・REQ-0012-202、タスクファイルテストケース2（TC-001-E02）より

- 🔵 信頼性レベル: 要件定義書REQ-0012-102・EDGE-0012-101、タスクファイルテストケース3（TC-001-B01）より

### TC-NEW-04: 不正なUUID形式でVALIDATION_ERROR（ハンドラ、既存ロジック再利用確認）

- **テスト名**: `update_item_handler`が不正なUUID文字列のパスパラメータに対し400を返す

- **テストの目的**: REQ-0012-103（既存ID検証エラー処理に従う）を確認する
  - **品質保証の観点**: GET /items/:idとPATCH /items/:idでパスパラメータ検証の挙動に差異がないこと（一貫性）
- 🟡 信頼性レベル: 要件定義書REQ-0012-103・EDGE-0012-03（🟡相当の妥当な推測）より。既存`parse_item_id`のテストが別途存在する前提で、PATCH側では結合のみを確認する軽量テストとする

### TC-NEW-05: DBエラー発生時にInternalErrorへ正規化される（実DB統合、unreachable_pool）

- **テスト名**: `update_item`がDB接続不能時に`db_error`経由でInternalErrorに変換される
  - **エラーケースの概要**: DB接続自体が失敗するケース（ネットワーク障害、DB停止等）をシミュレートする
  - **エラー処理の重要性**: SQLエラーやDB内部情報をクライアントに漏洩させないことがセキュリティ要件（NFR-0012-02関連）であるため
- **入力値**: `unreachable_pool()`で構築した到達不能な`PgPool` + 任意のID・`UpdateItemRequest`
  - **不正な理由**: 接続先ホストが存在しないため、すべてのクエリがエラーになる
  - **実際の発生シナリオ**: 本番DBの一時的なダウンタイムやネットワーク分断時
- **期待される結果**: `update_item`が`Err(ApiError)`を返し、`ApiErrorCode::InternalError`（500）であること。エラーメッセージにSQL文やDB接続文字列が含まれないこと
  - **エラーメッセージの内容**: 既存`db_error`関数が返す汎用メッセージと同一
  - **システムの安全性**: 機密情報（接続文字列等）がレスポンスに漏れないことを文字列検証で確認
- **テストの目的**: REQ-0012-402（db_errorヘルパー経由の正規化）を新規UPDATE処理パスでも保証する
  - **品質保証の観点**: 既存の`db_error`変換テスト（item_repository.rs内、unreachable_pool使用パターン）と同型の回帰テストを追加することで、新規関数が規約から逸脱していないことを確認する
- 🔵 信頼性レベル: 要件定義書REQ-0012-402、note.md「db_errorヘルパーを必ず通す」「unreachable_poolパターン」より

## 3. 境界値テストケース（最小値、最大値、null等）

### TC-001-EDGE101: title=Some("")のみが空文字バリデーション対象、title=Noneは対象外（ユニット）

- **テスト名**: titleがNoneの場合は空文字バリデーションを実行しない
  - **境界値の意味**: 「`Some("")`」と「`None`」は明確に区別すべき境界であり、両者を混同すると正常な部分更新（titleを更新しないケース）まで誤ってエラー化してしまう
  - **境界値での動作保証**: `Option<String>`の3状態（`None` / `Some("")` / `Some("非空文字")`）すべてに対する分岐の一貫性を保証する
- **入力値**: ケースA: `title: None`（他フィールドのみ更新）／ケースB: `title: Some("")`／ケースC: `title: Some("正常タイトル")`
  - **境界値選択の根拠**: 要件定義書EDGE-0012-101「`title`が`None`の場合はバリデーション自体を実行してはならない」という明示要件の直接境界
  - **実際の使用場面**: ケースAは「titleを変更せず他フィールドだけ更新する」という最も一般的な部分更新パターンに対応
- **期待される結果**: ケースAはバリデーション成功（エラーなし）、ケースBはバリデーションエラー、ケースCはバリデーション成功
  - **境界での正確性**: `None`をバリデーション対象外として明確にスキップするロジックが必要（`if let Some(t) = &title { if t.is_empty() { ... } }`のような実装になっているか）
  - **一貫した動作**: 3パターンすべてが意図した分岐に入ることを1テスト内（または3テストに分割）で確認する
- **テストの目的**: Option型の状態判定漏れ（NoneをSomeとして誤処理する等）を防ぐ
  - **堅牢性の確認**: 部分更新の基本契約（更新対象外フィールドにはバリデーションをかけない）が破られないことを保証する
- 🔵 信頼性レベル: 要件定義書EDGE-0012-101より直接対応

### TC-NEW-06: title=Some(" ")（空白のみ文字列）の扱い確認（ユニット、要実装時確定）

- **テスト名**: 空白のみのtitleがバリデーション対象になるかを確認する
  - **境界値の意味**: 「長さ0」と「空白のみ（長さ>0だが視覚的に空）」の境界。要件定義書EDGE-0012-102で明確な仕様が定義されておらず、実装時に既存`validate_title`の挙動を確認して確定すべき事項
  - **境界値での動作保証**: 既存`CreateItemRequest`用`validate_title`が空白のみを許容するか拒否するかに、`UpdateItemRequest`側も合わせる必要がある
- **入力値**: `title: Some(String::from(" "))`（半角スペース1文字）
  - **境界値選択の根拠**: 要件定義書EDGE-0012-102「空白のみの文字列の扱いは本タスクの完了条件に明記がない」との記載に基づき、既存ロジックとの整合性を確認するための調査的テストケース
  - **実際の使用場面**: クライアント側でtitle欄にスペースのみ入力して送信してしまうケース
- **期待される結果**: 既存`validate_title`（CreateItemRequest用）が空白のみを拒否する実装であれば本テストもエラーを期待、許容する実装であれば成功を期待する。**いずれの仕様にするかは`tdd-red`着手前に既存`validate_title`実装（`models/item.rs`）を確認して確定すること**
  - **期待結果の理由**: 要件定義書の引き渡し事項に「既存validate_titleの実装箇所を確認し流用可能か確定すること」と明記されているため、実装確認後に期待値を固定する
  - **一貫した動作**: `CreateItemRequest`と`UpdateItemRequest`でtitleの有効性判定基準が異なると一貫性を欠くため、同一ロジックを参照すべき
- **テストの目的**: 仕様未確定部分を明示的にテストケース化し、実装時の意思決定を強制する
  - **堅牢性の確認**: 将来`validate_title`の実装が変わった場合に検知できる回帰テストとしても機能する
- 🟡 信頼性レベル: 要件定義書EDGE-0012-102（仕様未確定である旨を明記した黄信号要件）に基づく、実装時確認が前提のテストケース

### TC-NEW-07: ratingの最小値・最大値境界での更新（実DB統合、補助的）

- **テスト名**: ratingに極端な値（0.0、5.0等のドメイン上限値があれば）を設定して更新できる
  - **境界値の意味**: `rating: Option<f32>`はREQ-0012-401により本タスクではアプリ側バリデーション対象外と明記されているため、DBのCHECK制約等に委ねられる挙動を確認する
  - **境界値での動作保証**: バリデーションを行わない設計が意図通りであり、DB制約違反時は適切にエラーになることを確認する
- **入力値**: `rating: Some(0.0)`、`rating: Some(5.0)`（DBスキーマのCHECK制約範囲に応じる。範囲外の値、例: `Some(-1.0)`も別ケースとして検討可）
  - **境界値選択の根拠**: REQ-0012-401「title以外のフィールドのバリデーションは本タスクの範囲外」という制約要件の境界確認
  - **実際の使用場面**: 評価値の最小・最大設定操作
- **期待される結果**: DB側のCHECK制約内であれば200で更新成功。制約違反時はDBエラー→`db_error`経由でInternalError（アプリ側で個別の422等を返さないことを確認）
  - **境界での正確性**: アプリ層に独自のrating範囲チェックロジックが紛れ込んでいないことを確認する（REQ-0012-401の逸脱検知）
  - **一貫した動作**: title以外のフィールドに対する処理の一貫性（バリデーションなし）を保証する
- **テストの目的**: スコープ外バリデーションの不要な追加実装を防ぐ回帰テスト
  - **堅牢性の確認**: 将来someoneがrating範囲チェックを誤って追加した場合に検知する
- 🟡 信頼性レベル: 要件定義書REQ-0012-401からの妥当な推測（DBのCHECK制約有無はdatabase-schema.sql確認が前提、本タスクでは優先度低の補助的テストとして位置づける）
