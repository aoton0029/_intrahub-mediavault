# mediavault-backend 要件定義書

## 概要

MediaVaultバックエンドは、映画・アニメ・漫画・小説・ドラマ・ゲーム・論文/文献・学術書/専門書のメタデータを一元管理するセルフホスト型アプリケーションのうち、API提供・外部API連携・データベース管理を担う部分である。単一ユーザー前提でユーザー管理・認証機能は持たず、Rust(Axum) + PostgreSQL(sqlx) + Docker構成で実装する。

現状、`backend/src` は空のスケルトン（main.rs に `Hello, world!` のみ）であり、実装はゼロからのスタートとなる。一方 `api-client-lib` には Jikan/TMDb/NDL/OpenLibrary/Steam/IGDB/AniList の外部APIクライアント実装が既に存在しており、これを活用する。

## 機能要件（EARS記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: PRD・tech-stack・ユーザヒアリングを参考にした確実な要件
- 🟡 **黄信号**: PRD・tech-stack・ユーザヒアリングから妥当な推測による要件
- 🔴 **赤信号**: PRD・tech-stack・ユーザヒアリングにない推測による要件

### 通常要件

- REQ-001: システムは `items` テーブルに対する作品の新規登録・取得・更新・削除（CRUD）APIを提供しなければならない 🔵 *backend/docs/PRD.md 共通機能より*
- REQ-002: システムは外部API検索（メディア種別に応じてJikan/TMDb/NDL/OpenLibrary/Steam/IGDBを呼び分け）の結果からアイテムを新規作成できなければならない 🔵 *PRD「作品検索・追加（API）」より*
- REQ-003: システムはAPI検索結果に依存せず、フォーム入力のみでアイテムを新規作成できなければならない 🔵 *PRD「作品手動追加」より*
- REQ-004: システムはタグ・カテゴリの作成、アイテムへの付与・削除を行うAPIを提供しなければならない 🔵 *PRD「タグ/カテゴリ管理」より*
- REQ-005: システムは任意名称のマイリスト（`mylists`）の作成、アイテムの追加・削除を行うAPIを提供しなければならない 🔵 *PRD「マイリスト管理」より*
- REQ-006: システムは他メディアのアイテムへの関連付け（`item_relations`、relation_type=reference/dlc）を作成・削除できなければならない 🔵 *PRD「関連付け」より*
- REQ-007: システムは `item_links`・`item_files`・`item_trailers` の追加・編集・削除APIを提供しなければならない 🔵 *PRD「リンク/ファイル/トレーラー管理」より*
- REQ-008: システムはアイテムの `status`（視聴中/読了/未着手等）と `consumed_date` を更新できなければならない 🔵 *PRD「視聴・読了記録」より*
- REQ-009: システムはスタッフ（`staff`）の追加、役割（role）の付与、作品への紐付け（`item_staff`）を行うAPIを提供しなければならない 🔵 *PRD「スタッフ管理」より*
- REQ-010: システムはアニメ・ドラマについてシーズン単位（`item_groups`, group_type=season）の話数（`item_episodes`）の登録・編集・一覧表示APIを提供しなければならない 🔵 *PRD メディア別機能より*
- REQ-011: システムは漫画・小説について巻単位のグループ管理（`item_groups`, group_type=volume）を提供しなければならない 🔵 *PRD メディア別機能より*
- REQ-012: システムは映画について章単位のグループ管理（`item_groups`, group_type=chapter）を任意で提供してもよい 🔵 *PRD メディア別機能より（オプション要件）*
- REQ-013: システムはゲームのDLC/拡張パックを `item_relations`（relation_type=dlc）で本体作品に紐付けられなければならない 🔵 *PRD メディア別機能より*
- REQ-014: システムは学術書・専門書（著者・出版社・ISBN等）および論文・文献（DOI・掲載誌・巻号・ページ等）特有の属性でのCRUDを提供しなければならない 🔵 *PRD メディア別機能より*
- REQ-015: システムは各外部APIのキー（TMDb・IGDB・NDL等。Jikanはキー不要）をDBに登録・更新するAPIを提供しなければならない 🔵 *ヒアリングにて確定（DB保存を採用）*
- REQ-016: システムはブクログ(csv)からのアイテム一括インポート機能を提供しなければならない 🔵 *PRD「インポート」・ヒアリングで今回スコープに含めることを確認*
- REQ-017: システムはSteamライブラリからのアイテム一括インポート機能を提供しなければならない 🔵 *PRD「インポート」・ヒアリングで今回スコープに含めることを確認*
- REQ-018: システムは内部REST API（巡回バッチ・ファイルサーバー監視プロセスからのアイテム登録・更新・検索・ファイル紐付け）をAPIキー1本による簡易認証で提供しなければならない 🔵 *PRD「外部から登録・更新・検索をするためのAPI」・ヒアリングで今回スコープに含めることを確認*
- REQ-019: システムは `item_files` のファイル登録時、ファイルサーバー上の既存パスを指定する方式と、バイナリを直接アップロードしてサーバー側で配置する方式の両方をサポートしなければならない 🔵 *ヒアリングにて両対応を確定*
- REQ-020: PDFファイルを登録する場合、システムは `calibre_book_id` を紐付け更新できなければならない 🔵 *PRD「ファイルアップロード」より*

### 条件付き要件

- REQ-101: media_typeが anime または drama の場合、システムはシーズン（`item_groups`）配下に話数（`item_episodes`）を登録できなければならない 🔵 *データモデル定義より*
- REQ-102: media_typeが manga または novel の場合、システムは巻（`item_groups`, group_type=volume）を登録できる。volumeには `item_episodes` を使用してはならない 🔵 *PRDデータモデル注記より*
- REQ-103: file_typeが pdf の場合、システムはCalibre-Web側の取り込み完了後に `calibre_book_id` を更新できなければならない 🔵 *PRD「ファイルアップロード」より*
- REQ-104: バイナリ直接アップロードの場合、システムはfile_typeに応じて `/srv/files/pdf` または `/srv/media/photos` に配置し、配置後の相対パスを `item_files.path` に保存しなければならない 🟡 *既存パス規約からの妥当な推測*

### 状態要件

- REQ-201: アイテムの `source` が `manual` の場合、システムは `external_id` をNULL許容として扱わなければならない 🟡 *データモデルから妥当な推測*
- REQ-201b: アイテムの `source` が `api` の場合、システムは `external_id` を保持しなければならない 🟡 *データモデルから妥当な推測*

### オプション要件

- REQ-301: システムはコレクションをObsidian/Notion向け形式でエクスポートする機能を提供してもよい（次回フェーズ） 🟡 *PRDに記載あるがヒアリングで本フェーズ対象外と確認*
- REQ-302: システムは映画の章単位グループ管理機能を提供してもよい 🔵 *PRDにて任意機能と明記*

### 制約要件

- REQ-401: システムはユーザー管理機能・ログイン認証機能を持ってはならない（単一ユーザー前提） 🔵 *PRD「やらなくていいこと」より*
- REQ-402: システムはファイル本体をアプリコンテナ内に保存してはならず、ファイルサーバー用HDDへのバインドマウントパスのみをDBに保持しなければならない 🔵 *PRD・tech-stackより*
- REQ-403: 内部REST APIへのアクセスは `Authorization` ヘッダー等によるAPIキー検証を必須としなければならない 🔵 *tech-stack.md「内部REST API認証」より*
- REQ-404: 外部APIキー・内部APIキーはリポジトリにコミットしてはならず、`.env`または DBで管理しなければならない 🔵 *tech-stack.md「環境変数」より*
- REQ-405: DBスキーマは `items` 共通テーブル + メディア種別ごとの詳細テーブル（`anime_details`等）のJOIN構成としなければならない 🔵 *PRDデータモデルより*

## 非機能要件

### パフォーマンス

- NFR-001: 単一ユーザー・セルフホスト運用を前提とし、同時接続数は少数（数接続程度）を想定したコネクションプール設定で問題ない 🟡 *単一ユーザー前提から妥当な推測*
- NFR-002: 一覧・絞り込みAPIは数千件規模のアイテム数でも応答時間1秒以内を目標とする 🟡 *自己ホスト型コレクション管理の規模感から妥当な推測*

### セキュリティ

- NFR-101: 内部REST APIはAPIキー1本によるヘッダー検証ミドルウェアで保護しなければならない 🔵 *tech-stack.mdより*
- NFR-102: 入力検証はAxum側でリクエストボディ・パスパラメータに対して実施しなければならない 🔵 *tech-stack.md「入力検証」より*
- NFR-103: 外部公開時はリバースプロキシ（Caddy/nginx等）でHTTPS終端を行う想定とし、API自体はHTTPS終端を持たない 🔵 *tech-stack.md「通信」より*

### ユーザビリティ・保守性

- NFR-201: マイグレーションは `sqlx-cli`（`sqlx migrate`）で管理し、スキーマ変更履歴を追跡可能にしなければならない 🔵 *tech-stack.mdより*
- NFR-202: APIキー管理機能により、外部APIキーをコード変更なしにDB経由で更新可能にしなければならない 🔵 *ヒアリングで確定*

## Edgeケース

### エラー処理

- EDGE-001: 外部API検索で対象APIが利用不可（タイムアウト・APIキー未設定等）の場合、システムはエラーを返しつつ手動追加（REQ-003）への切り替えを妨げてはならない 🟡 *PRD構成から妥当な推測*
- EDGE-002: ブクログCSV・Steamライブラリインポートで一部行が形式不正の場合、システムは不正行のみスキップし正常行の取込を継続しなければならない 🟡 *インポート機能の一般的挙動から妥当な推測*
- EDGE-003: バイナリ直接アップロードでファイルサーバーへの書き込みに失敗した場合、システムは `item_files` レコードを作成してはならない（ロールバック） 🟡 *データ整合性確保の観点から妥当な推測*

### 境界値

- EDGE-101: `item_episodes` はseason/chapter配下のみで使用可能とし、volume配下のグループへの登録はリクエストを拒否しなければならない 🔵 *PRDデータモデル注記より*
- EDGE-102: `item_groups` はparent_item_idを通じて入れ子構造を持てるが、DLC等の作品間関係は対象外とし `item_relations` で表現しなければならない 🔵 *PRDデータモデルより*
