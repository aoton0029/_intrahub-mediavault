# backend-frontend-integration ヒアリング記録

**作成日**: 2026-07-02
**ヒアリング実施**: step4 既存情報ベースの差分ヒアリング

## ヒアリング目的

`docs/PRD-integration.md` に加え、既存の `backend/Dockerfile`・`backend/docker-compose.yml`・`frontend/src/api/client.ts`・`frontend/vite.config.ts` 等の実装状況を確認したうえで、PRDに明記されていない不明点（CI連携方針、selfhosted対応範囲、dev サーバーの扱い、APIベースURLの変更可否、既存ポート公開設定の扱い）を明確化するためヒアリングを実施しました。

## 質問と回答

### Q1: CI（.github/workflows/backend-ci.yml）の再構築・移行について

**質問日時**: 2026-07-02
**カテゴリ**: 影響範囲確認
**背景**: `git status` で `.github/workflows/backend-ci.yml` が削除(D)扱いになっており、今回の統合作業がCI再構築を含むか不明瞭だったため

**回答**: 対象外（CI再構築は本要件のスコープに含めない）

**信頼性への影響**:
- REQ-403 を制約要件として追加（信頼性レベル: 🔵）
- スコープが明確化され、要件全体の曖昧さが低減

---

### Q2: selfhosted環境固有の設定（外部ファイルサーバーのバインドマウント、ドメイン/HTTPS終端）について

**質問日時**: 2026-07-02
**カテゴリ**: 未定義・曖昧部分の詳細化
**背景**: PRDの前提・スコープに「ローカル環境・selfhosted環境の両方で起動確認できるようにする」とあるが、selfhosted固有設定の扱いが不明瞭だったため

**回答**: 対象外（最小限の環境変数切り替えのみとし、HTTPS終端やファイルサーバー本番運用設定は含めない）

**信頼性への影響**:
- REQ-404 を制約要件として追加（信頼性レベル: 🔵）
- 「selfhosted環境」というPRD記載の解釈の曖昧さが解消

---

### Q3: docker-compose統合環境でのフロントエンド配信方式（nginx配信 vs Vite dev サーバーのコンテナ化）について

**質問日時**: 2026-07-02
**カテゴリ**: 未定義・曖昧部分の詳細化
**背景**: PRDに「開発時はViteのプロキシ設定でbackend:8080へ転送」との記載があり、docker-compose統合環境でVite dev サーバーもコンテナ化する想定か、nginxでビルド成果物のみ配信する想定か不明瞭だったため。初回質問では意図が伝わらず、再質問を実施

**回答**: 問題ない（nginxのみで良い。統合環境の目的は結合テスト・Webアプリとしての動作確認であり、Vite dev サーバーは `docker-compose` 外で `yarn dev` を使う場合のみ使用）

**信頼性への影響**:
- REQ-004・REQ-405 の信頼性レベルが 🟡 → 🔵 に向上
- フロントエンドコンテナの実装方針（nginx配信のみ）が確定

---

### Q4: フロントエンドAPI呼び出しの `VITE_API_BASE_URL` から相対パス `/api/v1` への変更を要件に含めるか

**質問日時**: 2026-07-02
**カテゴリ**: 影響範囲確認
**背景**: 既存実装（`frontend/src/api/client.ts`）は `VITE_API_BASE_URL` 環境変数（ビルド時埋め込み）でAPI URLを切り替えているが、PRDでは相対パス `/api/v1` への統一が提案されており、既存実装への影響範囲を確認する必要があったため

**回答**: 含める（推奨どおり相対パスへ変更）

**信頼性への影響**:
- REQ-009 の信頼性レベルが 🟡（PRDのみからの推測）→ 🔵（ヒアリングで確定）に向上

---

### Q5: 既存 `backend/docker-compose.yml` のポート公開（db: 5432:5432、app: 8080:8080）を統合用composeで非公開に変更してよいか

**質問日時**: 2026-07-02
**カテゴリ**: 既存設計の妥当性・過不足確認
**背景**: PRDでは「backend と db はホストにポート公開しない」とあるが、既存の `backend/docker-compose.yml` には両方ともポート公開設定が存在しており、この既存ファイルを変更するか、統合用の新規composeでのみ非公開にするかが不明瞭だったため

**回答**: はい、非公開にする（ただし統合用composeのみ。既存の `backend/docker-compose.yml`（backend単体起動用）は変更しない）

**信頼性への影響**:
- REQ-401・REQ-402 を制約要件として追加（信頼性レベル: 🔵）
- 既存ファイルとの責務分離が明確化

---

## ヒアリング結果サマリー

### 確認できた事項
- フロントエンドコンテナはnginxによるビルド成果物配信のみで、Vite dev サーバーのコンテナ化は不要
- API呼び出しは相対パス `/api/v1` へ統一する
- 統合用docker-composeでは `backend`・`db` にホストポートを公開しない。ただし既存の `backend/docker-compose.yml`（backend単体起動用）は変更しない
- CI再構築・selfhosted本番設定（HTTPS終端・外部ファイルサーバー本番運用）は本要件のスコープ外

### 追加/変更要件
- REQ-009（API呼び出しの相対パス化）
- REQ-401, REQ-402（ポート非公開方針と既存ファイル不変更の切り分け）
- REQ-403, REQ-404, REQ-405（スコープ外事項の明確化）

### 残課題
- 統合用compose定義のファイル名（`docker-compose.yml` か `docker-compose.integration.yml` か）は未確定（REQ-301として選択肢を残す）
- `frontend` のホスト公開ポート番号の最終決定（PRDでは暫定案として80番）
